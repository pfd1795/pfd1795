Data modelling and normalisation

Before writing CREATE TABLE, you have to decide which entities exist, what attributes they have and how they relate. A good model avoids duplicated data, inconsistencies and anomalies when inserting, updating or deleting. Normalisation is the systematic process for reaching that model.

In 5 points

  • Modelling is describing reality as entities, attributes and relationships, not as tables from the start.
  • Redundancy causes anomalies: the same data repeated gets out of sync when updated.
  • Keys (primary, foreign) identify rows and connect tables.
  • Normal forms (1NF, 2NF, 3NF, BCNF) eliminate partial and transitive dependencies.
  • Deliberate denormalisation can improve read performance, at a maintenance cost.

What is data modelling?

A data model describes the information a system handles and its rules. You start from reality (customers, orders, products) and end up with a table schema. The basic concepts:

  • Entity: thing or object of the domain (Customer, Order).
  • Attribute: property of the entity (name, date, price).
  • Relationship: link between entities (one customer places many orders).
  • Cardinality: how many instances take part (1:1, 1:N, N:M).

An N:M relationship (order-product) is resolved with an intermediate table (order_product) containing the foreign keys of both. That step is essential before creating tables.

Anomalies and redundancy

Imagine a single orders table that repeats the customer data in every row: 

order_id | customer_name | customer_email | product | quantity
1         | Ana            | ana@mail.com  | Book     | 2
2         | Ana            | ana@mail.com  | Pencil   | 5

If Ana changes her email, every one of her rows has to be updated; if one is forgotten, two different emails remain for the same customer. That is an update anomaly. There are also insertion anomalies (you cannot register a customer without an order) and deletion anomalies (deleting the last order also deletes the customer). The common cause is redundancy: the same data stored several times.

Keys

  • Primary key (PK): uniquely identifies each row. Not null and without duplicates.
  • Foreign key (FK): column referencing the PK of another table; keeps referential integrity.
  • Candidate key: any set of columns that could be a PK; one is chosen as primary.
  • Composite key: PK formed by several columns (e.g. order line).
  • Surrogate key: artificial identifier (auto-increment/UUID) when there is no stable natural key.

Prefer surrogate keys for internal PKs and natural keys (email, ID number) as additional unique constraints. FKs should be indexed to speed up JOINs and cascades.

Normal forms

Normalisation applies progressive rules. Each normal form (NF) eliminates one kind of problematic dependency.

Normal form Rule What it removes
1NFAtomic values; no repeated groups; each row unique.Lists inside a cell; duplicate rows.
2NF1NF + no non-key attribute depends on part of a composite PK.Partial dependencies.
3NF2NF + no non-key attribute depends on another non-key attribute.Transitive dependencies.
BCNFEvery functional dependency X→Y implies X is a candidate key.Edge cases 3NF does not cover.

Example: from a single table to 3NF

Original table (denormalised):

order (order_id, customer_name, customer_email, product_name, price, quantity)

Steps:

  1. 1NF: already atomic; split the order line if an order has several products.
  2. 2NF: customer_name and customer_email depend only on order_id (not on the composite PK order_id+product). They move to customer.
  3. 3NF: price depends on product, not on the order. It moves to product.

Result:

customer (customer_id, name, email)
order (order_id, customer_id, date)
product (product_id, name, price)
order_product (order_id, product_id, quantity)

When to denormalise

Normalisation optimises writing and consistency. But read queries (reports, dashboards) may require many JOINs. In those cases you denormalise deliberately: you duplicate a computed field or create an aggregate table. Always with a process that keeps the copy in sync (triggers, jobs, or recomputation).

Practical rule: normalise first; measure; denormalise only where the JOIN is the real bottleneck and document the source of truth.

Best practices

  • Start with a conceptual model (entities/relationships) and then move to tables.
  • Use clear, consistent names (singular or plural, but only one).
  • Define PK and FK from the start; add NOT NULL and UNIQUE constraints.
  • Normalise to 3NF by default; justify any deviation.
  • Version the schema (migrations) and document the changes.
  • Index the columns used in JOIN, WHERE and ORDER BY.

Common mistakes

Mistake Why it is wrong What to do
Storing lists in a column (CSV) Violates 1NF; cannot be queried or indexed well. Create a child table with one row per element.
Repeating customer data in every order Update anomalies and inconsistencies. Split into a customer table with an FK.
Not defining foreign keys Orphaned data and broken integrity. Declare FKs and decide ON DELETE/UPDATE.
Over-normalising (dozens of tables for everything) Complex and slow queries; costly maintenance. Balance with real use cases and denormalise if needed.
Using mutable data as PK Changing the PK forces massive cascades. Use a surrogate key (id) and a unique constraint on the natural data.
