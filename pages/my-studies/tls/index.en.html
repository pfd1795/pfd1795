Networks

Network security and TLS

Packets travel across the Internet and anyone in the middle can read or manipulate them. TLS (Transport Layer Security) adds confidentiality, integrity and authenticity: it is the «S» in HTTPS and it also protects SMTP, SSH and other protocols.

What problems TLS solves

Without TLS, whoever controls the route (a shared Wi-Fi, a router at your ISP, a corporate proxy) can read the traffic and modify it in flight. TLS aims at the three basic guarantees:

Property Without TLS With TLS
ConfidentialityAnyone on the route reads the dataSymmetric encryption with session keys
IntegrityPackets could be altered silentlyMAC per record: change means broken connection
AuthenticityAn impostor passes itself off as the serverThe server proves its identity with a certificate

TLS protects transit; it says nothing about how data is stored on arrival. For data at rest there is disk encryption and the good practices of Security · Web applications, and the concrete algorithms are explained in Cryptography basics.

The handshake: how the connection is agreed

Before sending a single byte of HTTP, client and server negotiate the algorithms and exchange cryptographic material. Summary of the flow in TLS 1.3 (the current one):

  1. ClientHello: the client offers the cipher suites it supports and its key exchange (for example X25519).
  2. ServerHello + Certificate: the server chooses a suite, delivers its certificate and its part of the exchange.
  3. Verification: the client validates the certificate (signed by a known CA, matching domain, not expired).
  4. Session keys: both parties derive the same symmetric key without it travelling over the network.
  5. Application Data: everything else is encrypted and authenticated.
# Agreed version and suite (output of two handshakes, 1.3 and 1.2)
  TLSv1.3  TLS_AES_256_GCM_SHA384     # X25519 exchange, AES-256-GCM
  TLSv1.2  ECDHE-RSA-AES128-GCM-SHA256

In TLS 1.3 the handshake takes a single round trip (two in 1.2) and only guarantees forward secrecy: if the server's private key is stolen tomorrow, today's recorded sessions cannot be decrypted.

Certificates and chains of trust

An X.509 certificate binds a domain name to a public key, signed by a certificate authority (CA). The browser ships with the root CAs it trusts pre-installed; your certificate is signed by a CA, which in turn chains up to a root. 

Root CA (root, pre-installed in your OS/browser)
    └─ Intermediate CA (intermediate, signed by the root)
          └─ server.example.com (your certificate, signed by the intermediate)

Fields to review in a certificate:

  • CN / SAN: which domains it is valid for (SAN includes them all; CN is now historical).
  • Validity: issue and expiry dates. Today the standard duration is getting shorter (~90 days at Let's Encrypt).
  • Algorithms: signature (SHA-256+) and key type (RSA≥2048, ECDSA, Ed25519).

Trust is demonstrated, not promised: the browser checks the chain, the expiry and the revocation. A badly installed certificate (missing intermediate) works for you but fails in other browsers: your server must serve the full chain.

HTTPS from the client's point of view

For the user all of this reduces to visible browser details; for you as a developer it has concrete consequences:

  • Locked padlock: correct TLS. The padlock does not certify that the site is honest, only that the domain is who it claims to be.
  • Risk warning: expired certificate, untrusted self-signed one, different domain… the browser blocks access instead of letting it through.
  • Struck-through padlock / «Not secure»: HTTPS with content loaded over internal HTTP (mixed content). Browsers mark the page as partially insecure and block active scripts outright.
  • Cookies marked Secure do not travel over HTTP: if your site calls an HTTP API, it breaks in production.
<!-- mixed content danger: inside an HTTPS page -->
  <img src="http://cdn.example/image.jpg">      <!-- ⚠ passive -->
  <script src="http://cdn.example/lib.js"></script> <!-- 🚫 blocked -->

HSTS: forgetting about HTTP

HTTP Strict Transport Security is the header that instructs the browser to talk to your domain over HTTPS only after the first visit, even if the user types http:// or a link points to it. It easily prevents a downgrade on the first request. 

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  • max-age: how many seconds the browser's commitment lasts.
  • includeSubDomains: extends the obligation to all subdomains.
  • preload: includes your domain in the browsers' preloaded lists (first make sure you can keep HTTPS always).

HSTS is one-way: if you enable includeSubDomains or preload without HTTPS on ALL subdomains, you block parts of your own site (impossible to revert quickly, the browser stores it for months). Start without preload and test it.

TLS in other protocols

The same scheme protects more than the web; there are «STARTTLS» variants that upgrade an already-open protocol:

Service With TLS Comment
HTTPS (HTTP)Port 443The case this article is devoted to
SMTP / IMAP / POP3465 / 993 / 995 (implicit) or STARTTLSEmail, or everything goes in the clear
FTP→FTPS / SSH / SFTP990 / 22scp and sftp use SSH, not TLS
PostgreSQL / MySQL5432 / 3306 (optional with TLS)Use sslmode=verify-full: check that you enable it

Verifying certificates and connections

Command-line tools to inspect your own deployments:

# See the certificate served by a domain (issuer, validity, algorithms)
  openssl s_client -connect pfd1795.github.io:443 -servername pfd1795.github.io </dev/null 2>/dev/null \
    | openssl x509 -noout -subject -dates -issuer

  # Full connectivity, agreed suite and chain
  openssl s_client -connect pfd1795.github.io:443 -servername pfd1795.github.io -brief </dev/null

  # Check the expiry of a local file
  openssl x509 -in cert.pem -noout -dates

  # From curl: headers and handshake detail
  curl -vI https://pfd1795.github.io/ | head -25

  # Is HSTS and mandatory HTTPS present after a redirect?
  curl -sI http://pfd1795.github.io/ | grep -iE 'location|strict-transport'

These commands are legitimate introspection of your services. Scanning third parties is a different matter: do it only with authorisation. More web checks in Security · Checking your own site.

Best practices

  • HTTPS in production always; renew certificates with automation (certbot, Caddy or your hosting's CI).
  • Serve the full certificate chain, not only your domain's.
  • Disable TLS 1.0/1.1: only 1.2 and 1.3 remain.
  • Redirect every HTTP request to HTTPS and add Strict-Transport-Security.
  • Do not mix HTTP content inside HTTPS pages: upload the resources or serve relative data.
  • Monitor expiry: an alert before a certificate expires saves your users a day of panic.
