Software architecture and design

Design patterns

A design pattern is a reusable solution to a problem that appears again and again when designing software. It is not copyable code or a framework: it is a name and a structure that developers recognise. Used well it improves communication and maintainability; used for fashion, it worsens them.

In 5 points

  • A pattern describes problem + solution + consequences, not implementation.
  • They are grouped into creational (how objects are created), structural (how they are composed) and behavioural (how they interact).
  • The most used: Factory, Adapter, Decorator, Observer, Strategy, Facade.
  • A pattern is good when it solves a real problem; applied without need it is over-engineering.
  • Patterns combine with the SOLID principles and with composition.

What is a pattern?

Popularised by the book «Design Patterns» (Gang of Four, 1994), patterns describe proven solutions to recurring object-oriented design problems. Each pattern includes: name, problem, solution, structure and consequences. They are not algorithms or libraries; they are shared vocabulary («use an Observer here»).

Patterns are not exclusive to OOP; they also exist in functional programming (functors, monads) and in architecture (MVC, CQRS). Here we focus on the classic OOP ones.

Creational patterns

They control how objects are created, decoupling creation from use.

Factory Method

Delegates creation to subclasses or functions, so the client does not depend on the concrete class.

function createLogger(type) {
  if (type === 'file') return new FileLogger();
  if (type === 'console') return new ConsoleLogger();
  throw new Error('Unknown type');
}
const log = createLogger('console');
log.info('hello');

Builder

Builds complex objects step by step, useful when there are many optional parameters.

class PizzaBuilder {
  constructor() { this.ingredients = []; }
  withCheese() { this.ingredients.push('cheese'); return this; }
  withPepperoni() { this.ingredients.push('pepperoni'); return this; }
  build() { return new Pizza(this.ingredients); }
}
const pizza = new PizzaBuilder().withCheese().withPepperoni().build();

Singleton (with reservations)

Guarantees a single instance. Useful for configuration or pools, but it hinders tests and hides dependencies. Prefer dependency injection.

Structural patterns

They compose classes and objects to form larger structures.

Adapter

Converts the interface of a class into another the client expects. Useful for integrating external libraries.

class OldApi { getUser(id) { /* ... */ } }
class UserAdapter {
  constructor(api) { this.api = api; }
  get(id) { return this.api.getUser(id); } // new interface
}

Decorator

Adds responsibilities to an object dynamically, without subclasses. Example: adding logging to a function.

function withLog(fn) {
  return function (...args) {
    console.log('calling with', args);
    return fn(...args);
  };
}
const sumWithLog = withLog((a, b) => a + b);

Facade

Provides a simple interface to a complex subsystem (e.g. a module that hides several services).

Behavioural patterns

They define how responsibilities are assigned and how objects communicate.

Observer

A subject notifies its observers when its state changes. Basis of events and reactivity.

class EventEmitter {
  constructor() { this.listeners = {}; }
  on(event, cb) { (this.listeners[event] ||= []).push(cb); }
  emit(event, data) { (this.listeners[event] || []).forEach(cb => cb(data)); }
}
const bus = new EventEmitter();
bus.on('msg', (m) => console.log('received', m));
bus.emit('msg', 'hello');

Strategy

Defines a family of interchangeable algorithms. Avoids giant switches.

const strategies = {
  fast: (a, b) => a + b,
  safe: (a, b) => a + b + validate(a, b),
};
function calculate(a, b, mode) {
  return strategies[mode](a, b);
}

Command

Encapsulates a request as an object, allowing undo/redo and execution queues.

Problem Pattern
Create objects without coupling to the concrete classFactory Method
Build objects with many optional parametersBuilder
Adapt an incompatible interfaceAdapter
Add behaviour dynamicallyDecorator
Simplify a complex subsystemFacade
Notify several interested parties of changesObserver
Swap algorithms at runtimeStrategy
Undo/redo or queue actionsCommand

When NOT to use them

  • When the problem does not exist yet: do not anticipate abstractions.
  • When a simple function or composition solves the case.
  • When the team does not know the pattern: the code becomes opaque.
  • When the pattern adds more indirection than value.

«Design Patterns» warns: patterns describe how to solve, not when. The decision to apply them is one of design, not of catalogue.

Best practices

  • Start with the problem, not with the pattern.
  • Prefer composition over inheritance.
  • Use patterns as vocabulary in reviews and documentation.
  • Keep patterns small and testable.
  • Combine patterns with SOLID and dependency injection.

Common mistakes

Mistake Why it is wrong What to do
Applying patterns «just because» Over-engineering: more classes, more indirection, less clarity. Justify each pattern with a real problem.
Singleton for everything Hidden global state, hard to test. Inject dependencies; reserve Singleton for unique resources.
Deep pattern inheritance Fragile coupling. Prefer composition and delegation.
Confusing pattern with framework Infrastructure is expected that does not exist. A pattern is an idea, not a library.
Not documenting the intent The code looks arbitrary. Name the pattern in comments/PRs when it adds value.
