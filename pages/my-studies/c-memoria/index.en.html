Programming languages

C and memory management

C is a compiled programming language that offers direct control over the representation and lifetime of data. That control makes it possible to build efficient software, but it also requires understanding pointers, memory limits and resource release. Knowing the difference between the stack and the heap helps write safer programs and avoid errors such as leaks, invalid accesses and buffer overflows.

In 5 points

  • C lets you work close to memory, but the programmer must respect types, object limits and lifetimes.
  • A pointer holds an address; using it requires that address to be valid and the object it points to to still exist.
  • The stack usually holds data with automatic lifetime, while dynamic memory is requested on the heap and must be managed explicitly.
  • Every successful dynamic allocation must have a clear release plan, and the program must check whether allocation failed.
  • Out-of-bounds accesses, dangling pointers and unterminated strings can cause undefined behavior and vulnerabilities.

What is it?

C is a general-purpose language used, among other fields, in operating systems, drivers, development tools and programs where resource control matters. Source code is compiled into instructions that a platform can execute. C offers operations on values and also tools for working with memory addresses.

Memory is the space where a program keeps instructions and data while it runs. A variable represents an object with a type and a lifetime. The type determines what kind of value it can hold and how it is interpreted; the lifetime indicates during which part of the execution that object exists.

In C, the programmer can declare objects with automatic, static or dynamic lifetime. In practice, people often talk about the stack and the heap to explain two common ways of organizing memory, although those terms describe implementation conventions and do not replace the formal rules of the language.

A memory error can be subtle: the program may compile and work in a test, but fail with other data or on another platform. Some errors produce wrong results; others imply undefined behavior, that is, the C standard does not establish what should happen. That is why one should not rely on an invalid access always causing a visible failure.

In C, memory control does not mean the program can safely access any address. Only valid objects, within their limits and during their lifetime, should be used.

Compilation and program structure

A C source file usually has the .c extension. The build process includes preprocessing directives such as #include, compiling the code and linking the resulting objects with the needed libraries. The concrete tools and options depend on the platform.

This minimal program includes the declaration of a standard function for printing text and a main function, which is the usual entry point of an application: 

#include <stdio.h>

int main(void) {
    int quantity = 3;
    printf("Quantity: %d\n", quantity);
    return 0;
}

In an environment that has a GCC-compatible compiler available, an example command to compile it would be: 

cc -std=c17 -Wall -Wextra -Wpedantic program.c -o program

-std=c17 requests a C17 standard mode in compilers that support it, and the -Wall, -Wextra and -Wpedantic options enable groups of useful warnings. A warning does not always indicate an error, but it is worth understanding before ignoring it.

The function returns an integer value to the environment. By convention, 0 usually indicates successful completion. For small programs, keeping input, processing and resource release organized makes it easier to follow the execution flow.

The compile command is illustrative: the compiler name, available options and program execution may change depending on the operating system and the installed toolchain.

Types and variable declaration

Every object in C has a type. Integer types, such as int and size_t, represent whole numbers; floating-point types, such as double, represent approximate values with a fractional part; and derived types, such as arrays and structures, group data. The char type can represent a character unit and is also used when working with bytes.

A declaration gives a name and a type to an object. If the object can change, it is usually called a variable. Initializing it at declaration avoids depending on an indeterminate value: 

int attempts = 0;
double temperature = 21.5;
char initial = 'M';

An array contains a fixed number of elements of the same type, placed consecutively. C indices start at zero. An array of four elements has valid indices from 0 to 3; accessing 4 is out of bounds. 

int scores[4] = {12, 18, 15, 20};

for (size_t i = 0; i < 4; i++) {
    printf("%d\n", scores[i]);
}

In the example, size_t is an unsigned integer type commonly used for sizes and indices. When iterating over an array, the loop bound must match the actual number of elements. C does not automatically check array bounds at runtime.

Pointers and memory addresses

A normal variable holds a value. A pointer is an object whose value can be the address of another object, as long as the pointer's type is compatible. The declaration int *p indicates that p can point to an int.

The & operator obtains the address of an object, and the * operator, when applied to a valid pointer, allows access to the pointed-to object. Using * to declare a pointer and to dereference it is related, but its concrete meaning depends on context. 

int temperature = 18;
int *pointer = &temperature;

*pointer = 19;
printf("%d\n", temperature);

pointer holds the address of temperature. Writing *pointer = 19 modifies the pointed-to object; therefore, afterwards, temperature is 19. A null, indeterminate or no-longer-alive pointer must not be dereferenced.

The special value NULL represents a pointer that points to no object. It can be used to indicate «no object» and to check whether a function returned a valid pointer. It is not an address that can be read or written.

Pointers also appear when passing data to functions. C passes arguments by value: a function receives a copy of the argument. If a function is to modify an object of the caller, a pointer to that object can be passed: 

void increment(int *value) {
    if (value != NULL) {
        *value += 1;
    }
}

The function checks that the pointer is not null before using it. That check cannot prove that any non-null address is valid, but it does avoid the specific case of receiving NULL.

Stack vs heap

The stack is usually associated with function calls and objects with automatic lifetime. When entering a function, its automatic local variables cease to exist when their block ends. By contrast, dynamic memory is requested during execution and keeps its lifetime until it is freed or the program ends.

«Heap» is the usual name for the region managed by C's dynamic allocation functions. The language standard defines the behavior of those functions and the lifetime of objects, but does not require an implementation to physically organize memory as a stack or a heap in a specific way.

Aspect Automatic lifetime (often on the stack) Dynamic memory (often on the heap)
How it is obtained On entering the block where the object is declared. Through functions such as malloc or calloc.
End of life On leaving the block, according to the language rules. On calling free with the allocation's pointer.
Usual control Managed by the flow of blocks and functions. The program must organize the release.
Frequent use Local variables of known size and lifetime. Data whose size or lifetime is determined at runtime.
Typical risk Returning or keeping the address of an object that no longer exists. Forgetting to free, freeing twice or using the object after freeing.

The table describes the usual programming model, not a promise about the exact physical location of each object. For example, compilers may optimize storage as long as observable behavior follows the language rules.

Dynamic memory with malloc and free

The malloc function, declared in <stdlib.h>, requests a number of bytes and returns a pointer to the reserved block. If it cannot satisfy the request, it returns NULL. Memory obtained with malloc is not initialized: its contents must not be read until valid values have been written.

This example reserves space for five integers, checks the result, initializes the elements, uses them and frees the block. The size check avoids multiplications that exceed the range of size_t. 

#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    size_t count = 5;

    if (count > SIZE_MAX / sizeof(int)) {
        return 1;
    }

    int *values = malloc(count * sizeof *values);
    if (values == NULL) {
        return 1;
    }

    for (size_t i = 0; i < count; i++) {
        values[i] = (int)(i * 10);
    }

    for (size_t i = 0; i < count; i++) {
        printf("%d\n", values[i]);
    }

    free(values);
    return 0;
}

The expression sizeof *values obtains the size of the type pointed to by values. That way, if the pointer's type changes, the type does not need to be repeated in the calculation. The conversion of i to int is explicit; in this example the range is small and known.

free must receive a pointer returned by a dynamic allocation function that has not yet been freed. Freeing an automatic object, passing an incorrect address or freeing the same block again has undefined behavior. After freeing a block, the pointers that pointed to it become dangling: they must no longer be used to access the object.

Assigning NULL to a pointer variable after free can help prevent that variable from keeping an obsolete value: 

free(values);
values = NULL;

This only clears that variable. If copies of the pointer exist, they also become dangling and must stop being used. Zeroing a pointer does not free memory by itself; the release happens in the valid call to free.

To reserve memory initialized to zero there is calloc, which receives a count of elements and the size of each. To change the size of a block there is realloc, but it must be used carefully: if it fails, it returns NULL and the original block stays reserved. Saving its result first in a temporary pointer avoids losing the only reference to the original block. 

int *temp = realloc(values, new_count * sizeof *values);

if (temp != NULL) {
    values = temp;
} else {
    /* values still points to the original block */
}

The realloc example is a partial pattern: before computing the new size the multiplication should also be checked for overflow, and the program must define how to handle failure. Do not use the original block after a resize operation has succeeded if its previous address is no longer valid.

Character strings

C does not have a built-in string type equivalent to those of some high-level languages. A conventional string is an array of char that ends with the null character '\0'. That terminator marks where the text ends; it must not be confused with the character '0'.

To store the text sol four positions are needed: three letters and the terminator. The following declaration leaves room for that terminator: 

char word[] = "sol";

When copying or building strings, enough space must be reserved for all characters and the terminator. Standard library functions may require the programmer to guarantee that space; not all of them receive the destination's size or can check its bounds automatically.

A string that does not contain a terminator within its array can make a function keep reading beyond the object. An array that is too small can cause writes out of bounds. Both errors can lead to undefined behavior, crashes or vulnerabilities.

For text input, one option is to read a line with fgets, providing the buffer size: 

#include <stdio.h>

int main(void) {
    char name[32];

    if (fgets(name, sizeof name, stdin) != NULL) {
        printf("Text received: %s", name);
    }

    return 0;
}

fgets reads at most one character less than the given capacity and terminates the result with '\0' if the read succeeds. If the line is longer, text may remain pending in the stream; a program that needs to process long inputs must define how to detect and handle that situation.

Best practices

  • Initialize objects before reading them. Do not use the contents of an automatic variable without assigning it a valid value.
  • Check allocation results. Verify whether malloc, calloc or realloc returned NULL.
  • Compute sizes carefully. Check that the count multiplied by the size of each element does not exceed the range of size_t.
  • Document who is responsible for freeing. Every dynamic block needs a clear owner and a release path, even when an error occurs.
  • Respect array and string bounds. Use the destination's real capacity and leave room for the null terminator of strings.
  • Do not keep addresses of objects that cease to exist. An address does not extend the lifetime of a local variable.
  • Avoid freeing twice or using after free. After freeing an object, treat all copies of its pointer as invalid.
  • Enable compiler warnings and analysis tools. They help detect some errors, but do not replace design review nor guarantee the program is correct.
  • Use automatic allocation when appropriate. If the size and lifetime are known, a local array can be simpler than dynamic memory, taking into account the platform's resource limits.

Design the error flow before adding dynamic allocations. A simple release structure prevents an early exit from leaving resources unfreed.

Common mistakes

Mistake What may happen How to prevent it
Dereferencing a null or indeterminate pointer. Invalid access and undefined behavior. Initialize pointers and check results before using them.
Writing past the end of an array. Other data is corrupted or the program crashes; it can also open a vulnerability. Control the index and always compare against the real element count.
Forgetting to free dynamic memory. The program retains memory it no longer needs while the block stays reserved. Define ownership of the block and make sure to free it on all appropriate paths.
Using a pointer after free. The pointer becomes dangling and can no longer be used to access the object. Invalidate all aliases and assign NULL to the variable that was freed.
Freeing the same block twice. Undefined behavior. Centralize freeing and change the owner's state after freeing.
Reading memory returned by malloc before initializing it. An indeterminate value is used. Write valid values before reading the block or use an initializing allocation function when appropriate.
Computing the allocation size with an unchecked multiplication. The size can overflow and reserve less space than needed. Check the multiplication limit before calling the allocation function.
Returning the address of an automatic local variable. The variable ceases to exist when leaving the function and the pointer becomes invalid. Return a value by copy, use an object with suitable lifetime or clearly define a dynamic ownership strategy.
