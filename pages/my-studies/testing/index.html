Testing automatizado

Una prueba automatizada es un programa que comprueba otro programa y decide si el resultado es correcto sin intervención humana. Bien elegidas, las pruebas convierten el miedo a tocar código en la confianza de poder cambiarlo: fallan rápido, señalan el punto exacto y se ejecutan igual en el portátil de cada persona y en el servidor de integración continua.

En 5 puntos

  • Una prueba es código que verifica código: prepara una situación, ejecuta una acción y compara el resultado con lo esperado.
  • Las unitarias comprueban piezas aisladas, las de integración verifican que varias piezas cooperan y las de extremo a extremo recorren un flujo completo desde la interfaz.
  • La pirámide sana tiene muchas unitarias, menos de integración y unas pocas de extremo a extremo: las primeras son rápidas y precisas, las últimas son lentas y frágiles.
  • Una buena prueba nombra el comportamiento, tiene una sola razón para fallar y no depende del orden de ejecución, del reloj ni de datos externos.
  • La cobertura mira qué código se ejecutó, no qué se comprobó: sirve para encontrar huecos, no como objetivo por sí misma.

Qué es una prueba automatizada

Un caso de prueba describe una situación de partida, una acción y el resultado esperado. Automatizarlo significa escribir esa descripción como código para que la máquina la repita. La pieza que se comprueba se suele llamar sujeto bajo prueba, y la comprobación final es una aserción: una afirmación que debe cumplirse o la prueba falla. 

import test from 'node:test';
import assert from 'node:assert/strict';
import { totalCarrito } from '../carrito.js';

test('suma los precios y aplica el descuento', () => {
  const carrito = [
    { precio: 10, cantidad: 2 },
    { precio: 5, cantidad: 1 }
  ];

  const total = totalCarrito(carrito, 0.1);

  assert.equal(total, 22.5);
});

Aquí la situación es el carrito, la acción es llamar a totalCarrito y la aserción compara el resultado con 22.5. Si alguien cambia el cálculo y el total deja de ser ese, la prueba falla en el punto exacto del cambio.

La prueba no demuestra que el código sea correcto: demuestra que, para los casos que describe, el comportamiento sigue siendo el acordado. Su valor está en repetirse de forma barata y rápida cada vez que el código cambia.

Por qué automatizar

Comprobar a mano que una página sigue funcionando después de cada cambio es posible al principio e imposible después de unos meses. Las pruebas automatizadas aportan tres cosas que la revisión manual no puede garantizar:

  • Detección de regresiones: un cambio aparentemente inocuo que rompe una función antigua se descubre antes de publicar.
  • Confianza para refactorizar: puedes reestructurar el código sabiendo que el comportamiento observable sigue sujeto a comprobación.
  • Documentación ejecutable: los nombres de las pruebas describen casos de uso concretos y se actualizan con el código.

También tienen un coste: hay que escribirlas, leerlas, mantenerlas y aceptar que a veces fallan por un cambio legítimo. Por eso se empieza por los comportamientos importantes, no por cada línea del programa.

La pirámide de pruebas

No todas las pruebas cuestan lo mismo. La forma habitual de representarlo es una pirámide: una base amplia de pruebas rápidas y una cúspide estrecha de pruebas lentas.

Tipo Qué comprueba Velocidad y estabilidad
Unitaria Una función o clase aislada. Muy rápida y determinista.
De integración Que varios módulos cooperan: código, base de datos, cola o API. Rápida o media; algo más frágil.
Extremo a extremo Un flujo de usuario completo a través de la interfaz. Lenta y más propensa a fallos intermitentes.

Si la pirámide se invierte y casi todo se prueba desde el navegador, cada ejecución tarda minutos, los fallos son difíciles de localizar y el equipo deja de confiar en el resultado. La regla práctica es comprobar cada comportamiento en el nivel más bajo que pueda verificarlo de verdad.

Pruebas unitarias

Una prueba unitaria ejerce una pieza pequeña sin arrancar la aplicación completa. Para que sea estable, la pieza no debe depender de la hora actual, de la red, de un archivo ni del orden en que se ejecutaron las demás pruebas. Si lo hace, se sustituye esa dependencia por un doble. 

test('rechaza una cantidad negativa', () => {
  const carrito = [{ precio: 10, cantidad: -1 }];

  assert.throws(() => totalCarrito(carrito), /cantidad/);
});

El patrón organizar, actuar, comprobar (AAA, por sus siglas en inglés) ayuda a mantener la estructura: primero se preparan los datos, después se llama a la función y por último se hacen las aserciones. Conviene dejar una línea en blanco entre las tres partes para que el caso se lea de un vistazo.

No hace falta una prueba para cada función. Una función privada que solo se usa desde otra queda cubierta al probar el comportamiento público; probarla por separado acopla la prueba a detalles de implementación que cambiarán.

Pruebas de integración

Las pruebas de integración responden a otra pregunta: «¿estas piezas funcionan juntas?». Comprueban, por ejemplo, que una ruta llama al servicio correcto, que una consulta SQL devuelve lo esperado o que un mensaje publicado llega a su consumidor.

Los límites del sistema son los importantes aquí. Se puede usar una base de datos real en un entorno de pruebas, un servidor HTTP local o un repositorio en memoria con el mismo contrato. Lo que se evita es una configuración compartida entre pruebas: cada una debe crear sus datos y limpiarlos al terminar. 

test('guarda el usuario y devuelve su identificador', async () => {
  const guardados = [];
  const repositorio = {
    guardar: async (usuario) => {
      guardados.push(usuario);
      return 'u-1';
    }
  };

  const id = await registrarUsuario('ana@ejemplo.com', repositorio);

  assert.equal(id, 'u-1');
  assert.equal(guardados[0].email, 'ana@ejemplo.com');
});

Esta prueba no necesita base de datos porque inyecta un repositorio falso con el mismo contrato. Eso la hace rápida; una prueba con la base de datos real comprobaría además la consulta y las restricciones.

Pruebas extremo a extremo

Una prueba extremo a extremo, o E2E, conduce la aplicación real desde la interfaz: abre una página, rellena un formulario y comprueba el resultado visible. Es la que más se parece a lo que hace una persona y la que mejor detecta problemas de integración entre frontend, backend y despliegue. 

test('el usuario puede iniciar sesión', async ({ page }) => {
  await page.goto('/acceso');
  await page.getByLabel('Correo').fill('usuario@ejemplo.com');
  await page.getByRole('button', { name: 'Entrar' }).click();

  await expect(page.getByRole('heading', { name: 'Panel' })).toBeVisible();
});

Las herramientas de navegador, como Playwright o Cypress, permiten este estilo de prueba. Algunas decisiones marcan la diferencia:

  • Buscar elementos por rol, etiqueta o texto visible, no por clases CSS que cambian con el diseño.
  • Esperar a una condición observable en lugar de usar pausas fijas de tiempo.
  • Preparar los datos mediante la API o la base de datos antes de abrir la página, no haciendo clics preparatorios en cada prueba.
  • Guardar capturas y trazas cuando falle, para entender el estado del navegador sin reproducirlo a mano.

Un flujo E2E no sustituye a las pruebas unitarias: si falla, suele decir «algo ha roto», pero no qué función concreta. Por eso se reservan para los recorridos críticos del producto: registro, pago, publicación.

Cómo escribir una buena prueba

Una prueba útil se lee como un ejemplo. Si su nombre no permite saber qué comportamiento describe, alguien tendrá que leer el código para entenderla. Unas reglas sencillas mejoran mucho el conjunto:

  • Nombra el comportamiento: «aplica el descuento al total» dice más que «prueba 2».
  • Una razón para fallar: si una prueba comprueba tres cosas distintas, un fallo no indica cuál se rompió.
  • Aserciones sobre resultados, no sobre cómo se calculan: cambiar el algoritmo no debe romper la prueba si el resultado sigue siendo correcto.
  • Independencia: cualquier prueba debe poder ejecutarse sola y en cualquier orden.
  • Datos mínimos y explícitos: solo los campos que influyen en el resultado; el resto se construye con fábricas o generadores.
  • Sin fechas ni números aleatorios sin control: se fija la hora o se inyecta un generador determinista.

Cuando una prueba falla en integración continua y no en local, lo más probable es que dependa de algo del entorno: zona horaria, idioma, orden de archivos o estado persistente. Busca esa dependencia antes de volver a ejecutarla esperando que pase.

Dobles de prueba

Un doble sustituye una dependencia real durante la prueba. Los nombres varían según el marco de trabajo, pero las ideas son estas:

  • Falso (fake): una implementación sencilla del mismo contrato, como un repositorio en memoria.
  • Escudo (stub): devuelve valores preparados y no comprueba cómo se usa.
  • Espía (spy): registra las llamadas para revisarlas después.
  • Simulacro (mock): además exige que se cumplan ciertas llamadas, y suele fallar si no es así.

Se usa el doble más sencillo que sirva. Si solo necesitas que una función devuelva un valor, un escudo basta. Si necesitas comprobar que se envió un correo, un espía o un simulacro tiene sentido. Sustituir demasiadas piezas por simulacros produce pruebas que pasan aunque la aplicación esté rota: comprueban llamadas, no comportamiento.

No conviene simular lo que no es tuyo, como la biblioteca estándar o el marco de trabajo. Esas librerías ya tienen sus propias pruebas; simularlas solo añade fragilidad.

Cobertura y calidad

La cobertura mide qué parte del código se ejecutó durante las pruebas: líneas, ramas, funciones o sentencias. Es una señal útil para detectar zonas sin probar, no una medida de calidad. 

node --test --experimental-test-coverage
npm test -- --coverage

Un 100 % de cobertura de líneas puede convivir con pruebas que no comprueban nada: basta con llamar a cada función sin aserciones. Al revés, una zona sin cobertura no siempre es un problema, por ejemplo un código de defensa imposible de alcanzar.

Para valorar de verdad una batería de pruebas se puede recurrir a pruebas de mutación: la herramienta cambia una condición o un operador en el código y comprueba si alguna prueba falla. Si ninguna falla, ese comportamiento no estaba protegido. Es más lento que la cobertura, pero responde a la pregunta correcta.

Pruebas de interfaz

En una interfaz web se puede probar una pieza sin navegador, montando el DOM con una biblioteca de pruebas y comprobando qué ve y qué puede hacer la persona usuaria: un mensaje de error visible, un botón deshabilitado, el foco después de cerrar un diálogo.

Estas pruebas se parecen a las unitarias en velocidad y a las E2E en criterio: interactúan con etiquetas y roles, no con detalles internos del componente. Comprueban, por ejemplo, que al escribir en un campo de búsqueda aparece el resultado filtrado y que el contador se actualiza, sin importar qué función interna lo calcule.

La accesibilidad y las pruebas se llevan bien: si una prueba encuentra un botón por su nombre accesible, ese mismo nombre es el que usa un lector de pantalla. Un selector que solo funciona por una clase CSS no aporta esa señal.

Pruebas en integración continua

Unas pruebas que nadie ejecuta se quedan obsoletas. La integración continua las lanza en cada cambio y convierte el resultado en una condición para fusionar: si fallan, el cambio no entra. 

name: tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test

La orden importa: las comprobaciones rápidas van primero para dar feedback pronto, y el build o las pruebas de navegador se ejecutan después. Conviene fijar la versión del entorno de ejecución y usar instalación estricta de dependencias para que un fallo no dependa de una actualización accidental.

Las pruebas intermitentes merecen atención inmediata. Una prueba que falla una de cada veinte ejecuciones acostumbra al equipo a ignorar el resultado y destruye el valor de toda la batería. Se aísla, se arregla o se elimina; no se deja «ya se arreglará».

Errores comunes

  • Probar detalles de implementación, como el nombre de una variable interna o una llamada concreta, en lugar del resultado observable.
  • Escribir pruebas que comparten estado: una modifica una variable global y la siguiente falla solo al ejecutarse después.
  • Usar pausas fijas de tiempo en pruebas de navegador en lugar de esperar a una condición.
  • Perseguir un porcentaje de cobertura con aserciones vacías.
  • Simular tantas dependencias que la prueba deja de parecerse a la aplicación real.
  • Repetir el mismo recorrido largo en decenas de pruebas E2E cuando unas pocas unitarias lo cubren mejor.
  • Ignorar pruebas intermitentes hasta que nadie confía en el resultado de la integración continua.
  • No actualizar la prueba cuando el comportamiento esperado cambia de verdad: entonces la prueba es la que está equivocada.

Si una prueba falla tras un cambio intencionado, no la ajustes hasta que pase sin más. Revisa primero si el nuevo comportamiento es el que quieres y escribe la aserción acorde a esa decisión.

Referencia rápida

Concepto Para qué sirve
Aserción Comprobar que el resultado cumple lo esperado.
Prueba unitaria Verificar una pieza aislada y determinista.
Prueba de integración Verificar que varias piezas cooperan.
Prueba E2E Recorrer un flujo completo desde la interfaz.
Doble Sustituir una dependencia para controlar la prueba.
AAA Organizar, actuar y comprobar en ese orden.
Cobertura Señalar código no ejecutado por las pruebas.
Regresión Fallo de una función que antes funcionaba.
