GitHub Actions y CI/CD

Integración continua es ejecutar las mismas comprobaciones en cada cambio; entrega continua es llevar el resultado verificado a un entorno sin pasos manuales. GitHub Actions describe esos procesos en archivos YAML dentro del repositorio, así que la automatización se revisa, se versiona y se mejora igual que el código.

En 5 puntos

  • CI verifica cada cambio de forma automática; CD publica un artefacto ya verificado.
  • Un workflow de GitHub Actions se define en .github/workflows/ y se compone de eventos, permisos, trabajos y pasos.
  • Las pruebas y el build deben ejecutarse con instalación estricta de dependencias y versiones fijas del entorno.
  • Los artefactos conectan los trabajos: se construyen una vez y se promocionan entre entornos sin recompilar.
  • Secretos, permisos mínimos y protección de ramas convierten la automatización en una red de seguridad, no en un botón que cualquiera puede pulsar.

Qué significan CI y CD

Integración continua (CI) es la práctica de integrar los cambios en una rama compartida y verificarlos automáticamente: formateo, análisis estático, pruebas y build. El objetivo no es acumular procesos, sino reducir el tiempo entre escribir un cambio y saber si funciona.

Entrega continua (CD) lleva ese artefacto verificado a un entorno de prueba o de preparación. Cuando la publicación en producción también es automática se habla de implementación continua. En ambos casos la idea es la misma: el mismo paquete que pasó las comprobaciones es el que se promueve.

CI/CD no sustituye a las pruebas: las ejecuta. Si una batería de pruebas es incompleta o intermitente, la canalización solo automatiza la incertidumbre.

Anatomía de un workflow

Un workflow es un archivo YAML en .github/workflows/. Define cuándo se dispara, qué permisos tiene y qué trabajos ejecuta. Un trabajo (job) corre en una máquina propia, llamada ejecutor (runner), y contiene pasos secuenciales. Los pasos pueden ejecutar comandos con run o reutilizar una acción con uses. 

name: tests
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test

Los eventos más habituales son push, pull_request y workflow_dispatch, que permite lanzarlo a mano desde la pestaña Actions. Cada evento puede filtrarse por rama, ruta o etiquetas para no gastar ejecuciones en cambios que no afectan.

Por defecto los trabajos de un workflow son independientes y se ejecutan en paralelo. Si uno necesita el resultado de otro se declara con needs. Los ejecutores pueden ser alojados por GitHub o propios; estos últimos permiten acceder a recursos internos, pero hay que mantenerlos.

GitHub Actions en la práctica

El despliegue de este portafolio es un ejemplo real: .github/workflows/static.yml publica el sitio en GitHub Pages cuando hay un push a main. El archivo declara permisos concretos, evita despliegues simultáneos y construye un artefacto filtrado. 

on:
  push:
    branches: ["main"]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: "pages"
  cancel-in-progress: false

La sección permissions aplica el principio de menor privilegio: el token solo puede leer el repositorio, escribir en Pages y pedir un token de identidad. Sin esa declaración, el token tendría más permisos de los necesarios.

concurrency agrupa las ejecuciones bajo el nombre pages. Con cancel-in-progress: false las ejecuciones nuevas esperan a que termine la actual, en lugar de interrumpir un despliegue a medias. Para trabajos de pruebas suele preferirse true, porque cancelar una ejecución obsoleta ahorra tiempo.

Otro detalle del flujo real es la preparación del artefacto: se copia el repositorio con rsync y se excluyen documentación, plantillas y material interno. Lo que se sube a Pages es exactamente el sitio público, no el repositorio completo.

En este repositorio las acciones se fijan por SHA en lugar de por etiqueta (actions/checkout@11d5960…). Una etiqueta como v4 puede reasignarse; fijar el hash evita que una actualización externa cambie el comportamiento del despliegue sin revisión.

Pruebas y calidad en CI

Una canalización útil falla pronto y con un mensaje claro. Las comprobaciones rápidas van primero: formateo, análisis estático y pruebas unitarias. Después llegan las pruebas de integración, el build y, solo para los recorridos críticos, las pruebas de navegador. 

jobs:
  verificar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run format:check
      - run: npm test
      - run: npm run build

npm ci instala exactamente lo que describe el archivo de bloqueo y falla si cambió. Usar npm install en automatización puede resolver versiones distintas en cada ejecución y hacer que un fallo aparezca sin que el código cambiara.

Las pruebas deben ser deterministas en el ejecutor: fijar zona horaria e idioma, evitar dependencias de red y preparar sus propios datos. Una prueba intermitente que se vuelve a lanzar «a ver si pasa» destruye la confianza en toda la canalización.

Las comprobaciones de CI son obligatorias solo si la rama está protegida y exige que pasen antes de fusionar. Sin esa regla, un fallo en Actions es solo una notificación que se puede ignorar.

Caché y artefactos

La caché guarda entradas caras de recrear, como las dependencias descargadas. El ejemplo con actions/setup-node y cache: npm ya aprovecha el archivo de bloqueo como clave: si no cambia, se reutiliza la caché.

Un artefacto es el resultado de un trabajo: el directorio compilado, un informe de cobertura o el sitio preparado para publicar. Se sube con una acción y otros trabajos pueden descargarlo. Así el build se hace una sola vez y el despliegue no vuelve a compilar. 

- name: Upload artifact
  uses: actions/upload-artifact@v4
  with:
    name: sitio
    path: _site/

La caché es una optimización: si falta, el trabajo sigue funcionando. El artefacto es parte del resultado: si falta, la cadena se rompe. Conviene darle un nombre estable y comprobar que contiene lo esperado antes de promocionarlo.

Secretos y permisos

Los valores sensibles se guardan en los secretos del repositorio o de la organización y se inyectan como variables de entorno. Nunca se escriben en el YAML ni en el código. 

- name: Publicar
  run: npm run deploy
  env:
    DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

GitHub oculta el valor en los registros, pero no evita que un paso malintencionado lo lea. Por eso importa revisar las acciones de terceros que se ejecutan junto a los secretos y fijarlas por hash, como se hace en el workflow de este sitio.

  • Usar permisos mínimos: contents: read para leer, solo write donde haga falta.
  • No exponer secretos en trabajos que ejecutan código aportado por externos, como pull requests de bifurcaciones.
  • Rotar tokens y revisar cuáles siguen en uso.
  • Distinguir entre secretos de repositorio, de entorno y de organización según quién debe poder usarlos.

Entornos y protección de ramas

Un entorno agrupa secretos y reglas de aprobación para un destino concreto, por ejemplo produccion. Se puede exigir que una persona apruebe el trabajo antes de que acceda a ese entorno, útil cuando publicar tiene un coste o un riesgo.

La protección de ramas complementa esto desde el lado de Git: exige pull request, revisiones y que las comprobaciones obligatorias estén en verde. Con ambas piezas, nadie fusiona un cambio sin verificar y nadie publica sin querer en producción. 

jobs:
  publicar:
    needs: verificar
    if: github.ref == 'refs/heads/main'
    environment:
      name: produccion
      url: ${{ steps.deploy.outputs.url }}
    runs-on: ubuntu-latest

needs encadena trabajos, if limita la publicación a la rama principal y environment aplica las reglas del destino. La URL del entorno aparece entonces en la interfaz de GitHub Actions y facilita encontrar el resultado.

Matrices y workflows reutilizables

Una matriz genera varios trabajos a partir de una lista de valores, por ejemplo versiones de Node o sistemas operativos. Es una forma compacta de comprobar compatibilidad sin duplicar YAML. 

strategy:
  matrix:
    node: [18, 20, 22]
    os: [ubuntu-latest, windows-latest]
runs-on: ${{ matrix.os }}
steps:
  - uses: actions/setup-node@v4
    with:
      node-version: ${{ matrix.node }}

Hay que usar las matrices con criterio: cada combinación consume minutos de ejecución. Si todas las versiones comparten comportamiento, basta con probar los extremos.

Cuando varios repositorios repiten el mismo proceso, un workflow reutilizable permite centralizarlo. Se define con on: workflow_call y se invoca desde otro workflow con uses. 

jobs:
  desplegar:
    uses: mi-organizacion/repo-compartido/.github/workflows/deploy.yml@main
    secrets: inherit

Un workflow reutilizable referenciado por @main cambia cuando cambia esa rama. Si muchas canalizaciones dependen de él, fija una etiqueta de versión o un SHA, y documenta quién puede modificarlo.

Buenas prácticas

  • Fijar versiones del entorno de ejecución y de las acciones; no depender de latest.
  • Instalar dependencias de forma estricta a partir del archivo de bloqueo.
  • Construir una sola vez y promocionar el mismo artefacto entre entornos.
  • Poner primero las comprobaciones rápidas para dar feedback pronto.
  • Declarar permisos mínimos y guardar los secretos en el lugar correcto.
  • Usar protección de ramas para que las comprobaciones sean obligatorias.
  • Cancelar ejecuciones obsoletas en pruebas, pero no interrumpir despliegues en curso.
  • Revisar los registros de ejecución cuando falle algo: suelen explicar el entorno, no solo el error.

Errores comunes

  • Usar npm install en lugar de npm ci y perder reproducibilidad.
  • Dejar los permisos por defecto cuando solo se necesita lectura.
  • Escribir tokens en el YAML o en un paso run en lugar de usar secretos.
  • Recompilar en cada entorno y publicar algo distinto de lo que pasó las pruebas.
  • Referenciar acciones por etiquetas movibles sin revisar qué contienen.
  • Lanzar pruebas de navegador en cada pull request aunque sean lentas y redundantes.
  • Ignorar ejecuciones fallidas o volver a lanzarlas sin investigar la causa.
  • Proteger la rama principal pero permitir que cualquier persona modifique el workflow que la protege.

Si una comprobación pasa en local y falla en Actions, compara primero versión del entorno, variables, zona horaria y archivos generados. Casi siempre la diferencia está en el entorno, no en el código.

Referencia rápida

Concepto Para qué sirve
Workflow Archivo YAML que describe una automatización.
Evento Cuándo se dispara el workflow.
Job Conjunto de pasos en un ejecutor.
Step Un comando o una acción dentro de un job.
Artefacto Resultado de un job que otro job puede usar.
Secreto Valor sensible inyectado como variable de entorno.
Entorno Destino con secretos y reglas de aprobación propias.
Matriz Generar trabajos para varias combinaciones de valores.
