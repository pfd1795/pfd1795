Web (HTML, CSS and JavaScript)

HTTP and the web browser

Between typing a URL and seeing the page on screen, everything happens: DNS, TCP, TLS, an HTTP request, parallel downloads, DOM construction, style resolution... If you understand that cycle and the tools that inspect it, the browser stops being a black box.

In 5 points

  • A typical page triggers dozens of requests: HTML, CSS, images, scripts, fonts and API calls.
  • A request is method + path + headers; the response is status code + headers + body.
  • The browser builds the DOM (from HTML) and the CSSOM (from CSS), and only then paints.
  • Cache, compression and CDN avoid repeating work: Cache-Control is where that is decided.
  • CORS decides whether a page may read responses from another origin; it is negotiated with headers, not with «blocks» the server applies on a whim.

The full page cycle

Steps from pressing Enter until the page works:

  1. Name resolution: the browser asks DNS for the IP of example.com (OS, router and DNS server cache).
  2. Connection: opens TCP to port 80/443; if HTTPS, TLS handshake first (see TLS).
  3. Request: sends GET / HTTP/1.1 with headers (Host, Accept, cookies…).
  4. Response: the server replies with code + headers + HTML.
  5. Parsing and derived loads: while reading the HTML, it discovers CSS, scripts, images and fonts, and requests each one (see the blocking section).
  6. Render: builds the render tree and paints.
  7. Execution: runs the scripts; they may issue more fetch calls and repeat the cycle.

From HTML to pixels: how the browser renders

The rendering engine performs four steps, in this order, for every visual refresh:

  1. HTML parsing → DOM: parses tags and builds the node tree.
  2. CSS parsing → CSSOM: turns rules into a style tree.
  3. Render tree: combines both (layout: size and position of each box) and discards the invisible (display: none, hidden elements).
  4. Painting and compositing: draws layers and composites them with the GPU.

Changing properties that only affect painting (color, background) is cheap; changing size or position forces a layout recalculation (reflow) and is more expensive. Animating transform and opacity is recommended.

Resources, order and blocking

Not all resources load the same way while the parser is reading the HTML:

Resource Default behavior How to control it
CSS (<link>)Blocks rendering until downloaded and parsedmedia for specific profiles; small critical sheets
Classic script (<script src>)Stops parsing, downloads, runs, then continuesdefer: after parsing, in order. async: as soon as it arrives, no order
type="module"Is defer by defaultNeeds an HTTP server (file:// blocks it via CORS)
ImagesDo not block parsing; space is reserved only when measuredloading="lazy", width/height to avoid jumps
Remote fontsCan leave text invisible while loadingfont-display: swap, preload with preload
 
<!-- runs in order, after parsing the document -->
  <script defer src="app-a.js"></script>
  <script defer src="app-b.js"></script>

  <!-- independent: does not wait for parser or other scripts -->
  <script async src="analytics.js"></script>

async and defer only work with external scripts. Inline ones run where they belong and block.

Cache and headers

The browser keeps copies of resources. The policy is dictated by response headers: 

Cache-Control: max-age=31536000, immutable   # good for CSS/JS with hash in the name
  Cache-Control: no-cache                       # always revalidate before use
  Cache-Control: no-store                       # store nothing (sensitive data)
  ETag: "v18b2"                                 # identifier version » If-None-Match
  Last-Modified: Thu, 05 Nov 2026 10:00:00 GMT  # » If-Modified-Since
  • 200 response: the resource comes in full.
  • 304 Not Modified: unchanged; the local copy is used (with ETag or Last-Modified in the validation request).
  • Typical pattern: statics are served with a «hashed» name (bundle.a8f3e2.css) and cached for a year safely; HTML is not cached, so it always announces the latest version.

Quick check:

curl -sI https://pfd1795.github.io/ | grep -iE 'cache-control|etag'
  curl -sI -H 'If-Modified-Since: Thu, 05 Nov 2026 10:00:00 GMT' \
    https://pfd1795.github.io/ | head -3

CORS: reading responses from another origin

An origin is the combination of scheme + domain + port. By default, the browser lets cross-origin requests be sent (with limitations), but does not give your JavaScript access to the response if the server does not explicitly authorize it. That is CORS: Cross-Origin Resource Sharing.

Typical scenario — your front at app.example — your API at api.example:

# simple request (GET, form POSTs): the browser sends it as is
  GET https://api.example/data  Origin: https://app.example
  # response: the server MUST authorize the origin
  Access-Control-Allow-Origin: https://app.example
# non-simple request (PUT, custom headers, JSON): first a preflight
  OPTIONS /data  Origin: https://app.example
                  Access-Control-Request-Method: PUT
                  Access-Control-Request-Headers: authorization
  # preflight response
  Access-Control-Allow-Origin: https://app.example
  Access-Control-Allow-Methods: PUT, POST
  Access-Control-Allow-Headers: authorization
  • * (any origin) does not work together with credentials (cookies): the specific origin must be listed.
  • CORS is configured on the server side: from the front there is nothing to «fix», except asking the API to enable your origin.
  • Typical errors: «blocked by CORS policy», preflight 404 (the server does not handle OPTIONS), missing Allow-Headers.

CORS protects users, not the server: it prevents JavaScript from a malicious site from reading data from another site where the victim is authenticated. Known hierarchy it coexists with: SameSite cookies (Security · Session cookies) and CSP protections.

All client-side storage is readable by JavaScript in your origin: sensitive data does not go there (see Security · Session cookies). This portfolio uses localStorage for theme, language and game records. 

localStorage.setItem('theme', 'dark');
  localStorage.getItem('theme');     // 'dark'
  localStorage.removeItem('theme');  // remove

HTTP/2 and HTTP/3

  • HTTP/2 (2015, over TLS): multiplexes several requests over one connection, compresses headers and lets the server «push» resources. Alt-Svc, h2.
  • HTTP/3 (2022, QUIC over UDP): like HTTP/2 but without TCP head-of-line blocking, faster handshake incorporating TLS 1.3. Improves perceived speed on mobile.
  • CDNs and modern hostings serve both by default; from the browser you only notice a faster connection.
# check the version used (transparent)
  curl -sI -o /dev/null -w '%{http_version}\n' https://pfd1795.github.io/

DevTools: the Network tab

Useful habits when debugging network performance and errors (F12 → Network):

  • Disable cache with DevTools open, to always see server responses.
  • Sort by size/latency; look at the time column and the waterfall.
  • Size column: (disk cache) means it was served from local memory.
  • Filter by XHR/Fetch to see only API calls, and inspect «Initiator» to see who requested the resource.
  • «Throttling» (Fast 3G) to simulate mobile; «Block request URL» to check whether your site works without third-party CDNs.
# command-line equivalents for the same
  curl -o /dev/null -s -w 'total: %{time_total}s · size: %{size_download}B\n' URL
  curl -w '@-' -o /dev/null -s URL <<'EOF'
             dns:  %{time_namelookup}s
             tcp:  %{time_connect}s
             tls:  %{time_appconnect}s
             1 byte: %{time_starttransfer}s
EOF

Best practices

  • Fewer requests weigh more than optimizing one at a time: combine, minify and use sprites for fonts and icons.
  • Cache statics aggressively (with hash in the name) and nothing dynamic.
  • Define width and height on images to avoid layout shifts (CLS).
  • defer (or modules) for your scripts unless they are truly needed instantly.
  • Enable compression (gzip/brotli) on your server or ask the CDN to apply it.
  • Learn to diagnose first with Network and curl: less guessing, more measuring.
