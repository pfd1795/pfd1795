Frameworks

Front-end frameworks

A front-end framework offers conventions and tools for building web interfaces from reusable pieces. React, Vue and Svelte let you organize the interface through components and respond to data changes, but they differ in their model and in the work they do during execution or compilation. Choosing one depends on the project, the team and how much behavior the interface needs.

In 5 points

  • A front-end framework or library helps structure dynamic interfaces; it does not replace HTML, CSS or JavaScript.
  • A component encapsulates a part of the interface and can receive data to represent different cases.
  • State holds data that can change and whose update should be reflected in the interface.
  • React, Vue and Svelte share the component-based approach, but their APIs, tools and update models are different.
  • Not every page needs a framework: for mainly static content, HTML, CSS and JavaScript can be enough.

What is it?

The front-end is the part of a web application the user interacts with: content, controls, navigation and responses to actions. It is built on web technologies such as HTML, CSS and JavaScript.

A front-end framework organizes how those interfaces are built and updated. It usually offers a way to divide the screen into components, relate data to what is shown and manage changes. Some projects use «framework» as a general term; others distinguish framework from library by the scope of the tools or by how much they prescribe the architecture.

React is usually described as a library for user interfaces, although it is part of a broad ecosystem of tools. Vue and Svelte are presented as frameworks for building interfaces, with their own conventions and tools. In practice, all three can be used to create component-based interfaces; their development model is not identical.

These systems do not automatically generate a complete application nor solve design, accessibility, data storage or security on their own. Those responsibilities still require explicit decisions.

Why use a framework?

When an interface contains many views, interactions and changing data, maintaining the DOM manually can become difficult. A framework establishes a consistent way of associating data with the interface and of dividing work into reusable pieces.

  • Organization: divides a large interface into components with more focused responsibilities.
  • Reuse: lets the same piece be shown with different data, for example several rows of a list.
  • Updating: helps reflect state changes in the interface without having to modify each element manually.
  • Shared conventions: makes it easier for a team to follow common patterns for building and reviewing interface features.
  • Ecosystem tools: can integrate with development, testing, routing or build tools, depending on the project's needs.

These advantages come at a cost: there is a model to learn, dependencies to maintain, tools to configure and updates to follow. The framework adds value when the project's complexity justifies that cost.

The concept of component

A component is an interface unit that can combine structure, behavior and, depending on the framework, styles or related logic. A button, a product card or a navigation bar can be components. Granularity should help understand and maintain the project; splitting everything into tiny pieces does not always improve the design.

Many components receive properties (often called props): values provided by whoever uses them to determine what to show. For example, a Greeting component could receive a name and present a personalized message. Properties are usually treated as inputs, not as data the component modifies directly.

State and data flow

State is information that can change while the application runs and that affects what is shown. A counter, the text of a field or the open/closed state of a menu are examples. When state changes through the mechanism provided by the framework, it can update the corresponding interface.

In a unidirectional data flow pattern, data flows down from parent components to descendant components through properties. A child component communicates an action to the parent through a function or an event; the component that owns the state decides how to update it.

This pattern makes it easier to trace where data comes from and who can modify it. It does not mean every application must concentrate state in a single place. Keeping each datum close to the components that need it usually reduces complexity, while shared state can be lifted or managed with an appropriate tool.

  • Properties: inputs the component receives from whoever invokes it.
  • State: data that changes and whose update may affect the interface.
  • Event or action: interaction that expresses an intention, such as pressing a button.
  • Update: state change that may produce a new visual representation.

Avoid duplicating the same datum in several independent states when it can be derived from a single source. Copies can fall out of sync when one of them changes and the others do not.

React, Vue and Svelte

React, Vue and Svelte let you build interfaces with components, but they use different models and conventions. The following comparison is conceptual: concrete APIs can change between versions and projects can add external tools.

Aspect React Vue Svelte
Approach Interface library based on components; usually combined with ecosystem tools. Progressive framework with components and options to adopt more structure as the project needs it. Component framework that compiles components to produce code that updates the interface.
How the interface is written Frequently with JSX, a syntax combining JavaScript and a markup-like description. Frequently with component files that separate template, logic and styles. With component files combining markup, logic and styles, processed by its tools.
State Managed through mechanisms such as local state, properties and, if needed, shared solutions. Can be declared with Options API or Composition API options, depending on the chosen style. Declared with the reactivity syntax and conventions of the version and configuration used.
Interface update React computes interface changes from a new description; uses reconciliation and an element tree model. Vue tracks reactive dependencies and updates affected parts through its rendering system. The compiler analyzes components and generates update mechanisms for the detected changes.
Frequent choice May fit when the team needs its ecosystem, patterns or prior experience. May appeal when seeking gradual adoption and integrated structure. May interest teams that value its compilation model and component syntax.

There is no universally better option. Team experience, accessibility needs, required support, ecosystem, technical constraints and maintainability are more useful criteria than an isolated claim about speed or popularity.

Virtual DOM and rendering

The DOM is the representation the browser exposes for the HTML document. Changing it lets you update a page, but managing many modifications manually can be complicated.

The term Virtual DOM usually refers to an in-memory representation of the interface that certain systems compare between updates to decide which changes to apply to the real DOM. React uses a reconciliation process based on its element representation. Vue also uses a virtual DOM in its rendering system.

Svelte follows a compilation approach: it processes components during the build and generates code that updates the interface when data changes. That is why it is usually explained as a compilation-based alternative, not simply as another framework that works the same way as React or Vue.

These descriptions alone do not allow concluding which will be faster in a specific application. Performance depends on the usage pattern, code size, updates, browser, configuration and other decisions. To choose by performance, measure a representative load of the project instead of relying only on the name of a technique.

Rendering can also refer to producing HTML on the server, rendering in the browser or generating static output during the build. They are different delivery strategies, and some ecosystems support several.

A counter in React, Vue and Svelte

The following examples represent the same interaction: showing a number and increasing it when a button is pressed. They are brief examples for comparing models; they require a configured project for each tool and are not standalone HTML files.

React

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <section>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>
        Add
      </button>
    </section>
  );
}

Local state is declared with useState. When the update function is called, React receives the new state and reprocesses the component according to its rules.

Vue

<script setup>
import { ref } from 'vue';

const count = ref(0);
</script>

<template>
  <section>
    <p>Count: {{ count }}</p>
    <button @click="count++">
      Add
    </button>
  </section>
</template>

In this example with the Composition API, ref creates a reactive value. In the template, Vue updates the view when that value changes; inside the JavaScript block it is accessed through .value in contexts where the template's automatic unwrapping does not apply.

Svelte

<script>
  let count = 0;
</script>

<section>
  <p>Count: {count}</p>
  <button on:click={() => count += 1}>
    Add
  </button>
</section>

This example illustrates Svelte's classic event syntax. The concrete syntax may vary depending on the compiler version and the project's current conventions; when starting a project, follow the documentation for the installed version.

When not to use a framework

A framework is not a requirement for creating a website. Adding one can increase the size of the delivered code, configuration complexity and maintenance effort. If the site has few interactions and mainly static content, semantic HTML, CSS and simple JavaScript can be enough.

It may also not be suitable if the team has no time to learn and maintain the tool, if the project must integrate with an existing incompatible base or if the benefits do not offset the cost. The decision should consider the project's lifetime, not just the speed of writing the first screen.

An intermediate strategy is to incorporate dynamic behavior only in the parts that need it, without turning every page into a complex application. The architecture depends on the site, its requirements and the team's capabilities.

Common mistakes

Mistake Why it causes problems Better approach
Choosing by a general performance claim. The result depends on the project, its configuration and how the interface is updated. Compare a representative load and measure with appropriate tools.
Storing the same datum in several states without need. Copies can diverge and show contradictory information. Define a single source and compute derived values when possible.
Creating components that are too large or too small. At one extreme responsibilities mix; at the other, composition becomes hard to follow. Split by clear responsibilities and real reuse.
Modifying the DOM directly without considering the framework's model. Can desynchronize the interface from the state the application keeps. Use the mechanisms provided by the tool and reserve direct manipulation for cases that justify it.
Treating properties as state modifiable by the child component. It becomes unclear who is responsible for updating the data. The child communicates an action and the owner of the data decides the change.
Using a framework even though the page does not need it. Adds dependencies and concepts the project may not use. Evaluate the amount of interaction, maintenance and team capabilities.
Copying examples without checking the version. Syntax, tools and conventions can change. Check the documentation for the version the project uses.
