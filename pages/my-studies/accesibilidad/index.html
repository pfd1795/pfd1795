Web (HTML, CSS y JavaScript)

Accesibilidad web

Una página accesible puede usarla cualquier persona, tanto con ratón como con teclado, con lector de pantalla o con el contraste reducido. No es una capa que se añade al final: es el resultado de elegir bien el HTML, gestionar el foco y probar la interfaz con herramientas reales. El navegador ya expone roles, nombres y estados cuando el marcado es correcto.

En 5 puntos

  • Los cuatro principios de WCAG —perceptible, operable, comprensible y robusto— resumen lo que debe cumplir una interfaz accesible.
  • El navegador construye un árbol de accesibilidad a partir del HTML semántico: un div con un evento de clic no se anuncia como botón.
  • El orden de foco sigue el DOM; usar controles nativos y tabindex con criterio evita las trampas de teclado.
  • Un texto alternativo descriptivo, una etiqueta asociada y un ARIA usado con moderación resuelven la mayoría de los fallos habituales.
  • La auditoría automática detecta solo una parte de los problemas: hay que probar con teclado y lector de pantalla antes de dar una página por buena.

¿Qué es y para quién?

La accesibilidad web garantiza que la información y las acciones de una página estén disponibles para todas las personas. Las pautas WCAG organizan ese objetivo en cuatro principios:

  • Perceptible: el contenido debe poderse percibir, por ejemplo con texto alternativo para las imágenes o con suficiente contraste.
  • Operable: la interfaz y la navegación deben funcionar con teclado y dejar tiempo para leer y actuar.
  • Comprensible: el texto, los nombres y las instrucciones deben ser claros, y la página debe comportarse de forma predecible.
  • Robusto: el marcado debe ser válido y compatible con las tecnologías de asistencia actuales y futuras.

A quien más se menciona es a las personas que usan un lector de pantalla, pero los beneficios llegan mucho más lejos. Quien navega solo con teclado, quien tiene una lesión temporal en la muñeca, quien usa un móvil con la pantalla rota o quien lee a mucha luz depende de las mismas decisiones: buen contraste, foco visible, controles nativos y nombres claros.

La accesibilidad no es una lista de requisitos que se revisa al publicar. Cada elemento que se añade al DOM puede ayudar o estorbar, así que conviene decidirlo bien desde el principio.

El modelo de accesibilidad del navegador

El navegador no entrega el HTML tal cual a un lector de pantalla. A partir del DOM construye un árbol de accesibilidad: una representación de los elementos interactivos y del contenido, con cuatro datos importantes por nodo —su rol, su nombre, su estado y su descripción—. La tecnología de asistencia consulta ese árbol y permite, por ejemplo, pedir «siguiente botón» o anunciar si una casilla está marcada.

El HTML nativo ya aporta esos datos. Un botón se anuncia como botón, tiene nombre por su texto y expone si está desactivado. Un enlace se anuncia como enlace y permite saltar a su destino. En cambio, un contenedor con un controlador de clic no tiene rol ni respuesta al teclado: existe visualmente, pero es invisible para el árbol. 

<button type="button" aria-pressed="false">Guardar</button>

Ese botón expone el rol button, el nombre «Guardar» y el estado aria-pressed="false". Si mañana cambia a «true», el lector de pantalla puede anunciar el cambio. Las herramientas de desarrollador del navegador incluyen un panel de accesibilidad donde se inspecciona cada nodo de ese árbol; es el sitio más rápido para comprobar qué se está anunciando realmente.

Primero HTML semántico, después ARIA. ARIA solo modifica el árbol de accesibilidad: no añade comportamiento, foco ni eventos.

Semántica y HTML

La semántica es la decisión más rentable en accesibilidad. Reservar un elemento para su función real —nav para navegación, main para el contenido principal, ul para listas, table para datos tabulares— da estructura al documento sin escribir ni una línea de JavaScript. Esas regiones, llamadas puntos de referencia, permiten saltar directamente a la sección que interesa.

Los encabezados forman el esqueleto que sigue un lector de pantalla al recorrer la página. Deben anidar por nivel, no por tamaño visual:

Nivel Cuándo usarlo Error frecuente
h1Título principal de la página.Repetirlo para cada tarjeta.
h2Cada sección de primer nivel.Saltar de h1 a h3.
h3Subsección dentro de un h2.Elegirlo por su tamaño, no por jerarquía.
h4 a h6Niveles más profundos, si el contenido los necesita.Usarlos sin una estructura detrás.

La misma idea se aplica a los controles. Compara estas dos formas de ofrecer una acción: 

<div class="tarjeta" onclick="abrirDetalles()">Ver detalles</div>
<button type="button" class="tarjeta" id="ver-detalles">Ver detalles</button>

La primera solo responde al ratón: no recibe el foco, no reacciona a Enter ni a Espacio y no se anuncia como algo pulsable. La segunda obtiene todo eso gratis. El comportamiento se conecta después desde JavaScript: 

document.querySelector('#ver-detalles')
  .addEventListener('click', abrirDetalles);

También conviene distinguir enlaces y botones. Un enlace (a href) lleva a otra página o a otra parte de la misma; un botón (button) realiza una acción dentro de la página. Usar un enlace para abrir un modal rompe la expectativa de quien navega con teclado.

Foco y orden de tabulación

El foco es el elemento que recibe las pulsaciones del teclado. El orden de tabulación suele seguir el orden del DOM, por lo que reorganizar visualmente los elementos con CSS no basta: si el orden visual y el del DOM divergen, Tab saltará de un sitio a otro de forma imprevisible.

Solo los elementos interactivos reciben foco por defecto. Con tabindex="0" se incluye un elemento en ese orden; con tabindex="-1" se deja fuera del orden, pero se le puede enfocar desde JavaScript. Los valores positivos alteran el orden global y casi siempre son un error.

El indicador de foco es la señal visual de dónde está el teclado. Eliminar el contorno con outline: none sin poner otro sustituto deja a quien navega con teclado sin referencia. La pseudoclase :focus-visible permite mostrarlo solo cuando el foco llegó desde el teclado: 

boton:focus-visible {
  outline: 3px solid currentColor;
  outline-offset: 2px;
}

Cuando se abre un modal o un menú, hay que llevar el foco dentro de él y devolverlo al control que lo abrió al cerrarlo. Si el foco se queda en el fondo, el teclado seguirá recorriendo una interfaz que el usuario ya no ve.

Navegación por teclado

Probar una página sin ratón es la comprobación más sencilla y la que más fallos revela. Estas son las teclas que una interfaz-web debe respetar:

Tecla Acción esperada
Tab / Mayús + TabAvanzar o retroceder entre elementos enfocables.
EnterActivar enlaces y botones.
EspacioActivar botones y marcar casillas.
FlechasMoverse dentro de grupos, menús y controles compuestos.
Inicio / FinIr al primero o al último elemento del grupo.
EscCerrar menús, diálogos o ventanas temporales.

En un menú con varios elementos no conviene que Tab recorra cada opción: se espera que entre una vez, se navegue con las flechas y se salga con Esc. El patrón se conoce como tabindex móvil: solo la opción activa tiene tabindex="0" y las demás tienen -1. 

<button type="button" id="abrir-menu" aria-haspopup="menu" aria-expanded="true">Opciones</button>
<ul role="menu" aria-label="Opciones">
  <li role="none"><button type="button" role="menuitem" tabindex="0">Nuevo</button></li>
  <li role="none"><button type="button" role="menuitem" tabindex="-1">Guardar</button></li>
  <li role="none"><button type="button" role="menuitem" tabindex="-1">Cerrar</button></li>
</ul>

La gestión del foco se resume en mover el índice y actualizar los atributos:

const botonAbrir = document.querySelector('#abrir-menu');
const menu = document.querySelector('[role="menu"]');
const opciones = Array.from(menu.querySelectorAll('[role="menuitem"]'));
let indice = 0;

function enfocar(posicion) {
  indice = (posicion + opciones.length) % opciones.length;
  opciones.forEach((opcion, i) => {
    opcion.tabIndex = i === indice ? 0 : -1;
  });
  opciones[indice].focus();
}

menu.addEventListener('keydown', (evento) => {
  if (evento.key === 'ArrowDown') {
    evento.preventDefault();
    enfocar(indice + 1);
  } else if (evento.key === 'ArrowUp') {
    evento.preventDefault();
    enfocar(indice - 1);
  } else if (evento.key === 'Home') {
    evento.preventDefault();
    enfocar(0);
  } else if (evento.key === 'End') {
    evento.preventDefault();
    enfocar(opciones.length - 1);
  } else if (evento.key === 'Escape') {
    botonAbrir.focus();
  }
});

El preventDefault() evita que la página se desplace al usar las flechas. Esc devuelve el foco al botón que abrió el menú, que es el comportamiento esperado.

Contraste y color

El texto debe distinguirse del fondo. WCAG pide una relación de contraste de al menos 4,5 a 1 para texto normal y de 3 a 1 para texto grande y para los bordes de controles e iconos significativos. Esa relación se calcula entre los colores finales, teniendo en cuenta transparencias y estados hover.

El color tampoco puede ser el único canal de información. Un campo inválido no debe señalarse solo con un borde rojo: necesita un mensaje de texto. Un gráfico no debe distinguir sus series solo por color: conviene añadir patrones, etiquetas o una tabla. 

<p class="estado">
  <span aria-hidden="true">✕</span>
  Error: la contraseña debe tener al menos 8 caracteres.
</p>

En los temas claros y oscuros se revisan los mismos pares. Un acento que funciona sobre blanco puede perder contraste sobre una superficie oscura, y al revés. Por eso los componentes deben consumir variables semánticas —texto, superficie, borde— en lugar de colores fijos.

El modo de alto contraste del sistema puede forzar sus propios colores. Si un componente desaparece en ese modo, casi siempre es porque su información dependía de una imagen de fondo o de un color escrito a mano.

Textos alternativos

El atributo alt describe la información de una imagen que no se puede ver. Debe transmitir el propósito de la imagen en ese contexto, no repetir «imagen de» ni transcribir todos sus detalles. Si la imagen es decorativa, se deja vacío para que el lector de pantalla la ignore: 

<img src="ventas.svg"
     alt="Las ventas subieron de 100 a 140 unidades entre enero y marzo." />

<img src="adorno.svg" alt="" />

Para gráficos complejos, el texto alternativo puede ser breve y remitir a una tabla o a un párrafo cercano con los datos. Los iconos dentro de un botón nombre reciben alt="" cuando el botón ya tiene texto visible; si el icono es lo único que hay, el nombre accesible se pone con aria-label en el botón.

El atributo title no sustituye al texto alternativo: muchos lectores no lo anuncian y no aparece al navegar sin ratón.

Roles y atributos ARIA

ARIA (Accessible Rich Internet Applications) es un conjunto de atributos que completan el árbol de accesibilidad cuando el HTML nativo no basta. Su primera regla es no usar ARIA si existe un elemento nativo que haga lo mismo: un button siempre es mejor que un div role="button".

Los usos más habituales son dar un nombre (aria-label o aria-labelledby), asociar una descripción o un error (aria-describedby), anunciar estados (aria-expanded, aria-pressed, aria-invalid) y avisar de cambios en vivo (aria-live). Para un diálogo, el nombre del cuadro debe venir de un encabezado visible: 

<button type="button" aria-haspopup="dialog" aria-controls="panel">Configuración</button>

<section id="panel" role="dialog" aria-modal="true" aria-labelledby="panel-titulo">
  <h2 id="panel-titulo">Configuración</h2>
  <p>Opciones de la página.</p>
</section>

Dos atributos muy útiles son hidden e inert: el primero retira un elemento del árbol y de la vista; el segundo mantiene el contenido visible pero impide que reciba foco o interacciones. inert es la herramienta correcta para dejar el fondo inactivo mientras un modal está abierto.

ARIA no comprueba nada por sí solo. Poner role="button" a un contenedor no le da foco ni respuesta a Enter: hay que añadir esos comportamientos. Un atributo incorrecto puede hacer más daño que su ausencia, porque anuncia algo que luego no ocurre.

Formularios accesibles

Cada campo debe tener una etiqueta visible asociada por for e id. El placeholder no la sustituye: desaparece al escribir y suele tener poco contraste. La ayuda y el error se asocian con aria-describedby, y aria-invalid indica el estado inválido: 

<label for="correo">Correo electrónico</label>
<input id="correo" name="correo" type="email" autocomplete="email"
       required aria-describedby="correo-ayuda correo-error" aria-invalid="true" />
<p id="correo-ayuda">Lo usaremos solo para responderte.</p>
<p id="correo-error">Escribe una dirección con el formato nombre@dominio.com.</p>

Los grupos de opciones van dentro de fieldset con un legend que nombra el conjunto, por ejemplo «Prefiero recibir» para varias casillas. Los valores de autocomplete ayudan a quien tiene dificultades para escribir y a los gestores de contraseñas.

Cuando falla el envío, el mensaje debe estar cerca del campo y también en un resumen al principio del formulario. Ese resumen debe recibir el foco para que el cambio no pase desapercibido, y cada enlace del resumen debe llevar al campo correspondiente.

No se limpia un campo con mensaje de error hasta que se corrija: el lector de pantalla necesita que el error siga asociado mientras el valor sea inválido.

Reducir movimiento y animación

Las animaciones ayudan a entender cambios de estado, pero también pueden provocar mareo o dificultar la lectura. La consulta de medios prefers-reduced-motion permite respetar la preferencia del sistema sin pedir ningún control adicional: 

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms;
    animation-iteration-count: 1;
    transition-duration: 0.01ms;
    scroll-behavior: auto;
  }
}

Además de respetar esa preferencia, conviene evitar el movimiento automático que no se puede detener. Un carrusel necesita un botón de pausa; un degradado animado no debe repetirse rápido; ningún elemento debe parpadear más de tres veces por segundo. Las transiciones tampoco deben mover el foco ni ocultar el indicador mientras duran.

Reducir movimiento no significa eliminar toda la información: si una animación explicaba un cambio, se sustituye por texto o por un cambio de estado visible al final.

Pruebas y auditoría

Ninguna revisión sustituye a las demás. Una auditoría automática encuentra problemas concretos —imágenes sin alt, campos sin etiqueta, contraste insuficiente—, pero no sabe si un texto alternativo describe bien la imagen ni si el orden del foco tiene sentido.

  • Teclado: recorrer la página con Tab, Mayús + Tab, Enter, Espacio y Esc, comprobando que el foco siempre se ve.
  • Árbol de accesibilidad: inspeccionar los nodos en las herramientas de desarrollador y verificar roles, nombres y estados.
  • Lector de pantalla: probar con el lector del sistema —VoiceOver, NVDA u Orca— al menos una vez sobre los flujos importantes.
  • Zoom y móvil: ampliar al 200 % y comprobar que no se pierde contenido ni aparecen desplazamientos horizontales.
  • Automatización: integrar una herramienta de auditoría en el proceso de desarrollo para detectar regresiones conocidas.

El orden importa: primero lo que se puede probar en segundos —teclado y auditoría—, después la revisión con lector de pantalla de los flujos críticos. Anotar los fallos encontrados y volver a probarlos convierte la accesibilidad en una propiedad mantenible y no en una revisión puntual.

Errores comunes

Error Por qué está mal Qué hacer
Quitar el contorno de foco. Quien usa teclado pierde su única referencia visual. Usar :focus-visible con un contorno visible.
Usar div con eventos en lugar de botones. No recibe foco, no responde a Enter ni se anuncia como control. Usar button y dejar que el navegador aporte el comportamiento.
Poner alt con «imagen de…» o dejarlo vacío en imágenes útiles. Añade ruido o pierde información para quien no ve la imagen. Describir el propósito; dejarlo vacío solo en imágenes decorativas.
Confiar solo en el color. El contraste puede ser bajo y el color no se percibe igual en todos los casos. Añadir texto, iconos o patrones y verificar la relación de contraste.
Abusar de aria-* sobre elementos nativos. Puede anunciar estados falsos y romper el comportamiento esperado. Empezar por HTML semántico y usar ARIA solo cuando aporte algo nuevo.
