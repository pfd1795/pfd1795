Fundamentals of computing

Operating systems

An operating system (OS) is the program that runs whenever the computer is on. It manages the hardware, shares resources among programs and offers an interface so that applications can request what they need without touching the hardware directly. Understanding how it does this explains why a process blocks, why memory «runs out» or why a program cannot open a file.

In 5 points

  • The OS is an intermediary: apps do not access hardware; they request services from the kernel through system calls.
  • A process is a running program with its own memory space; a thread is a unit of execution inside it.
  • The CPU is shared by a scheduler (Round Robin, priorities…); a context switch saves and restores state.
  • Virtual memory gives each process the illusion of having all the RAM to itself; the OS translates addresses and pages to disk.
  • Concurrency requires synchronisation (mutex, semaphores) to avoid races and deadlocks.

What is an operating system?

The OS fulfils three main functions:

  • Hardware abstraction: offers files, processes, sockets and virtual memory instead of ports, registers and disk sectors.
  • Resource management: decides who uses the CPU, RAM, disk and network, and in what order.
  • Isolation and protection: one process cannot read another's memory or access files without permission.

The central part is the kernel, which runs in privileged mode. The rest (shell, services, applications) runs in user mode. This separation is the basis of security and stability: if an app fails, the kernel stays alive.

The OS is not only the graphical interface. On a Linux server with no graphical environment, the OS is still complete: kernel + services + shell.

Processes and threads

A process is a running program: code, data, stack, registers and a control block (PCB) with its state. Each process has its own virtual address space, so a failure in one does not corrupt the others.

A thread is a unit of execution inside a process. Several threads share the process's code and memory, but each has its own stack and registers. Creating a thread is cheaper than creating a process.

Typical states: New, Ready, Running, Blocked (waiting for I/O or a resource) and Terminated. The scheduler moves processes between Ready and Running.

CPU scheduling

With a single CPU (or a few cores) and many ready processes, the OS decides the order and execution time. Goals: fairness, response time, throughput and CPU usage.

Algorithm Idea Advantage / drawback
FIFO (FCFS)The first to arrive runs to completion.Simple; suffers the convoy effect (a long process blocks the short ones).
SJFThe shortest first.Minimises waiting time; requires knowing the duration (not always possible).
Round RobinFixed time slices (quantum) to each process.Good response time; lots of context switching if the quantum is small.
PrioritiesThe highest priority runs first.Flexible; risk of starvation of low-priority ones.
MultilevelSeveral queues with different policies.Balances interactive and batch; more complex to tune.

Interactive systems (desktop, web) seek low response latency; batch systems seek maximum throughput. Linux combines CFS (Completely Fair Scheduler) with dynamic priorities.

Virtual memory

Each process sees a large, contiguous virtual address space, even though physical RAM is small and shared. The OS translates virtual addresses to physical ones through page tables; pages that do not fit in RAM are stored on disk (swap).

  • Paging: memory is divided into pages (virtual) and frames (physical), of the same size (e.g. 4 KiB).
  • TLB: cache of translations so the page table is not queried on every access.
  • Page fault: access to a page not present in RAM; the OS loads it from disk (costly).
  • Thrashing: if pages are constantly missing, the system spends more time paging than executing.

Virtual memory also provides isolation: a process cannot access another's memory because their page tables are different. That is why a «valid» pointer in one process is useless in another.

File system

The OS organises data into files and directories, with metadata (permissions, size, dates). Internally it usually uses inodes (metadata) and data blocks; directories are special files that map names to inodes.

  • Permissions: read/write/execute for owner, group and others (Unix rwx model).
  • Journaling: log of changes before applying them, to recover after a power cut.
  • Links: hard (same inode, another name) and symbolic (a file pointing to a path).
  • Mounting: a file system is «mounted» on a directory and becomes part of the tree.

System calls and modes

A system call (syscall) is the mechanism by which a program in user mode requests a service from the kernel: opening a file, creating a process, sending data over the network. The hardware switches to privileged mode, executes the service and returns control. 

// Conceptual example in C/POSIX
int fd = open("data.txt", O_RDONLY);   // syscall
char buf[1024];
ssize_t n = read(fd, buf, sizeof(buf)); // syscall
close(fd);                              // syscall

Every syscall has a cost (mode switch and validations). That is why libraries group small reads into buffers (stdio) and servers use non-blocking or asynchronous I/O.

Concurrency and synchronisation

When several threads or processes access shared data, they can interfere (race condition). Synchronisation coordinates access:

  • Mutex: mutually exclusive lock; only one thread enters the critical section.
  • Semaphore: counter that allows up to N simultaneous threads; useful for resource pools.
  • Condition variable: waits for a condition to hold (e.g. «there is data in the queue»).
  • Deadlock: two or more processes wait for each other. Necessary conditions (Coffman): mutual exclusion, hold and wait, no preemption and circular wait.
// Producer-consumer pattern (pseudocode)
mutex.lock();
while (queue.empty()) condition.wait(mutex);
item = queue.take();
mutex.unlock();
process(item);

Best practices

  • Use processes/threads with a clear purpose; do not create threads «just in case».
  • Protect all shared data with the right synchronisation; minimise the critical section.
  • Prefer lock-free structures when possible (concurrent queues, channels).
  • Close file descriptors and free memory; avoid resource leaks.
  • Handle signals and syscall error codes; do not ignore EINTR or ENOMEM.
  • For intensive I/O, consider non-blocking or asynchronous I/O instead of one thread per connection.

Common mistakes

Mistake Why it is wrong What to do
Accessing shared data without synchronisation Race conditions: inconsistent results that are hard to reproduce. Protect with mutex/semaphore; use detection tools (ThreadSanitizer).
Locking with a mutex and then waiting for another resource Can produce a deadlock if another thread does the reverse. Fixed order of lock acquisition; or use trylock with retry.
Creating one thread per network connection Exhausts memory and CPU time on context switches. Use thread pools or asynchronous I/O (epoll/kqueue/io_uring).
Ignoring syscall return values Silent errors (full disk, permissions) that corrupt data. Always check the return and log the error (errno).
Assuming virtual memory is «free» Page faults and swap degrade performance (thrashing). Measure real usage; avoid massive random access patterns.
