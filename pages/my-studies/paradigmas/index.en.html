Programming languages

Programming paradigms

A paradigm is a way of thinking about and structuring a program: which entities exist (variables, functions, objects), how control flow is managed and how data is handled. It is not the same as a language: a language can support several paradigms. Understanding them lets you choose the right tool and read other people's code with less friction.

In 5 points

  • The imperative paradigm describes step by step how to change the program's state.
  • Object-oriented programming groups data and behaviour into objects with encapsulation, inheritance and polymorphism.
  • The functional paradigm treats functions as values, avoids mutable state and favours composition.
  • The declarative paradigm describes the desired result; the engine decides how (SQL, HTML, JSX).
  • Most modern languages are multi-paradigm; they are mixed according to the problem.

What is a paradigm?

A programming paradigm is a style of solving problems with code. It defines:

  • The available abstractions (variables, functions, classes, processes).
  • The control flow (sequence, conditionals, recursion, events).
  • State management (mutable, immutable, shared, isolated).
  • Composition (how the pieces are combined).

A language is not a paradigm. JavaScript supports imperative, OOP and functional; SQL is declarative; Haskell is purely functional. Learning paradigms makes you better in any language.

The imperative paradigm

The program is a sequence of instructions that modify state. It is the paradigm closest to the hardware and the first one usually learned. 

// Imperative: sum of the even numbers
const numbers = [1, 2, 3, 4, 5];
let sum = 0;
for (let i = 0; i < numbers.length; i++) {
  if (numbers[i] % 2 === 0) {
    sum += numbers[i];
  }
}
console.log(sum); // 6

Strengths: fine control, predictable performance, easy to follow step by step. Risks: mutable shared state, side effects and code that is hard to test as it grows.

Object-oriented programming

It organises code into objects: entities that encapsulate data (attributes) and behaviour (methods). The key principles:

  • Encapsulation: hide internal state and expose only what is needed.
  • Inheritance: create new classes from existing ones (reuse).
  • Polymorphism: treat different objects uniformly if they share an interface.
  • Abstraction: model the essentials of the domain.
class BankAccount {
  #balance = 0; // private
  deposit(amount) { this.#balance += amount; }
  withdraw(amount) {
    if (amount > this.#balance) throw new Error('Insufficient balance');
    this.#balance -= amount;
  }
  get balance() { return this.#balance; }
}

const c = new BankAccount();
c.deposit(100);
c.withdraw(30);
console.log(c.balance); // 70

Strengths: models domains with entities and rules well; eases extension. Risks: deep hierarchies, coupling through inheritance and shared mutable state. That is why composition is preferred over inheritance today.

The functional paradigm

It treats computation as the evaluation of mathematical functions. Central ideas:

  • Pure functions: same input → same output; no side effects.
  • Immutability: data is not modified; new data is created.
  • Higher-order functions: receive or return other functions.
  • Composition: combine small functions to form others.
// Functional: sum of the even numbers
const numbers = [1, 2, 3, 4, 5];
const isEven = (n) => n % 2 === 0;
const add = (a, b) => a + b;
const result = numbers.filter(isEven).reduce(add, 0);
console.log(result); // 6

Strengths: easy to test, parallelise and reason about; ideal for data transformation. Risks: performance from creating many copies; learning curve (recursion, monads).

The declarative paradigm

It describes what is wanted, not how. The engine decides the execution. Everyday examples:

  • SQL: SELECT name FROM customer WHERE active = true;
  • HTML: describes the structure, not the drawing.
  • React/JSX: describes the UI from state.
  • CSS: declares styles, the browser applies them.

Declarative code is usually shorter and more expressive, but it depends on the engine (database, browser) being well optimised.

Practical comparison

The same problem (sum of the even numbers in a list) in each style:

Paradigm Approach
ImperativeLoop, condition and mutable accumulator.
OOPA Summator object with a method that encapsulates state.
Functionalfilter + reduce with pure functions.
DeclarativeQuery or expression that describes the result.

When to choose each one

  • Imperative: scripts, automation, code close to the hardware, critical performance.
  • OOP: domains with clear entities, large systems with teams, extensions via plugins.
  • Functional: data transformation, pipelines, concurrency, code that must be easy to test.
  • Declarative: queries, UI, configuration, business rules expressible as data.

In practice they are mixed: a JavaScript backend may use OOP for the domain and functional for processing lists; SQL for persistence; JSX for the UI.

Best practices

  • Choose the paradigm by the problem, not by fashion.
  • Keep functions small and with a single purpose.
  • Prefer immutability when it does not cost performance.
  • Avoid shared mutable state; if you need it, synchronise.
  • Use composition before deep inheritance.
  • Write code that reads like the intent, not like the steps.

Common mistakes

Mistake Why it is wrong What to do
Using OOP for everything, even simple scripts Unnecessary boilerplate and forced abstractions. Start simple; introduce classes when there is real state and behaviour.
Mutating data in «pure» functions Hidden side effects and hard-to-reproduce bugs. Return copies; document if there are effects.
Deep inheritance Fragile coupling; changes in the base break descendants. Prefer composition and interfaces.
Mixing paradigms without criteria Inconsistent code that is hard to maintain. Define conventions per layer (OOP domain, functional data, declarative UI).
Ignoring the cost of immutability Massive copies in hot loops degrade performance. Measure; use local mutation when it is safe and isolated.
