Databases

SQL and relational databases

A relational database stores data in tables that relate to each other through keys. SQL is the standard language for querying and modifying that data, and it remains one of the most valuable things to learn: SQLite, PostgreSQL and MySQL speak almost the same dialect.

In 5 points

  • Everything is tables (rows × columns); relationships are expressed with primary (PK) and foreign (FK) keys.
  • SELECT – FROM – WHERE – GROUP BY – HAVING – ORDER BY: that is the skeleton of 90% of queries.
  • JOIN combines tables by their keys; INNER keeps only matching rows, LEFT keeps everything on the left.
  • Indexes speed up searches at the cost of writes and space: create them for what you query most, not "just in case".
  • Transactions group operations into a block: either all succeed (commit) or none do (rollback).

Tables, keys and relationships

Each table models a kind of entity. Columns have a type (integer, text, date…) and each row is a unique record identified by its primary key. 

CREATE TABLE authors (
    id          INTEGER PRIMARY KEY,
    name        TEXT NOT NULL
  );

  CREATE TABLE articles (
    id           INTEGER PRIMARY KEY,
    title        TEXT NOT NULL,
    author_id    INTEGER REFERENCES authors(id),  -- foreign key: FK
    published    DATE,
    views        INTEGER DEFAULT 0
  );

The "one author writes many articles" (1‑N) relationship is reflected by carrying author_id in the child table. For "many to many" (N‑M) a join table is needed: 

CREATE TABLE article_tags (
    article_id  INTEGER REFERENCES articles(id),
    tag_id      INTEGER REFERENCES tags(id),
    PRIMARY KEY (article_id, tag_id)
  );

Basic queries: SELECT and WHERE

SELECT title, views
    FROM articles
    WHERE views > 100 AND published IS NOT NULL
    ORDER BY views DESC
    LIMIT 10 OFFSET 0;
  • WHERE filters rows; do not confuse it with HAVING, which filters after grouping.
  • NULL is never equal to anything: for it, use IS NULL / IS NOT NULL.
  • LIKE 'a%' searches by prefix (it can use an index); a leading % (LIKE '%a') makes the full scan slow because it disables the index.
  • The standard order of clauses is not optional: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

JOIN: combining tables

SELECT a.title, au.name AS author
    FROM articles a
    INNER JOIN authors au ON au.id = a.author_id
    WHERE a.views > 100;
Type What it returns
INNER JOINOnly rows that match in both tables.
LEFT JOINAll rows on the left; if there is no match, right-hand columns = NULL.
RIGHT JOINThe mirror of LEFT (less common; reorder and usually use LEFT).
FULL OUTER JOINEverything from both sides, with NULL where the match is missing.

Typical use of LEFT JOIN: "all authors, even those who still have no articles":

SELECT au.name, COUNT(a.id) AS total
    FROM authors au
    LEFT JOIN articles a ON a.author_id = au.id
    GROUP BY au.id;

The triangular query: an oversized JOIN with WHERE on columns without an index. If something "hangs", it is almost always a JOIN without an index or a SELECT * over millions of rows: measure with EXPLAIN.

Aggregations: GROUP BY

SELECT au.name,
           COUNT(*)            AS articles,
           AVG(a.views)        AS average_views,
           MAX(a.published)    AS latest
    FROM articles a
    INNER JOIN authors au ON au.id = a.author_id
    GROUP BY au.id
    HAVING COUNT(*) >= 3
    ORDER BY average_views DESC;
  • Common functions: COUNT, SUM, AVG, MIN, MAX.
  • In strict SQL, every column in the SELECT outside a function must appear in GROUP BY — or be the grouping key.
  • HAVING filters groups already computed; WHERE filters rows before grouping (and is cheaper).

INSERT, UPDATE, DELETE

INSERT INTO articles (title, author_id)
    VALUES ('Basic SQL', 7)
    RETURNING id;                 -- PostgreSQL/SQLite: returns the new row

  UPDATE articles SET views = views + 1 WHERE id = 42;

  DELETE FROM articles WHERE id = 42 AND author_id = 7;

An UPDATE or DELETE without WHERE affects every row in the table. Before running it on production, run the SELECT version with the same condition: 

-- Check which row(s) you would touch…
  SELECT id, title FROM articles WHERE id = 42 AND author_id = 7;
  -- …and only then replace SELECT with UPDATE / DELETE.

INSERT/UPDATE/DELETE should always use prepared statements from your code (parameters, never concatenation). The reason is in Security · SQL injection.

Indexes

An index is an ordered structure (a B‑tree) that lets you find rows without scanning the whole table: it is like the index of a book: 

CREATE INDEX articles_author_idx ON articles (author_id);
  CREATE INDEX articles_views_idx ON articles (views DESC);

  UNIQUE  INDEX articles_title_uq  ON articles (title);  -- also guarantees uniqueness
Pros Cons
Searches, JOINs and ORDER BY on those columns become much fasterEvery INSERT/UPDATE/DELETE must update it
FK and UNIQUE indexes are created by defaultThey take disk space

Index for JOINs on FKs, for frequent ORDER BY or GROUP BY, and for columns with few distinct values (status, type). Do not index columns that are almost always queried in full or with LIKE '%…%'. 

-- PostgreSQL: the query execution plan
  EXPLAIN ANALYZE
    SELECT * FROM articles WHERE author_id = 7;

  -- See existing indexes
  \di articles        -- psql
  .indexes articles   -- sqlite3

Transactions and ACID

A transaction groups operations so they are indivisible. If something fails halfway through, everything before it is undone (rollback): 

BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    UPDATE accounts SET balance = balance + 100 WHERE id = 2;
    COMMIT;        -- only if both steps succeeded
    -- on exception: ROLLBACK;

The four guarantees that define conventional database systems (ACID):

  • Atomicity — all or nothing.
  • Consistency — the rules (FK, types, UNIQUE constraints) are never violated.
  • Isolation — two concurrent transactions do not see half-finished states.
  • Durability — a commit survives a restart or a power cut.

Isolation has levels (READ UNCOMMITTED → SERIALIZABLE). The default REPEATABLE READ prevents two reads of the same transaction from returning different results; set it with SET TRANSACTION ISOLATION LEVEL …. Ask whether a different level is needed (the default is almost always fine).

Useful commands

# Lightweight client model for quick tests (SQLite ships without a server)
  sqlite3 test.db
    .tables             -- list tables
    .schema articles    -- show the CREATE TABLE
    .headers on         -- show column names
    .mode column        -- readable column output

  # PostgreSQL from psql
  psql -U user -d db
    \dt                 -- tables
    \d  articles        -- structure + indexes
    \di articles        -- indexes only

  # Backup / restore (PostgreSQL)
  pg_dump db > backup.sql
  psql db < backup.sql

Client commands vary between engines (\di only in psql, .indexes only in SQLite); the only invariant is standard SQL: SELECT, INSERT, UPDATE, DELETE, CREATE TABLE.

Best practices

  • Let columns be named consistently across the project (pick snake_case and do not change it).
  • No SELECT * in production: request the columns you will use; it also helps the query resolve from an index (covering).
  • Never interpolate user values into a query: always use prepared statements.
  • Enforce constraints: FK, NOT NULL, UNIQUE… so the engine defends integrity, not your code.
  • Measure before indexing: look at plans with EXPLAIN and create only the evidenced ones.
  • Versioned migrations (`.sql` files in the repo) and never modify tables by hand in production.
  • Automated scheduled backups: the basis of a programmer's peace of mind.
