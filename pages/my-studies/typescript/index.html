TypeScript

TypeScript es JavaScript con un sistema de tipos estáticos: describe qué forma tienen los valores antes de ejecutar el programa y el compilador avisa cuando el código no respeta esa descripción. Se convierte a JavaScript estándar, así que funciona en cualquier navegador y en cualquier entorno donde funcione JavaScript.

En 5 puntos

  • TypeScript añade anotaciones de tipo a JavaScript y se compila a JavaScript: no necesita un motor nuevo ni cambia el navegador.
  • La inferencia deduce la mayoría de los tipos; conviene anotar los contratos públicos y los casos ambiguos, no cada variable.
  • interface describe la forma de un objeto y type nombra también uniones e intersecciones de tipos.
  • Los genéricos permiten reutilizar funciones y estructuras conservando el tipo concreto de entrada y salida.
  • El compilador estrecha uniones según el control de flujo (narrowing) y detecta errores que en JavaScript solo aparecerían en producción.

¿Qué es TypeScript?

TypeScript es un superset de JavaScript: todo código JavaScript válido es código TypeScript válido, y además se pueden escribir anotaciones de tipo. Esas anotaciones describen la intención del programa; el compilador las comprueba y luego las elimina al generar el JavaScript final.

La diferencia se aprecia en una función sencilla. En JavaScript, llamar con un valor inesperado no produce ningún aviso hasta que la función intenta usarlo: 

function saludar(nombre) {
  return nombre.toUpperCase();
}

saludar(42);

Con TypeScript, el contrato queda explícito y el error se detecta antes de ejecutar: 

function saludar(nombre: string): string {
  return nombre.toUpperCase();
}

saludar(42);

No hace falta instalar nada en el navegador: la comprobación ocurre en el entorno de desarrollo. El compilador se suele ejecutar con tsc --noEmit cuando solo interesa revisar tipos, o con tsc cuando además se quiere generar el JavaScript de salida.

Los tipos viven en el código fuente, no en el JavaScript resultante. No validan por sí solos los datos que llegan de una API, un formulario o localStorage: esos datos hay que comprobarlos en tiempo de ejecución.

El objetivo no es «escribir más código», sino hacer explícitas las decisiones que ya se estaban tomando: qué acepta una función, qué devuelve y qué forma tienen los objetos que circulan entre módulos. En proyectos grandes, esa información evita tener que reconstruir el contrato de cada función leyendo todas sus llamadas.

Tipos primitivos e inferencia

Los tipos básicos son string, number, boolean, bigint, symbol, null y undefined. A partir de ellos se construyen arrays (number[]), tuplas, objetos y funciones. TypeScript también dispone de unknown (valor del que no se sabe nada y que obliga a comprobarlo antes de usarlo) y de never (un tipo que no puede tener valores, útil para ramas inalcanzables).

La inferencia es la parte que más trabajo ahorra: el compilador deduce el tipo a partir del valor inicial o del uso, así que no hace falta anotar cada declaración. 

let mensaje = 'Hola';
let contador = 0;
let activo = true;

const numeros = [1, 2, 3];
const persona = { nombre: 'Ana', edad: 34 };

mensaje = 42;

En el ejemplo, mensaje se infiere como string y la última línea es un error. numeros se infiere como number[] y persona como un objeto con las propiedades nombre: string y edad: number. Las anotaciones aportan información nueva cuando el valor inicial no la tiene, cuando se quiere una forma más general o cuando se define un contrato: 

let resultado: string | null = null;
const etiquetas: string[] = [];

function duplicar(valor: number): number {
  return valor * 2;
}

any desactiva la comprobación y contagia a todo lo que toca. Si aún no se conoce el tipo, unknown es la alternativa segura: obliga a estrechar el valor antes de acceder a sus propiedades.

Con strictNullChecks activo, null y undefined no se asignan automáticamente a cualquier tipo. Esa distinción obliga a declarar explícitamente cuándo un valor puede faltar, y es una de las comprobaciones que más errores reales evita.

Interfaces, tipos, uniones e intersecciones

Una interface describe la forma de un objeto: qué propiedades tiene y de qué tipo son. Se puede ampliar desde otra interfaz, por lo que encaja bien con modelos de datos que crecen por capas. 

interface Usuario {
  readonly id: number;
  nombre: string;
  correo?: string;
}

function mostrar(usuario: Usuario): string {
  return usuario.correo ?? usuario.nombre;
}

El signo ? marca una propiedad opcional y readonly impide reasignarla después de crear el objeto. El operador ?? elige el valor de la izquierda solo cuando no es null ni undefined.

Un alias de tipo (type) nombra cualquier tipo, no solo objetos: puede representar una unión, una intersección, una tupla o una firma de función. Una unión indica que el valor puede ser una de varias alternativas; una intersección combina requisitos de varios tipos. 

type Identificador = string | number;
type Punto = { x: number; y: number };
type Empleado = Usuario & { departamento: string };

function buscar(id: Identificador): Punto | null {
  return null;
}

Aquí Identificador admite texto o número, y Empleado debe cumplir a la vez lo que exige Usuario y tener departamento. Las uniones son la herramienta habitual para modelar estados: un resultado puede ser correcto o fallido, pero no las dos cosas a la vez.

Como regla práctica, usa interface para objetos que puedan ampliarse y type para uniones, intersecciones, tuplas o alias de funciones. Para objetos concretos que no se van a ampliar, ambas opciones son válidas; conviene elegir una y mantenerla en el proyecto.

Funciones y genéricos

Las anotaciones de una función describen sus parámetros y su valor de retorno. Los parámetros opcionales se marcan con ? y deben ir detrás de los obligatorios; los valores por defecto también hacen que un parámetro sea opcional. 

interface Opciones {
  idiom: string;
  mayusculas?: boolean;
}

function saludar(nombre: string, opciones?: Opciones): string {
  const texto = `Hola, ${nombre}`;
  return opciones?.mayusculas ? texto.toUpperCase() : texto;
}

Un genérico es un parámetro de tipo: permite escribir una función una sola vez sin perder el tipo concreto con el que se llama. Sin genéricos, la función identidad tendría que aceptar any y devolver any, con la consiguiente pérdida de información. 

function identidad<T>(valor: T): T {
  return valor;
}

const numero = identidad(7);
const texto = identidad('abc');

interface Respuesta<T> {
  datos: T;
  total: number;
}

numero se infiere como number y texto como string. Las estructuras de la biblioteca estándar usan el mismo mecanismo: Array<T>, Promise<T> o Map<K, V>.

Cuando la función necesita alguna capacidad del tipo, se puede restringir el genérico con extends. Así se exige, por ejemplo, que el valor tenga propiedad length: 

function longitud<T extends { length: number }>(valor: T): number {
  return valor.length;
}

longitud('hola');
longitud([1, 2, 3]);

Narrowing y control de flujo

El narrowing (estrechamiento) es el proceso por el que TypeScript reduce una unión a una de sus alternativas después de una comprobación. Es la razón principal por la que el compilador detecta antes muchos fallos que en JavaScript solo aparecerían al ejecutar una rama concreta. 

function describir(valor: string | number): string {
  if (typeof valor === 'string') {
    return valor.toUpperCase();
  }

  return valor.toFixed(2);
}

Dentro del if, valor es string y puede usar toUpperCase(); después, es number y puede usar toFixed(). No hace falta convertir ni afirmar el tipo a mano: la comprobación ya ha aportado esa información.

El patrón más útil es la unión discriminada: cada variante comparte una propiedad con un valor literal distinto. Al comprobar esa propiedad, el compilador sabe qué campos existen en cada rama. 

type Resultado =
  | { estado: 'ok'; datos: string[] }
  | { estado: 'error'; mensaje: string };

function resumir(resultado: Resultado): string {
  if (resultado.estado === 'ok') {
    return `${resultado.datos.length} elementos`;
  }

  return resultado.mensaje;
}

Otras comprobaciones que estrechan tipos son Array.isArray(), el operador in para preguntar por una propiedad, las comparaciones con null y las funciones de predicado de tipo. Conviene preferirlas antes que las afirmaciones as: una afirmación le dice al compilador que confíe, mientras que una comprobación realmente verifica el valor.

Si después de cubrir todas las variantes todavía queda un valor posible, el compilador puede avisar asignando la rama final a never. Ese aviso suele indicar que se añadió una alternativa nueva a la unión y que alguna función todavía no la trata.

Configuración y migración desde JavaScript

Las decisiones del compilador se guardan en tsconfig.json en la raíz del proyecto. Tres opciones marcan especialmente el resultado: target (versión de JavaScript de salida), module (sistema de módulos) y strict (conjunto de comprobaciones estrictas, que incluye strictNullChecks y noImplicitAny). 

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "noEmit": true,
    "lib": ["ES2022", "DOM"]
  },
  "include": ["src"]
}

Con noEmit, tsc actúa solo como revisor de tipos y el empaquetador existente sigue generando los archivos. En proyectos sin empaquetador, se puede quitar esa opción y dejar que el compilador produzca los archivos JavaScript.

Migrar un proyecto grande no obliga a renombrar todos los archivos de una vez. Una ruta gradual es:

  • Activar allowJs para que el compilador acepte archivos .js junto a los .ts.
  • Renombrar primero los módulos pequeños y bien delimitados; después los que más se usan.
  • Empezar con strict en false si hace falta y activar una opción cada vez, empezando por strictNullChecks.
  • Usar unknown en los límites del sistema (respuestas HTTP, almacenamiento local) y validar ahí los datos antes de confiar en ellos.
  • Añadir la comprobación de tipos a la integración continua para que un error de tipo no llegue a la rama principal.

Lo importante es que cada paso deje el código en un estado mejor: más contratos explícitos y menos decisiones implícitas. Un proyecto parcialmente tipado se beneficia de la comprobación en las zonas ya migradas.

Errores comunes

Error Por qué está mal Qué hacer
Usar any para silenciar errores. Desactiva la comprobación y se propaga por las llamadas. Usar unknown y estrechar el valor, o escribir el tipo correcto.
Creer que los tipos validan datos externos. Las anotaciones desaparecen al compilar. Comprobar en tiempo de ejecución los datos de API, formularios y almacenamiento.
Anotar variables cuya ya tipo se infiere. Añade ruido y puede quedar desactualizado al cambiar el valor. Reservar las anotaciones para contratos y valores ambiguos.
Abusar de as para forzar un tipo. La afirmación no comprueba nada: solo calla al compilador. Preferir comprobaciones reales con typeof, in o uniones discriminadas.
Olvidar null en un tipo de retorno. Una búsqueda puede no encontrar resultado y devolver null. Declarar T | null y obligar a tratar ese caso.
