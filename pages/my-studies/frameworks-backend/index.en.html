Frameworks

Back-end frameworks

A back-end framework organizes the code that receives requests, applies business rules and returns responses. Its tools can ease routing, error handling, validation and data access, but they do not replace application design. Understanding the request-response cycle and separating responsibilities helps build clearer, more maintainable services.

In 5 points

  • The back-end processes requests, applies business logic and responds to clients such as browsers, mobile apps or other services.
  • A server framework offers conventions and tools for common tasks, such as routes and middleware.
  • Separating routes, controllers, services and data access lets you assign responsibilities and test each part more easily.
  • REST, GraphQL and WebSockets are distinct approaches to communicating systems; they are not interchangeable in all cases.
  • Security must be designed into every layer: validate inputs, control permissions and handle errors without revealing sensitive information.

What is a back-end framework?

The back-end is the part of an application that runs on the server or in a service environment. It can receive requests over a network, query data, apply business rules and prepare a response. The front-end is usually the browser or application that starts the interaction, although one service can also communicate with another service.

A back-end framework provides a structure for developing that software. Depending on the technology, it may include an HTTP server, a routing system, middleware, validation tools, templates or database integration. Some solutions are lightweight and leave many decisions to the team; others offer a more prescriptive structure.

Using a framework does not make an application automatically secure, scalable or correct. The team remains responsible for defining its rules, validating data, controlling access, handling errors and maintaining its dependencies.

The request-response cycle

In a typical HTTP communication, the client sends a request that includes a method, a path, headers and, in some cases, a body. The server receives that request, identifies which operation it corresponds to, performs the needed work and returns a response with a status code, headers and, often, content.

  1. The client makes a request: for example, it asks for a list of products.
  2. The server interprets the path and method: the router looks for the matching operation.
  3. Checks and rules run: middleware and application logic may validate the request and permissions.
  4. The application obtains or modifies data: it may query a database or another service.
  5. The server builds a response: it returns a status code and appropriate content.

Routing, controllers and middleware

Routing relates an HTTP method and a path to an operation. For example, an application may use GET /articles to query a collection and POST /articles to request creation of a resource.

A controller receives the request associated with a route and organizes the response. It is good practice to avoid accumulating all business logic and all data queries in it: delegating responsibilities makes the code easier to understand, test and maintain.

Middleware is a function that can run during request processing, before the response is completed. It can log information, parse the body, check authentication or handle errors. Registration order matters: a middleware must run at the right moment and either continue the flow or end the response correctly.

In Express, a route can connect a URL with a handler function. It is also common to separate route registration, controller functions and domain logic into different modules. The appropriate structure depends on the project's size and needs.

Application layers

A server application can be divided into layers with differentiated responsibilities. There is no single mandatory architecture, but separating functions reduces the mixing of HTTP details, business rules and data queries.

Layer Usual responsibility Example task
Routing Relates methods and paths to handlers. Connect GET /articles/:id with a query operation.
Controller Interprets the request and coordinates the HTTP response. Read parameters, invoke a service and choose the status code.
Service Implements application rules and use cases. Check whether publishing an article is allowed.
Data access Obtains or modifies persistent information. Find a record through a query or repository.
Middleware Applies cross-cutting processing to the request flow. Log requests or verify credentials.

Layers may be named differently and combined in small projects. The important criterion is that each piece has an understandable responsibility and that dependencies do not create hard-to-maintain cycles.

ORM and data access

The data access layer communicates the application with a storage system. It can use direct SQL queries, a query library or an ORM (object-relational mapper), which relates programming-language structures to relational tables and records.

An ORM can reduce repetition of common operations and offer abstractions for queries, relationships and schema changes. However, it does not remove the need to understand the database: inefficient queries, poorly modeled relationships or excessive record access can affect performance and correctness.

  • Validate data before persisting it and apply appropriate constraints in the database.
  • Use parameterized queries or equivalent mechanisms so inputs are not concatenated untreated into statements.
  • Define how transactions are handled when several operations must complete together.
  • Avoid exposing internal storage details in public responses when not needed.

The ORM is an implementation tool, not an automatic security layer. Authorization, validation and query design remain the application's responsibilities.

Server rendering and API

In server rendering, the server generates HTML for a page and sends it to the browser. This approach can deliver content ready to show and is useful for sites whose content is organized around pages. Hydration or client-side JavaScript can add interactivity, if the project uses them.

An API exposes operations or data for another client to consume. An HTTP API can respond with JSON, although the format and protocol depend on the design. The client can be a web application, a mobile application, an integration or even another service.

Rendering HTML and exposing an API are not mutually exclusive options. The same application can serve pages and offer data endpoints. The choice depends on the clients, the content, the interaction needs and the operational requirements.

REST, GraphQL and WebSockets

REST, GraphQL and WebSockets often appear in conversations about communication between clients and servers, but they represent concepts of different kinds. REST is an architectural style for designing resource interfaces; GraphQL is a query language and a runtime environment for APIs; WebSocket is a protocol that allows persistent bidirectional communication.

Approach Communication model May fit when… Consideration
REST HTTP operations over resources, usually identified by paths. An API based on resources and known HTTP methods is sought. Design paths, statuses, errors and compatibility consistently.
GraphQL The client expresses in a query the fields it needs, within the available schema. Several clients need to query different combinations of data. Control query complexity, permissions and execution cost.
WebSockets Persistent connection for bidirectional message exchange. Frequent updates are needed in both directions, such as live collaboration. Requires managing connections, authentication, reconnections and operational scaling.

The table is a general guide, not a quality ranking. REST and GraphQL describe ways of designing APIs; WebSocket describes a communication protocol. An application can combine mechanisms if its needs justify it.

Authentication and authorization

Authentication checks who makes a request. Authorization determines which actions that identity may perform. They are different controls: knowing who someone is does not imply they have permission to access all resources.

The framework can ease middleware or integration points for these controls, but the application must define the policies. Check permissions on the server for each protected operation; hiding a button on the front-end does not prevent someone from trying to call a route directly.

  • Validate inputs and limit accepted data to what the operation needs.
  • Avoid including passwords, secrets or internal details in logs and responses.
  • Use session or token mechanisms appropriate to the context and protect their storage and transport.
  • Return errors useful to the client without revealing internal traces or confidential information.
  • Apply limits and additional controls when operations or resources require it.

Authentication and authorization should be part of the design of each protected route. Adding a generic control without reviewing permissions for each resource can leave improper accesses.

HTTP server with Express

This example shows a minimal server in Node.js with Express and a read REST endpoint. It includes a route to query a collection and another to obtain an element by identifier, plus basic responses for invalid requests or non-existent resources.

To run it, a project with Express installed is needed. Dependency installation and production configuration depend on the project and are not included here. 

const express = require('express');

const app = express();
const port = process.env.PORT || 3000;

app.use(express.json());

const articles = [
  { id: 1, title: 'Introduction to HTTP' },
  { id: 2, title: 'API design' }
];

app.get('/articles', (req, res) => {
  res.status(200).json(articles);
});

app.get('/articles/:id', (req, res) => {
  const id = Number(req.params.id);

  if (!Number.isInteger(id) || id < 1) {
    return res.status(400).json({ error: 'Invalid identifier' });
  }

  const article = articles.find((element) => element.id === id);

  if (!article) {
    return res.status(404).json({ error: 'Article not found' });
  }

  return res.status(200).json(article);
});

app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: 'Internal server error' });
});

app.listen(port, () => {
  console.log(`Server listening on port ${port}`);
});

The express.json() middleware allows interpreting JSON bodies in requests that admit them, although this example only exposes read routes. The article list lives in memory and is lost when the process restarts: a real application would normally delegate persistence to a data layer.

The error handler in the example is deliberately simple. In a real application, log errors in a controlled way, distinguish failure classes and avoid sending internal details to the client.

Common mistakes

Mistake Consequence Best practice
Concentrating routes, rules and queries in a single function. The code becomes hard to test and change without side effects. Separate responsibilities when complexity justifies it.
Trusting client-side validation. A request can be sent directly with unexpected data. Validate inputs on the server and define constraints in storage.
Confusing authentication with authorization. An authenticated user may end up accessing resources that do not belong to them. Check identity and permissions per operation and resource.
Always returning the success status code. Clients cannot distinguish a correct operation from a failed one. Choose status codes and error formats consistent with the result.
Exposing internal error messages. The response may reveal paths, queries, data or implementation details. Return safe messages and keep technical detail in protected logs.
Choosing a communication technology by fashion. The solution may add complexity without solving a real need. Start from client requirements, data and the interaction pattern.
Assuming the ORM avoids any query problem. There may be costly queries or excessive data access. Review queries and measure behavior with representative loads.
