Arquitectura y diseño de software

Principios de diseño y SOLID

Diseñar software implica decidir cómo repartir responsabilidades y cómo hacer que sus partes puedan cambiar sin romper otras. SOLID reúne cinco principios de diseño orientado a objetos que ayudan a razonar sobre esas decisiones: responsabilidad única, abierto/cerrado, sustitución de Liskov, segregación de interfaces e inversión de dependencias. No son reglas mecánicas ni garantizan buen diseño por sí solas; sirven para identificar acoplamientos y mejorar el código cuando hay una necesidad concreta.

En 5 puntos

  • SOLID es un conjunto de cinco principios para pensar el diseño de software orientado a objetos.
  • Responsabilidad única busca que un módulo tenga una razón principal para cambiar.
  • Abierto/cerrado y sustitución de Liskov promueven extensiones seguras y comportamientos compatibles.
  • Segregación de interfaces e inversión de dependencias reducen dependencias innecesarias entre componentes.
  • Aplicar SOLID no significa crear más clases: el diseño debe responder a necesidades reales y mantenerse comprensible.

¿Qué es SOLID?

SOLID es un acrónimo que agrupa cinco principios de diseño asociados a la programación orientada a objetos. Su propósito es ayudar a construir componentes con responsabilidades claras y dependencias que puedan manejarse cuando el sistema evoluciona.

Los principios no describen una arquitectura única ni una lista de pasos obligatorios. Son criterios para evaluar decisiones: ¿qué partes cambian juntas?, ¿qué dependencias hacen difícil probar una pieza?, ¿una implementación puede reemplazar a otra sin alterar las expectativas?

Aunque se explican con clases e interfaces, muchas de sus ideas también se aplican a módulos, funciones y servicios. La abstracción elegida debe ser adecuada al lenguaje y al tamaño del problema.

Letra Principio Pregunta guía
S Responsabilidad única ¿Este módulo tiene una razón principal para cambiar?
O Abierto/cerrado ¿Puedo añadir un comportamiento sin modificar código estable de forma repetida?
L Sustitución de Liskov ¿Una implementación alternativa cumple las expectativas del tipo que reemplaza?
I Segregación de interfaces ¿Los consumidores dependen solo de las operaciones que necesitan?
D Inversión de dependencias ¿La lógica importante depende de contratos en vez de detalles concretos?

S: responsabilidad única

El principio de responsabilidad única (SRP, por sus siglas en inglés) propone que un módulo tenga una responsabilidad principal y una razón coherente para cambiar. No exige que una clase haga una sola operación: busca evitar que una misma unidad mezcle preocupaciones que cambian por motivos diferentes.

Por ejemplo, una clase que calcula el total de una compra, genera un informe y lo envía por correo reúne reglas de cálculo, presentación y comunicación. Si cambian las reglas fiscales, el formato del informe o el servicio de correo, la misma clase puede necesitar modificaciones por razones distintas.

Una alternativa es separar esas preocupaciones en componentes con funciones definidas: un servicio para calcular, un formateador para presentar y un adaptador para enviar. La separación debe seguir la organización real del dominio; crear una clase por cada línea de código no es el objetivo.

«Una razón para cambiar» se interpreta en relación con los actores o áreas que solicitan cambios, no como una regla literal sobre el número de métodos.

O: abierto/cerrado

El principio abierto/cerrado (OCP) plantea que una unidad de software debería permitir la extensión de su comportamiento sin requerir modificaciones repetidas de su código estable. No significa que el código nunca pueda cambiar: significa que conviene diseñar puntos de extensión cuando los cambios previsibles lo justifican.

Si una función selecciona una operación mediante una cadena de condicionales, cada nuevo tipo puede exigir editar esa función. Cuando existen comportamientos que varían, una interfaz o una estrategia intercambiable puede permitir añadir una implementación sin reescribir la lógica que la utiliza. 

class CalculadoraDescuento {
  calcular(compra, tipoCliente) {
    if (tipoCliente === 'regular') {
      return compra * 0.05;
    }

    if (tipoCliente === 'preferente') {
      return compra * 0.10;
    }

    return 0;
  }
}

En este ejemplo, incorporar otra categoría obliga a modificar la misma función. Una opción para un sistema donde esas reglas cambian con frecuencia es representar cada política como un objeto con un método común: 

class DescuentoRegular {
  calcular(compra) {
    return compra * 0.05;
  }
}

class DescuentoPreferente {
  calcular(compra) {
    return compra * 0.10;
  }
}

function calcularDescuento(compra, politica) {
  return politica.calcular(compra);
}

const descuento = calcularDescuento(
  200,
  new DescuentoPreferente()
);

La segunda forma introduce abstracciones adicionales. Si solo existen dos reglas estables y el sistema es pequeño, una condición simple puede ser más clara. La extensión debe resolver un costo real, no anticipar posibilidades imaginarias.

L: sustitución de Liskov

El principio de sustitución de Liskov (LSP) indica que una implementación de un tipo debe poder utilizarse donde se espera ese tipo sin romper las propiedades que el programa presupone. En términos prácticos, una clase derivada o una implementación no debería sorprender a quien la usa al incumplir el contrato establecido.

Una señal de diseño problemático aparece cuando una subclase necesita rechazar operaciones que el tipo base promete, cambia el significado de un método o exige condiciones más restrictivas que el contrato original.

Por ejemplo, si un tipo Almacenamiento promete guardar y recuperar valores, toda implementación que se presente bajo ese contrato debería ofrecer ambas operaciones con el comportamiento acordado. Una implementación de solo lectura no debería fingir que cumple ese contrato si no puede guardar.

El principio no prohíbe la herencia. Invita a definir contratos claros y a comprobar que las variantes respeten las expectativas del código cliente. En algunos casos, composición o interfaces más pequeñas representan mejor las capacidades reales.

I: segregación de interfaces

El principio de segregación de interfaces (ISP) recomienda que los consumidores no dependan de operaciones que no utilizan. En vez de una interfaz grande que obliga a implementar métodos irrelevantes, pueden definirse contratos más pequeños según las capacidades necesarias.

Imagina una interfaz de dispositivo con operaciones para imprimir, escanear y enviar un fax. Un dispositivo que solo imprime tendría que incluir métodos que no puede ofrecer, posiblemente con errores o implementaciones vacías. Separar las capacidades permite que cada consumidor dependa de lo que realmente necesita. 

class Impresora {
  imprimir(documento) {
    console.log(`Imprimiendo: ${documento}`);
  }
}

class Escaner {
  escanear(documento) {
    return `Copia de: ${documento}`;
  }
}

function enviarAImpresora(impresora, documento) {
  impresora.imprimir(documento);
}

JavaScript no exige declarar interfaces de manera nativa como algunos lenguajes tipados, pero la separación de capacidades también puede reflejarse en funciones, módulos y contratos documentados.

D: inversión de dependencias

El principio de inversión de dependencias (DIP) propone que los módulos de alto nivel, donde viven las reglas importantes, no dependan directamente de detalles de bajo nivel. Ambos deberían depender de abstracciones. A su vez, los detalles concretos implementan esas abstracciones.

Un servicio de notificaciones que crea directamente un cliente SMTP queda acoplado a una tecnología concreta. Si recibe una dependencia que cumple un contrato común, puede utilizar distintas formas de envío sin cambiar la lógica central. 

class ServicioNotificaciones {
  constructor(canal) {
    this.canal = canal;
  }

  enviar(destinatario, mensaje) {
    return this.canal.enviar(destinatario, mensaje);
  }
}

class CanalConsola {
  enviar(destinatario, mensaje) {
    console.log(`Para ${destinatario}: ${mensaje}`);
  }
}

const servicio = new ServicioNotificaciones(new CanalConsola());
servicio.enviar('equipo@example.test', 'La tarea terminó');

La abstracción no tiene que ser una interfaz formal. Puede ser un contrato, una función o un objeto con las operaciones que el módulo necesita. La inyección de dependencias es una técnica habitual para proporcionar esas dependencias desde fuera; es una forma de implementar la idea, no un sinónimo exacto del principio.

Cómo se relacionan los principios

Los principios se apoyan entre sí. Una responsabilidad clara facilita localizar cambios; contratos pequeños evitan dependencias innecesarias; las abstracciones permiten sustituir implementaciones y extender comportamientos. El diagrama resume una posible relación, no una secuencia obligatoria de aplicación.

En conjunto, estos criterios ayudan a que los componentes tengan límites comprensibles y colaboren mediante contratos. Aun así, un sistema puede ser mantenible sin aplicar cada principio de forma explícita, y una aplicación rígida de SOLID puede producir abstracciones innecesarias.

Cuándo aplicar SOLID

SOLID resulta especialmente útil al revisar código que cambia con frecuencia, cuesta probar o obliga a modificar muchas partes para añadir una capacidad. También ofrece un vocabulario común para discutir por qué una dependencia o una responsabilidad dificulta el mantenimiento.

  • Empieza por un problema observable: cambios repetidos, pruebas difíciles o dependencias que impiden sustituir una pieza.
  • Identifica qué responsabilidad o contrato está involucrado antes de añadir una nueva abstracción.
  • Haz un cambio acotado y comprueba que el comportamiento existente siga funcionando.
  • Usa pruebas para documentar los contratos importantes y detectar regresiones.
  • Reevalúa el diseño cuando aparezcan nuevos requisitos; no es necesario anticiparlos todos.

La simplicidad también es una propiedad del diseño. Si una abstracción no reduce complejidad presente ni facilita un cambio probable, puede ser mejor mantener la solución directa.

Errores comunes

Error Por qué perjudica Mejor enfoque
Interpretar responsabilidad única como «una clase, un método». Produce divisiones artificiales sin aclarar los motivos reales de cambio. Busca responsabilidades coherentes y razones de cambio relacionadas.
Diseñar extensiones para cualquier futuro imaginable. Añade complejidad antes de que exista una necesidad. Introduce puntos de extensión cuando un patrón de cambio los justifique.
Usar herencia solo para reutilizar código. La subclase puede no cumplir el contrato de la clase base. Comprueba la sustituibilidad y considera composición cuando encaje mejor.
Crear interfaces enormes con métodos opcionales o vacíos. Los consumidores dependen de operaciones que no necesitan y los contratos pierden claridad. Divide las capacidades según las necesidades de sus consumidores.
Confundir inversión de dependencias con usar un contenedor de inyección. Una herramienta de inyección no garantiza que las dependencias estén bien diseñadas. Define primero el contrato necesario y después el mecanismo para proporcionar la implementación.
Aplicar los cinco principios como una lista de comprobación rígida. Puede llevar a capas y abstracciones que no aportan valor. Úsalos como preguntas de diseño frente a problemas concretos.
