Web (HTML, CSS y JavaScript)

HTTP y navegador web

Entre que escribes una URL y que aparece la página en pantalla pasa todo: DNS, TCP, TLS, una petición HTTP, descargas paralelas, construcción del DOM, determinación de estilos… Si entiendes ese ciclo y las herramientas que lo inspeccionan, el navegador deja de ser una caja negra.

En 5 puntos

  • Una página típica dispara decenas de peticiones: HTML, CSS, imágenes, scripts, fuentes y llamadas a APIs.
  • La petición la forma el método + ruta + cabeceras; la respuesta, el código de estado + cabeceras + cuerpo.
  • El navegador construye el DOM (del HTML) y el CSSOM (del CSS), y solo entonces pinta.
  • Caché, compresión y CDN evitan repetir trabajo: Cache-Control es donde se decide.
  • CORS decide si una página puede leer respuestas de otro origen; se negocia con cabeceras, no con «bloqueos» del servidor por gusto.

El ciclo completo de una página

Pasos desde que pulsas Intro hasta que la página funciona:

  1. Resolución de nombres: el navegador pregunta al DNS cuál es la IP de ejemplo.com (caché de SO, router y servidor DNS).
  2. Conexión: abre TCP hacia el puerto 80/443; si es HTTPS, primero handshake TLS (ver TLS).
  3. Petición: envía GET / HTTP/1.1 con cabeceras (Host, Accept, cookies…).
  4. Respuesta: el servidor contesta código + cabeceras + HTML.
  5. Análisis y cargas derivadas: mientras lee el HTML, descubre CSS, scripts, imágenes y fonts, y pide cada uno (ver la sección de bloqueo).
  6. Render: construye el árbol de render y pinta.
  7. Ejecución: corre los scripts; quizá hagan más fetch y repiten el ciclo.

Del HTML al píxel: cómo renderiza el navegador

El motor de render realiza cuatro pasos, en ese orden, para cada refresco visual:

  1. Análisis del HTML → DOM: parsea etiquetas y construye el árbol de nodos.
  2. Análisis del CSS → CSSOM: convierte las reglas en un árbol de estilos.
  3. Árbol de render: combina ambos (layout: tamaño y posición de cada caja) y descarta lo invisible (display: none, elementos hidden).
  4. Pintado y composición: dibuja capas y las compone con la GPU.

Cambiar propiedades que solo tocan el pintado (color, background) es barato; cambiar tamaño o posición obliga a recalcular layout (reflow) y es más caro. Animar transform y opacity es lo recomendable.

Recursos, orden y bloqueo

No todos los recursos se cargan igual cuando el parser está leyendo el HTML:

Recurso Comportamiento por defecto Cómo controlarlo
CSS (<link>)Bloquea el render hasta descargarse y analizarsemedia para perfiles concretos; hojas críticas pequeñas
Script clásico (<script src>)Detiene el parseo, descarga, ejecuta y continúadefer: tras el parseo y en orden. async: en cuanto llegue, sin orden
type="module"Es defer por defectoNecesita servidor HTTP (file:// lo bloquea por CORS)
ImágenesNo bloquean el parseo; reservan espacio recién al medirloading="lazy", width/height para evitar saltos
Fuentes remotasPueden dejar texto invisible mientras carganfont-display: swap, precarga con preload
 
<!-- ejecución en orden, tras parsear el documento -->
  <script defer src="app-a.js"></script>
  <script defer src="app-b.js"></script>

  <!-- independiente: no espera al parser ni a otros scripts -->
  <script async src="analytics.js"></script>

async y defer solo funcionan con script externos. En línea, corren donde toca y bloquean.

Caché y cabeceras

El navegador guarda copias de recursos. La política la dictan las cabeceras de respuesta: 

Cache-Control: max-age=31536000, immutable   # bueno CSS/JS con hash en el nombre
  Cache-Control: no-cache                       # revalidar siempre antes de usar
  Cache-Control: no-store                       # no guardar nada (datos sensibles)
  ETag: "v18b2"                                 # identificador de versión » If-None-Match
  Last-Modified: Thu, 05 Nov 2026 10:00:00 GMT  # » If-Modified-Since
  • Respuesta 200: el recurso va completo.
  • 304 Not Modified: no cambió; se usa la copia local (y con ETag o Last-Modified en la petición de validación).
  • Patrón típico: los estáticos se sirven con nombre «con hash» (bundle.a8f3e2.css) y se cachean un año de forma segura; el HTML no se cachea, para que siempre anuncie la última versión.

Comprobación rápida:

curl -sI https://pfd1795.github.io/ | grep -iE 'cache-control|etag'
  curl -sI -H 'If-Modified-Since: Thu, 05 Nov 2026 10:00:00 GMT' \
    https://pfd1795.github.io/ | head -3

CORS: leer respuestas de otro origen

Un origen es la combinación de esquema + dominio + puerto. Por defecto, el navegador deja que las peticiones cruzadas de origen se envíen (con limitaciones), pero no da a tu JavaScript el acceso a la respuesta si el servidor no autoriza explícitamente. Eso es CORS: Cross-Origin Resource Sharing.

Escenario típico — tu front en app.ejemplo — tu API en api.ejemplo:

# petición simple (GET, POST de formularios): el navegador la envía igual
  GET https://api.ejemplo/datos  Origin: https://app.ejemplo
  # respuesta: el servidor DEBE autorizar el origen
  Access-Control-Allow-Origin: https://app.ejemplo
# petición «no simple» (PUT, cabeceras custom, JSON): primero un preflight
  OPTIONS /datos  Origin: https://app.ejemplo
                  Access-Control-Request-Method: PUT
                  Access-Control-Request-Headers: autorizacion
  # respuesta del preflight
  Access-Control-Allow-Origin: https://app.ejemplo
  Access-Control-Allow-Methods: PUT, POST
  Access-Control-Allow-Headers: autorizacion
  • * (todo origen) no vale junto con credenciales (cookies): hay que listar el origen concreto.
  • CORS se configura del lado del servidor: desde el front no hay nada que «arreglar», salvo pedir al API que habilite tu origen.
  • Errores típicos: «blocked by CORS policy», preflight 404 (el servidor no maneja OPTIONS), falta Allow-Headers.

CORS protege a los usuarios, no al servidor: impide que el JS de un sitio malicioso lea datos de otro sitio donde la víctima esté autenticada. Jerarquía conocida con la que conviven: cookies SameSite (Seguridad · Cookies de sesión) y protecciones CSP.

Todo el almacenamiento client-side es legible por JavaScript en tu origen: los datos sensibles no van ahí (ver Seguridad · Cookies de sesión). Este portafolio usa localStorage para tema, idioma y récords de juegos. 

localStorage.setItem('tema', 'dark');
  localStorage.getItem('tema');     // 'dark'
  localStorage.removeItem('tema');  // borrar

HTTP/2 y HTTP/3

  • HTTP/2 (2015, sobre TLS): multiplexa varias peticiones en una conexión, comprime cabeceras y permite el servidor «empujar» recursos. Alt-Svc, h2.
  • HTTP/3 (2022, QUIC sobre UDP): como HTTP/2 pero sin bloqueo de cabecera TCP (head-of-line blocking), handshake más rápido incorpora TLS 1.3. Incrementa velocidad percibida en móvil.
  • Las CDN y los hostings modernos sirven ambos por defecto; desde el navegador solo se nota una conexión más rápida.
# comprobar la versión usada (es transparente)
  curl -sI -o /dev/null -w '%{http_version}\n' https://pfd1795.github.io/

DevTools: la pestaña Network

Hábitos útiles al depurar rendimiento y errores de red (F12 → Network):

  • Deshabilitar caché con DevTools abierto, para ver siempre respuestas de servidor.
  • Ordenar por tamaño/latencia; fijarse en la columna tiempo y en la de waterfall.
  • Columna Size: (disk cache) indica que se sirvió de memoria local.
  • Filtrar por XHR/Fetch para ver solo llamadas a APIs, e inspeccionar «Initiator» para ver quién pidió el recurso.
  • «Throttling» (Fast 3G) para simular móvil; «Block request URL» para saber si tu web funciona sin CDN de terceros.
# equivalentes de línea de comandos para lo mismo
  curl -o /dev/null -s -w 'total: %{time_total}s · tamaño: %{size_download}B\n' URL
  curl -w '@-' -o /dev/null -s URL <<'EOF'
             dns:  %{time_namelookup}s
             tcp:  %{time_connect}s
             tls:  %{time_appconnect}s
             1 byte: %{time_starttransfer}s
EOF

Buenas prácticas

  • Menos número de peticiones pesa más que optimizar de a una: combina, minifica y usa sprite de fuentes e iconos.
  • Cachear agresivamente lo estático (con hash en el nombre) y nada lo dinámico.
  • Define width y height en imágenes para evitar saltos de layout (CLS).
  • defer (o módulos) para tus scripts salvo que se necesizn realmente al instante.
  • Habilita compresión (gzip/brotli) en tu servidor o pide CDN que la aplique.
  • Aprende a diagnosticar primero con Network y curl: menos adivinar, más medir.
