Criptografía básica

La criptografía deja los datos ininteligibles para quien no tenga la clave. Como programador no vas a inventar algoritmos —y conviene que no lo intentes—, pero sí necesitas saber qué herramienta elegir en cada caso: hash para verificar, cifrado para ocultar, firma para autenticar.

Hash y cifrado: no es lo mismo

La confusión más común en seguridad. Sirven a objetivos opuestos:

Característica Hash Cifrado
Es reversibleNo: de ida y vuelta imposible (funciona en una sola dirección)Sí: con la clave se descifra
DevuelveUna «huella» de tamaño fijoEl mismo tamaño aprox. del original
ObjetivoVerificar integridad o identidadOcultar el contenido
Usa claveNo (en su uso básico)Siempre
Ejemplo de usoContraseñas, checksums, deduplicaciónTLS, discos, bases de datos cifradas

«Cifrar las contraseñas» es un error clásico: si el servidor tiene la clave, el atacante que la roba descifra todas. Las contraseñas se hashean con sal. (Vea Guardar contraseñas.)

Funciones hash

Un hash convierte cualquier entrada en una cadena de longitud fija, de forma determinista: la misma entrada da siempre la misma salida, pero de la salida no se puede deducir la entrada. Cambiar un solo bit del original cambia totalmente el hash (efecto avalancha).

  • SHA-256 / SHA-3: los recomendables hoy.
  • MD5 y SHA-1: rotos para seguridad (solo sirven para checksums de compatibilidad).
  • El choque (dos entradas distintas, mismo hash) es teóricamente posible; en SHA-256 es computacionalmente inviable.
echo -n "pfd1795" | sha256sum
  # b94d5a...  (64 caracteres hexadecimales = 256 bits)

Uso típico: comparar si un archivo descargado es idéntico al original:

sha256sum ubuntu.iso
  # compara el resultado con el valor que publica el proveedor

Guardar contraseñas

Una base de datos de usuarios no debe guardar contraseñas ni siquiera hasheadas con SHA-256 «a pelo»: son tan rápidas que un atacante prueba miles de millones de contraseñas por segundo con tarjetas de video. Se necesitan hashes deliberadamente lentos y con sal:

Algoritmo Comentario
bcryptMuy extendido; incorpora sal y un factor de coste ajustable.
argon2idGanador del concurso "Password Hashing"; opción recomendada hoy.
scryptSimilar, pensado para resistir hardware especializado (GPU/ASIC).
PBKDF2Aceptable, aunque el de menor protección de la lista.
MD5 / SHA-1 / SHA-256 solosNunca para contraseñas.
 
// bcrypt: el «cost factor» hace el hash 2^coste veces más lento
  import bcrypt from 'bcryptjs';

  const hash = await bcrypt.hash(contrasena, 12);      // al registrar
  const ok = await bcrypt.compare(contrasena, hash);   // al iniciar sesión

El hash resultante ya incluye la sal embebida:

$2a$12$R9h/cIPz0gi.URNNX3BkhO0qEHdZ8mG6bI7j1tXnSjW09pSmH8ED6
   |   |  |                       |
   |   |  |                       └ hash (con la sal dentro)
   |   |  └ cost factor (2^12 iteraciones)
   |   └ algoritmo bcrypt
   └ prefijo de formato

La sal es un valor aleatorio que se mezcla con la contraseña antes de hashear. Evita que dos usuarios con la misma contraseña compartan hash, y que el atacante use tablas precalculadas (rainbow tables).

Cifrado simétrico

La misma clave cifra y descifra. Es rápido y sirve para cualquier volumen de datos, pero hay un problema logístico: ¿cómo hace llegar la clave al destinatario sin que nadie la intercepte?

  • AES: el estándar vigente (AES-128 o AES-256).
  • ChaCha20-Poly1305: preferible en móviles por su eficiencia (lo usa TLS 1.3 también).
  • Antiguos (DES, 3DES, RC4): sustituidos, no usar en proyectos nuevos.
openssl enc -aes-256-cbc -salt -in secreto.txt -out secreto.enc
  openssl enc -d -aes-256-cbc -in secreto.enc -out secreto.txt

El modo importa tanto como el algoritmo: GCM (autenticado) es la opción por defecto; los modos CBC sin MAC quedan vulnerables a manipulación. En la práctica, usa librerías verificadas y deja que ellas elijan modo y relleno.

Cifrado asimétrico

Resuelve el problema logístico del simétrico con un par de claves: lo que cifra una, lo descifra solo la otra. Reparte la pública a todo el mundo; la privada jamás sale de tu equipo.

  • Para recibir mensajes: cualquiera cifra con tu pública; solo tú descifras con la privada.
  • Para demostrar identidad: la clave privada firma; cualquiera verifica con la pública.
  • Algoritmos actuales: RSA (2048 bits mínimo), ECDSA, Ed25519, X25519.
# Generar un par SSH (type ed25519, moderno)
  ssh-keygen -t ed25519 -C "tu@correo.com"
  # id_ed25519     → clave privada (no la compartas nunca)
  # id_ed25519.pub → clave pública (la publicas en GitHub / servidores)

En la web, HTTPS usa asimétrico solo para establecer la conexión (intercambiar o acordar una clave), y entonces cifra todo el resto con simétrico, mucho más rápido. Más detalles en Ciberseguridad · TLS y certificados.

Firmas digitales

Una firma prueba quién emitió el dato y que no cambió desde entonces. Se firma con la clave privada; cualquiera puede verificar con la pública:

  1. Se calcula el hash del documento.
  2. Se cifra el hash con la clave privada → la firma.
  3. Quien recibe recalcula el hash y descifra la firma con la pública: si coincide, es auténtico e íntegro.

Uso real: actualizaciones de software (el sistema operativo verifica la firma del paquete), paquetes firmados, JWT (el servidor firma el token y así detecta modificaciones), certificados TLS y commits de Git:

# Firmar commits verificables en GitHub
  git commit -S -m "Cambio"
  git log --show-signature

Cifrar o firmar son cosas distintas: cifrar protege la confidencialidad; firmar protege la autenticidad e integridad. Se pueden combinar: firma y luego cifra.

Gestión de secretos

Una clave criptográfica no protege nada si vive en el repositorio. Reglas elementales:

  • Nada de credenciales en el código fuente — usa variables de entorno o un gestor
  • Autorotación de clave: planifica qué hacer cuando (no «si») se filtra una
  • El .env se ignora en Git (.gitignore) y se documenta un .env.example sin valores reales.
  • Los secretos de producción no comparten valores con desarrollo.
# Comprobar si una clave quedó pegada en la historia de Git
  git log --all -S 'AKIA' --oneline     # AWS acceso
  git log --all -S 'API_KEY' --oneline

Comandos de verificación

Herramientas que ya tienes instaladas para trabajar con hash y claves:

# Verificar la integridad de un archivo descargado
  sha256sum archivo.iso

# Generar una sal o aleatorio criptográfico (para seeds, IDs de sesión)
  openssl rand -hex 32
  openssl rand -base64 24

# Generar una clave de API fuerte para tus proyectos
  openssl rand -hex 32 | cut -c1-32

# Comprobar qué hash usa un archivo de contraseñas de sistema Linux
  sudo cat /etc/shadow | head -1   # $6$ = SHA-512 con sal; $y$ = yescrypt

Y para la conexión HTTPS, sigue en Ciberseguridad · Verificar certificados TLS.

Prueba solo herramientas de evaluación sobre tus propios sistemas o con autorización explícita. Más comprobaciones del lado web en Seguridad · Comprobar tu propia web.

Buenas prácticas

  • No inventes esquemas criptográficos: usa libs revisadas como crypto, openssl o sodium.
  • Contraseñas: bcrypt o argon2id con sal y factor de coste generoso.
  • Distingue objetivos: hash para verificar, cifrado para ocultar, firma para autenticar.
  • AES con modo GCM (autenticado) si toca cifrar con librerías propias.
  • Claves de 2048+ bits en RSA, preferible Ed25519 para uso nuevo.
  • Los secretos fuera del repo; rota lo que se haya filtrado, no «borres» en el próximo commit.
