Patrones de diseño

Un patrón de diseño es una solución reutilizable a un problema que aparece una y otra vez al diseñar software. No es código copiable ni un framework: es un nombre y una estructura que los desarrolladores reconocen. Usarlos bien mejora la comunicación y la mantenibilidad; usarlos por moda, la empeora.

En 5 puntos

  • Un patrón describe problema + solución + consecuencias, no implementación.
  • Se agrupan en creacionales (cómo se crean objetos), estructurales (cómo se componen) y de comportamiento (cómo interactúan).
  • Los más usados: Factory, Adapter, Decorator, Observer, Strategy, Facade.
  • Un patrón es bueno cuando resuelve un problema real; aplicado sin necesidad es sobre-ingeniería.
  • Los patrones se combinan con los principios SOLID y con la composición.

¿Qué es un patrón?

Popularizados por el libro «Design Patterns» (Gang of Four, 1994), los patrones describen soluciones probadas a problemas recurrentes de diseño orientado a objetos. Cada patrón incluye: nombre, problema, solución, estructura y consecuencias. No son algoritmos ni bibliotecas; son vocabulario compartido («usa un Observer aquí»).

Los patrones no son exclusivos de OOP; también existen en funcional (functors, monads) y en arquitectura (MVC, CQRS). Aquí nos centramos en los clásicos de OOP.

Patrones creacionales

Controlan cómo se crean los objetos, desacoplando la creación del uso.

Factory Method

Delega la creación a subclases o funciones, para que el cliente no dependa de la clase concreta.

function crearLogger(tipo) {
  if (tipo === 'archivo') return new FileLogger();
  if (tipo === 'consola') return new ConsoleLogger();
  throw new Error('Tipo desconocido');
}
const log = crearLogger('consola');
log.info('hola');

Builder

Construye objetos complejos paso a paso, útil cuando hay muchos parámetros opcionales.

class PizzaBuilder {
  constructor() { this.ingredientes = []; }
  conQueso() { this.ingredientes.push('queso'); return this; }
  conPepperoni() { this.ingredientes.push('pepperoni'); return this; }
  build() { return new Pizza(this.ingredientes); }
}
const pizza = new PizzaBuilder().conQueso().conPepperoni().build();

Singleton (con reservas)

Garantiza una única instancia. Útil para configuración o pools, pero dificulta tests y oculta dependencias. Preferir inyección de dependencias.

Patrones estructurales

Componen clases y objetos para formar estructuras mayores.

Adapter

Convierte la interfaz de una clase en otra que el cliente espera. Útil para integrar librerías externas.

class ApiVieja { obtenerUsuario(id) { /* ... */ } }
class UsuarioAdapter {
  constructor(api) { this.api = api; }
  get(id) { return this.api.obtenerUsuario(id); } // nueva interfaz
}

Decorator

Añade responsabilidades a un objeto dinámicamente, sin subclases. Ejemplo: añadir logging a una función.

function conLog(fn) {
  return function (...args) {
    console.log('llamando con', args);
    return fn(...args);
  };
}
const sumarLog = conLog((a, b) => a + b);

Facade

Provee una interfaz simple a un subsistema complejo (p. ej. un módulo que oculta varios servicios).

Patrones de comportamiento

Definen cómo se asignan responsabilidades y se comunican los objetos.

Observer

Un sujeto notifica a sus observadores cuando cambia su estado. Base de eventos y reactividad.

class EventEmitter {
  constructor() { this.listeners = {}; }
  on(evento, cb) { (this.listeners[evento] ||= []).push(cb); }
  emit(evento, data) { (this.listeners[evento] || []).forEach(cb => cb(data)); }
}
const bus = new EventEmitter();
bus.on('msg', (m) => console.log('recibido', m));
bus.emit('msg', 'hola');

Strategy

Define una familia de algoritmos intercambiables. Evita switch gigantes.

const estrategias = {
  rapido: (a, b) => a + b,
  seguro: (a, b) => a + b + validacion(a, b),
};
function calcular(a, b, modo) {
  return estrategias[modo](a, b);
}

Command

Encapsula una petición como objeto, permitiendo deshacer/rehacer y colas de ejecución.

Cuándo NO usarlos

  • Cuando el problema no existe aún: no anticipes abstracciones.
  • Cuando una función o composición simple resuelve el caso.
  • Cuando el equipo no conoce el patrón: el código se vuelve opaco.
  • Cuando el patrón añade más indirección que valor.

«Design Patterns» advierte: los patrones describen cómo resolver, no cuándo. La decisión de aplicarlos es de diseño, no de catálogo.

Buenas prácticas

  • Empieza con el problema, no con el patrón.
  • Prefiere composición sobre herencia.
  • Usa patrones como vocabulario en revisiones y documentación.
  • Mantén los patrones pequeños y testeables.
  • Combina patrones con SOLID y con inyección de dependencias.

Errores comunes

Error Por qué está mal Qué hacer
Aplicar patrones «porque sí» Sobre-ingeniería: más clases, más indirección, menos claridad. Justifica cada patrón con un problema real.
Singleton para todo Estado global oculto, difícil de testear. Inyecta dependencias; reserva Singleton para recursos únicos.
Herencia profunda de patrones Acoplamiento frágil. Prefiere composición y delegación.
Confundir patrón con framework Se espera infraestructura que no existe. Un patrón es una idea, no una librería.
No documentar la intención El código parece arbitrario. Nombra el patrón en comentarios/PRs cuando aporte.
