Bases de datos

SQL y bases de datos relacionales

Una base relacional guarda los datos en tablas que se relacionan entre sí por claves. SQL es el lenguaje estándar para consultar y modificar esos datos, y sigue siendo una de las piezas más rentables de aprender: SQLite, PostgreSQL y MySQL hablan casi el mismo dialecto.

En 5 puntos

  • Todo son tablas (filas × columnas); las relaciones se expresan con claves primarias (PK) y externas (FK).
  • SELECT –FROM –WHERE –GROUP BY –HAVING –ORDER BY: ese es el esqueleto del 90 % de las consultas.
  • JOIN combina tablas por sus claves; INNER solo filas que coinciden, LEFT conserva todo lo de la izquierda.
  • Los índices aceleran las búsquedas al coste de escritura y espacio: se crean para lo que consultas más, no «por si acaso».
  • Las transacciones agrupan operaciones en bloque: o se cumplen todas (commit) o no se cumple ninguna (rollback).

Tablas, claves y relaciones

Cada tabla modela un tipo de entidad. Las columnas tienen un tipo (entero, texto, fecha…) y cada fila es un registro único identificado por su clave primaria. 

CREATE TABLE autores (
    id          INTEGER PRIMARY KEY,
    nombre      TEXT NOT NULL
  );

  CREATE TABLE articulos (
    id           INTEGER PRIMARY KEY,
    titulo       TEXT NOT NULL,
    autor_id     INTEGER REFERENCES autores(id),  -- clave externa: FK
    publicado    DATE,
    vistas       INTEGER DEFAULT 0
  );

La relación «un autor escribe muchos artículos» (1‑N) se refleja llevando autor_id en la tabla hija. Para las «varios a varios» (N‑M) es necesaria una tabla intermedia: 

CREATE TABLE articulo_etiquetas (
    articulo_id  INTEGER REFERENCES articulos(id),
    etiqueta_id  INTEGER REFERENCES etiquetas(id),
    PRIMARY KEY (articulo_id, etiqueta_id)
  );

Consultas básicas: SELECT y WHERE

SELECT titulo, vistas
    FROM articulos
    WHERE vistas > 100 AND publicado IS NOT NULL
    ORDER BY vistas DESC
    LIMIT 10 OFFSET 0;
  • WHERE filtra filas; no confundir con HAVING, que filtra tras agrupar.
  • NULL nunca es igual a nada: para él, usa IS NULL / IS NOT NULL.
  • LIKE 'a%' busca por prefijo (puede usar un índice); el % al inicio (LIKE '%a') hace lento el escaneo completo porque anula el índice.
  • El orden estándar de las cláusulas no es opcional: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

JOIN: combinar tablas

SELECT a.titulo, au.nombre AS autor
    FROM articulos a
    INNER JOIN autores au ON au.id = a.autor_id
    WHERE a.vistas > 100;
Tipo Qué devuelve
INNER JOINSolo filas que coinciden en ambas tablas.
LEFT JOINTodas las de la izquierda; si no hay pareja, columnas derechas = NULL.
RIGHT JOINLa simétrica del LEFT (menos común; se reordena y suele usar LEFT).
FULL OUTER JOINTodo de ambos lados, con NULL donde falte pareja.

Uso típico de LEFT JOIN: «todos los autores, incluso los que aún no tienen artículos»:

SELECT au.nombre, COUNT(a.id) AS total
    FROM autores au
    LEFT JOIN articulos a ON a.autor_id = au.id
    GROUP BY au.id;

La consulta triangular: JOIN demasiado grande con WHERE sobre columnas sin índice. Si algo «se cuelga», casi siempre es un JOIN sin índice o con SELECT * sobre millones de filas: mide con EXPLAIN.

Agregaciones: GROUP BY

SELECT au.nombre,
           COUNT(*)            AS articulos,
           AVG(a.vistas)       AS vistas_medias,
           MAX(a.publicado)    AS ultimo
    FROM articulos a
    INNER JOIN autores au ON au.id = a.autor_id
    GROUP BY au.id
    HAVING COUNT(*) >= 3
    ORDER BY vistas_medias DESC;
  • Funciones habituales: COUNT, SUM, AVG, MIN, MAX.
  • En SQL estricto, toda columna del SELECT fuera de una función debe estar en GROUP BY — o ser la clave de agrupación.
  • HAVING filtra grupos ya computados; WHERE filtra filas antes de agrupar (y es más barato).

INSERT, UPDATE, DELETE

INSERT INTO articulos (titulo, autor_id)
    VALUES ('SQL básico', 7)
    RETURNING id;                 -- PostgreSQL/SQLite: devuelve la fila nueva

  UPDATE articulos SET vistas = vistas + 1 WHERE id = 42;

  DELETE FROM articulos WHERE id = 42 AND autor_id = 7;

Un UPDATE o DELETE sin WHERE afecta a todas las filas de la tabla. Antes de ejecutarlo sobre producción, corre la versión SELECT con la misma condición: 

-- Comprueba qué fila(s) tocarías…
  SELECT id, titulo FROM articulos WHERE id = 42 AND autor_id = 7;
  -- …y solo entonces cambia el SELECT por UPDATE / DELETE.

Los INSERT/UPDATE/DELETE, siempre con consultas preparadas desde tu código (parámetros, jamás concatenación). El porqué está en Seguridad · Inyección SQL.

Índices

Un índice es una estructura ordenada (un B‑tree) que permite encontrar filas sin recorrer la tabla entera: es como el índice de un libro: 

CREATE INDEX articulos_autor_idx ON articulos (autor_id);
  CREATE INDEX articulos_vistas_idx ON articulos (vistas DESC);

  UNIQUE  INDEX articulos_titulo_uq  ON articulos (titulo);  -- también garantiza» unicidad
A favor En contra
Búsquedas, JOIN y ORDER BY por esas columnas, muchísimo más rápidosCada INSERT/UPDATE/DELETE debe actualizarlo
Los índices de FK y UNIQUE crean uno por defectoOcupan espacio en disco

Índice para joins sobre FK, para lo que hace ORDER BY o GROUP BY frecuente, y para columnas de pocos valores distintos (estado, tipo). No indexes columnas que casi se consultan en bloque completo o con LIKE '%…%'. 

-- PostgreSQL: el «plan» de ejecución de la consulta
  EXPLAIN ANALYZE
    SELECT * FROM articulos WHERE autor_id = 7;

  -- Ver los índices existentes
  \di articulos        -- psql
  .indexes articulos   -- sqlite3

Transacciones y ACID

Una transacción agrupa operaciones para que sean indivisibles. Si algo falla a mitad de camino, se deshace todo lo anterior (rollback): 

BEGIN;
    UPDATE cuentas SET saldo = saldo - 100 WHERE id = 1;
    UPDATE cuentas SET saldo = saldo + 100 WHERE id = 2;
    COMMIT;        -- solo si ambos pasos fueron bien
    -- en caso de excepción: ROLLBACK;

Las cuatro garantías que definen los sistemas de bases de datos convencionales (ACID):

  • Atomicidad — todo o nada.
  • Consistencia — las reglas (FK, tipos, restricciones UNIQUE) no se violan jamás.
  • Aislamiento — dos transacciones concurrentes no ven estados a medias.
  • Durabilidad — una confirmación (commit) sobrevive a un reinicio o corte de alimentación.

El aislamiento tiene niveles (READ UNCOMMITTED → SERIALIZABLE). El extensible REPEATABLE READ evita que dos lecturas de la misma transacción den resultados distintos; se ajusta con SET TRANSACTION ISOLATION LEVEL …. Pregúntate si distinto nivel es necesario (casi siempre el por defecto vale).

Comandos útiles

# Modelo cliente ligero para pruebas rápidas (SQLite viene sin servidor)
  sqlite3 test.db
    .tables             -- listar tablas
    .schema articulos   -- ver el CREATE TABLE
    .headers on         -- mostrar los nombres de columna
    .mode column        -- salida por columnas legible

  # PostgreSQL desde psql
  psql -U usuario -d base
    \dt                 -- tablas
    \d  articulos       -- estructura + índices
    \di articulos       -- solo índices

  # Copia de seguridad / restauración (PostgreSQL)
  pg_dump base > backup.sql
  psql base < backup.sql

Los comandos de cliente varían entre motores (\di solo en psql, .indexes solo en SQLite); lo único invariante es SQL estándar: SELECT, INSERT, UPDATE, DELETE, CREATE TABLE.

Buenas prácticas

  • Deja que las columnas se llamen igual en todo el proyecto (escoge snake_case y no lo cambies).
  • Nada de SELECT * en producción: pide las columnas que usarás; además facilita que la consulta resuelva de un índice (covering).
  • Nunca interpolares valores del usuario en una consulta: siempre consultas preparadas.
  • Refuerza las restricciones: FK, NOT NULL, UNIQUE… para que el motor defienda la integridad, no tu código.
  • Medición antes de índices: mira los planes con EXPLAIN y crea solo los evidenciados.
  • Migraciones versionadas (archivos .sql en el repo) y nada de modificar tablas a mano en producción.
  • Respaldo (backup) automático programado: la base de la tranquilidad de un programador.
