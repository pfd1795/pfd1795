Arquitectura y diseño de software

Cliente-servidor y APIs

Toda aplicación web moderna habla —de un modo u otro— con un backend vía HTTP. Aquí se explica el modelo cliente-servidor (quién hace qué), cómo diseñar una API REST legible y cómo demuestran su identidad los clientes: sesiones, tokens JWT y OAuth2.

En 5 puntos

  • El cliente manda peticiones; el servidor responde. Todo lo demás (estado de la sesión, caché) vive entre ambas.
  • Una API REST expone recursos en URLs («sustantivos») y usa métodos HTTP como verbos: GET/POST/PUT/PATCH/DELETE.
  • Sin estado (stateless): cada petición lleva todo lo necesario para entenderse, por eso se necesita un mecanismo de autenticación.
  • Tres formas de autenticar: sesión + cookie, token JWT o delegar en un servicio (OAuth2/OIDC).
  • El contrato con clientes externos se documenta y versiona; los códigos de error son parte del contrato.

El modelo cliente-servidor

El cliente pide algo (una página, un dato, una acción) y el servidor aporta la respuesta con la lógica, los datos y las garantías (persistencia, integridad). Hablan por el protocolo que elijas, casi siempre HTTP sobre TLS:

«Sin estado» no significa «sin memoria»: significa que no se guarda en el servidor la conversación. Lo que necesite persistir se guarda en la BD; lo que identifique al usuario viaja en cada petición (cookie o token).

APIs REST: recursos y métodos

REST es un estilo de arquitectura: cada concepto de negocio es un recurso identificado con una URL estable, y los métodos HTTP expresan las operaciones:

Recurso Operación Método · ruta
Listar artículosLectura de la colecciónGET /api/articulos
Detalle de un artículoLectura puntualGET /api/articulos/42
Crear artículoCreaciónPOST /api/articulos
Reemplazar artículoActualización completaPUT /api/articulos/42
Actualizar parte del artículoActualización parcialPATCH /api/articulos/42
Eliminar artículoBorradoDELETE /api/articulos/42
Acción con semántica propiaComando, no recursoPOST /api/articulos/42/publicar (aceptable como excepción)
  • Nombres en plural, minúsculas y sin verbos en la ruta; con / como separador jerárquico.
  • Los verbos van en el método, no en la URL: GET /api/borrarArticulo?id=42 es una señal de diseño impropia.
  • Los filtros, paginación y orden van en el query string: ?page=2&limit=20&sort=-fecha.
  • Las búsquedas complejas se modelan como sus propios recursos (GET /api/arts/busqueda?q=…) o como POST a un endpoint de consulta.
# Prueba manual de una API con curl (el cliente la llamaría con fetch)
  curl -s https://api.ejemplo.dev/api/articulos?limit=2 \
    -H 'Accept: application/json'

  curl -s -X POST https://api.ejemplo.dev/api/articulos \
    -H 'Content-Type: application/json' \
    -H 'Authorization: Bearer eyJhbGci...' \
    -d '{"titulo":"Nuevo artículo","cuerpo":"..."}'

JSON: el formato de intercambio

JSON es texto estructurado: objetos entre llaves, listas entre corchetes, y valores que pueden ser cadena, número, booleano, null u otra estructura anidada: 

{
    "page": 1, "limit": 20, "total": 143,
    "items": [
      { "id": 42, "titulo": "HTTP y navegador web", "tags": ["http", "web"] }
    ]
  }
  • Las claves suelen ir en camelCase (o snake_case, elige un estilo y sé coherente en toda la API).
  • Las fechas se mandan como ISO 8601: "2026-11-06T10:30:00Z" (UTC y con zona explícita).
  • Mapeo JS ofrecido de fábrica en JSON.parse y JSON.stringify; fetch ya trae .json().
  • Cuidado con los valores tipo money en floats: si la precisión importa, usa enteros en unidades menores (céntimos).
const respuesta = await fetch('/api/articulos?limit=20');
  if (!respuesta.ok) {
    throw new Error('HTTP ' + respuesta.status);
  }
  const { page, total, items } = await respuesta.json();

Códigos de estado y gestión de errores

Códigos significativos para una API (resumidos de Redes · HTTP):

Código Cuándo usarlo en una API
200 OKÉxito en GET/PUT/PATCH/DELETE
201 CreatedRecurso creado por POST; Location apunta al nuevo recurso
204 No ContentÉxito sin cuerpo que devolver (DELETE)
400 Bad RequestPetición mal formada o campos inválidos
401 UnauthorizedSin autenticar (falta un credencial o ya no es válido)
403 ForbiddenAutenticado, pero sin permiso
404 Not FoundEl recurso no existe (o no se revela por seguridad)
409 ConflictChoque de estado (email ya registrado)
422 Unprocessable EntitySintaxis válida pero semánticamente rechazable (campos vacíos)
429 Too Many RequestsRate limit
500Error no controlado; no debe estar en producción con detalles

El cuerpo del error debería ser predecible; la propuesta común es RFC 9457 (Problem Details): type, title, status, detail. Al menos, incluye un identificador de trazabilidad.

403 vs 404: si revelar la existencia del recurso es un dato sensible (organizaciones privadas), contesta 404.

Autenticación: sesión, JWT y OAuth2

Quién es el usuario que hace la petición; tres enfoques dominantes:

Mecanismo Cómo funciona Cuándo conviene
Sesión + cookie El servidor guarda estado («sesión n.º 15») y entrega una cookie; el cliente la reenvía automáticamente Sitios con front y back en el mismo proyecto; máxima capacidad de revocación
Token JWT El servidor firma un token auto-verificable; el cliente lo envía en Authorization: Bearer … en cada petición APIs públicas, móvil, servicios entre sí; identidad sin estado del servidor
OAuth2 / OIDC Delega la autenticación a un proveedor (Google, GitHub): el servidor se fía del token emitido por él “Iniciar sesión con…”, integraciones entre organizaciones, SSO

La autenticación responde «¿quién eres?». La autorización responde «¿qué puedes hacer?» (roles, permisos por recurso). Ambas se necesitan.

JWT por dentro

Un JSON Web Token es una cadena cabecera.payload.firma, cada parte en Base64URL: 

eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxNSIsInJvbCI6IkFETUlOIn0 . 1b4ad1c5
    { "alg": "HS256" }     { "sub": "15", "rol": "ADMIN" }   HMAC-SHA256(key, cabecera+payload)
  • Cabecera: algoritmo de firma.
  • Payload: claims (subject, expiration, roles). Se puede leer sin clave; no viaja nada secreto dentro.
  • Firma: el servidor la verifica con su clave privada/ el secreto compartido; cualquier modificación del payload la rompe.

El payload «expira» en el claim exp, pero eso no era magia: el servidor comprueba el dato al validar. Para revocar un token es necesario mantener una lista de revocación de tokens (por ejemplo, por sesión) o usar expiraciones cortas + refresh token. 

# Decodificar el payload de un JWT (no verifica firmas: solo interpreta)
  echo 'eyJzdWIi...payload...' | base64 --decode

Elegir la pieza correcta

Antes de diseñar tu backend e integrares, responde en orden:

  1. ¿Qué recursos existen y quién lee/edita cada uno?
  2. ¿Quién es el cliente (tu propio frontend, apps, terceros)? Eso condiciona CORS, auth y versionado.
  3. ¿Necesitas tiempo real? (WebSockets y SSE son otra familia de protocolos por encima de HTTP.)
  4. ¿Qué dominio de negocio se entienden intuitivamente y qué flujo se documenta en cada endpoint? (contrato y ejemplos).

Un buen predictor de sistemas sencillos: cada endpoint responde una intención; los clientes lo reproducen sin sorpresas. La base de tu API son las reglas de negocio, no la tecnología elegida.

Buenas prácticas

  • Devuelve códigos de estado correctos: son contrato, no decoración.
  • No expongas claves ni IDs internos que no deban viajar; valida y sanitiza en el servidor (Seguridad).
  • Paginación siempre en la colección, desde el día uno (la lista de 10 registros crecerá).
  • Idempotencia de PUT/DELETE: repetir la misma petición no duplica efectos.
  • Versiona la API en la ruta (/v1/) si hay clientes externos que van a depender de ella.
  • Nunca registres credenciales en los logs: ningún filtro posterior justifica lo que ya se filtró.
