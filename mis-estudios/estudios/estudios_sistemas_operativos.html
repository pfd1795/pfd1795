Fundamentos de computación

Sistemas operativos

Un sistema operativo (SO) es el programa que se ejecuta siempre que el ordenador está encendido. Gestiona el hardware, reparte los recursos entre los programas y ofrece una interfaz para que las aplicaciones pidan lo que necesitan sin tocar el hardware directamente. Entender cómo lo hace explica por qué un proceso se bloquea, por qué la memoria «se acaba» o por qué un programa no puede abrir un archivo.

En 5 puntos

  • El SO es un intermediario: las apps no acceden al hardware; piden servicios al kernel mediante llamadas al sistema.
  • Un proceso es un programa en ejecución con su propio espacio de memoria; un hilo es una unidad de ejecución dentro de él.
  • La CPU se reparte con un planificador (Round Robin, prioridades…); el cambio de contexto guarda y restaura el estado.
  • La memoria virtual da a cada proceso la ilusión de tener toda la RAM para sí; el SO traduce direcciones y pagina a disco.
  • La concurrencia exige sincronización (mutex, semáforos) para evitar carreras y bloqueos (deadlock).

¿Qué es un sistema operativo?

El SO cumple tres funciones principales:

  • Abstracción del hardware: ofrece archivos, procesos, sockets y memoria virtual en lugar de puertos, registros y sectores de disco.
  • Gestión de recursos: decide quién usa la CPU, la RAM, el disco y la red, y en qué orden.
  • Aislamiento y protección: un proceso no puede leer la memoria de otro ni acceder a archivos sin permiso.

La parte central es el kernel, que se ejecuta en modo privilegiado. El resto (shell, servicios, aplicaciones) corre en modo usuario. Esta separación es la base de la seguridad y la estabilidad: si una app falla, el kernel sigue vivo.

El SO no es solo la interfaz gráfica. En un servidor Linux sin entorno gráfico, el SO sigue siendo completo: kernel + servicios + shell.

Procesos y hilos

Un proceso es un programa en ejecución: código, datos, pila, registros y un bloque de control (PCB) con su estado. Cada proceso tiene su propio espacio de direcciones virtual, por lo que un fallo en uno no corrompe a los demás.

Un hilo (thread) es una unidad de ejecución dentro de un proceso. Varios hilos comparten el código y la memoria del proceso, pero cada uno tiene su propia pila y registros. Crear un hilo es más barato que crear un proceso.

Estados típicos: Nuevo, Listo, En ejecución, Bloqueado (esperando E/S o un recurso) y Terminado. El planificador mueve procesos entre Listo y En ejecución.

Planificación de la CPU

Con una sola CPU (o pocos núcleos) y muchos procesos listos, el SO decide el orden y el tiempo de ejecución. Objetivos: equidad, tiempo de respuesta, rendimiento y uso de CPU.

Algoritmo Idea Ventaja / inconveniente
FIFO (FCFS)El primero en llegar se ejecuta hasta terminar.Simple; sufre el efecto convoy (un proceso largo bloquea a los cortos).
SJFEl más corto primero.Minimiza tiempo de espera; requiere conocer la duración (no siempre posible).
Round RobinTurnos de tiempo fijo (quantum) a cada proceso.Buen tiempo de respuesta; mucho cambio de contexto si el quantum es pequeño.
PrioridadesEl de mayor prioridad ejecuta primero.Flexible; riesgo de inanición (starvation) de los de baja prioridad.
MultinivelVarias colas con políticas distintas.Equilibra interactivos y por lotes; más complejo de ajustar.

En sistemas interactivos (escritorio, web) se busca baja latencia de respuesta; en por lotes (batch), máximo rendimiento. Linux combina CFS (Completely Fair Scheduler) con prioridades dinámicas.

Memoria virtual

Cada proceso ve un espacio de direcciones virtual grande y contiguo, aunque la RAM física sea pequeña y compartida. El SO traduce direcciones virtuales a físicas mediante tablas de páginas; las páginas que no caben en RAM se guardan en disco (swap).

  • Paginación: la memoria se divide en páginas (virtual) y marcos (físico), del mismo tamaño (p. ej. 4 KiB).
  • TLB: caché de traducciones para no consultar la tabla de páginas en cada acceso.
  • Page fault: acceso a una página no presente en RAM; el SO la carga desde disco (costoso).
  • Thrashing: si faltan páginas constantemente, el sistema pasa más tiempo paginando que ejecutando.

La memoria virtual también da aislamiento: un proceso no puede acceder a la memoria de otro porque sus tablas de páginas son distintas. Por eso un puntero «válido» en un proceso no sirve en otro.

Sistema de archivos

El SO organiza los datos en archivos y directorios, con metadatos (permisos, tamaño, fechas). Internamente suele usar inodos (metadatos) y bloques de datos; los directorios son archivos especiales que mapean nombres a inodos.

  • Permisos: lectura/escritura/ejecución para propietario, grupo y otros (modelo Unix: rwx).
  • Journaling: registro de cambios antes de aplicarlos, para recuperarse tras un corte de luz.
  • Enlaces: duros (mismo inodo, otro nombre) y simbólicos (archivo que apunta a una ruta).
  • Montaje: un sistema de archivos se «monta» en un directorio y pasa a formar parte del árbol.

Llamadas al sistema y modos

Una llamada al sistema (syscall) es el mecanismo por el que un programa en modo usuario pide un servicio al kernel: abrir un archivo, crear un proceso, enviar datos por red. El hardware cambia a modo privilegiado, ejecuta el servicio y devuelve el control. 

// Ejemplo conceptual en C/POSIX
int fd = open("datos.txt", O_RDONLY);   // syscall
char buf[1024];
ssize_t n = read(fd, buf, sizeof(buf)); // syscall
close(fd);                              // syscall

Cada syscall tiene coste (cambio de modo y validaciones). Por eso las bibliotecas agrupan lecturas pequeñas en buffers (stdio) y los servidores usan E/S no bloqueante o asíncrona.

Concurrencia y sincronización

Cuando varios hilos o procesos acceden a datos compartidos, pueden interferir (condición de carrera). La sincronización coordina el acceso:

  • Mutex: bloqueo mutuamente excluyente; solo un hilo entra a la sección crítica.
  • Semáforo: contador que permite hasta N hilos simultáneos; útil para pools de recursos.
  • Variable de condición: espera a que se cumpla una condición (p. ej. «hay datos en la cola»).
  • Deadlock: dos o más procesos se esperan mutuamente. Condiciones necesarias (Coffman): exclusión mutua, posesión y espera, no apropiación y espera circular.
// Patrón productor-consumidor (pseudocódigo)
mutex.lock();
while (cola.vacia()) condicion.wait(mutex);
item = cola.sacar();
mutex.unlock();
procesar(item);

Buenas prácticas

  • Usa procesos/hilos con propósito claro; no crees hilos «por si acaso».
  • Protege todo dato compartido con la sincronización adecuada; minimiza la sección crítica.
  • Prefiere estructuras sin bloqueo cuando sea posible (colas concurrentes, canales).
  • Cierra descriptores de archivo y libera memoria; evita fugas de recursos.
  • Maneja señales y códigos de error de las syscalls; no ignores EINTR ni ENOMEM.
  • Para E/S intensiva, considera E/S no bloqueante o asíncrona en lugar de un hilo por conexión.

Errores comunes

Error Por qué está mal Qué hacer
Acceder a datos compartidos sin sincronización Carreras de datos: resultados inconsistentes y difíciles de reproducir. Protege con mutex/semáforo; usa herramientas de detección (ThreadSanitizer).
Bloquear con un mutex y luego esperar otro recurso Puede generar deadlock si otro hilo hace lo inverso. Orden fijo de adquisición de bloqueos; o usa trylock con reintento.
Crear un hilo por cada conexión de red Agota memoria y tiempo de CPU en cambios de contexto. Usa pools de hilos o E/S asíncrona (epoll/kqueue/io_uring).
Ignorar el valor de retorno de syscalls Errores silenciosos (disco lleno, permisos) que corrompen datos. Comprueba siempre el retorno y registra el error (errno).
Asumir que la memoria virtual es «gratis» Page faults y swap degradan el rendimiento (thrashing). Mide el uso real; evita patrones de acceso aleatorio masivo.
