Herramientas de desarrollo

Empaquetado y despliegue

Que funcione en tu máquina es solo el principio. Empaquetar convierte el código en un artefacto reproducible; desplegar lo pone a disposición de otras personas sin que el proceso dependa de quién lo ejecute.

En 5 puntos

  • Empaquetar es producir un artefacto (un directorio, un archivo comprimido o una imagen de contenedor) que contiene todo lo necesario para ejecutar la aplicación.
  • Un build debe ser reproducible: las mismas entradas producen siempre el mismo resultado, sin depender del equipo donde corra.
  • Las variables de entorno separan la configuración del código; los secretos nunca se escriben en el repositorio.
  • Docker empaqueta la aplicación con su entorno; una imagen es inmutable y un contenedor es una instancia en ejecución de esa imagen.
  • CI/CD automatiza la verificación y la publicación: cada cambio pasa por las mismas pruebas y llega a producción de forma predecible.

Qué significa empaquetar y desplegar

Durante el desarrollo ejecutas el código directamente: abres un archivo, lanzas un servidor local y ves el resultado al instante. En producción nadie tiene por qué tener instaladas las mismas herramientas ni las mismas versiones. Por eso se separan dos momentos.

Empaquetar es transformar el código fuente en un artefacto: un directorio con archivos estáticos, un archivo comprimido, un paquete npm o una imagen de contenedor. Ese artefacto es autocontenido y se puede mover de un entorno a otro.

Desplegar es tomar ese artefacto y ponerlo a funcionar en el entorno de destino: subirlo a un servidor, crear los contenedores, aplicar las migraciones y dejar la aplicación respondiendo peticiones.

La frontera Importante entre ambos es la reproducibilidad. Si el despliegue vuelve a compilar el código con una versión distinta de las dependencias, ya no estás publicando lo que probaste: estás probando una cosa y publicando otra.

El proceso de build

Un build reúne las dependencias, transforma el código y genera los archivos finales. En una aplicación web moderna puede incluir varias tareas:

  • Instalar dependencias a partir de un archivo de bloqueo (package-lock.json, pnpm-lock.yaml, requirements.txt fijado).
  • Compilar o transpilar: TypeScript a JavaScript, JSX a llamadas a funciones, Sass a CSS.
  • Agrupar y minificar (bundling): juntar módulos y reducir tamaño para que el navegador descargue menos archivos.
  • Procesar recursos: optimizar imágenes, copiar fuentes y resolver rutas de assets.
  • Generar el manifiesto de versión, con el hash del commit y la fecha de compilación, para saber qué está desplegado.
npm ci                  # instala exactamente lo del lockfile
npm run test            # falla el build si las pruebas fallan
npm run build           # genera el directorio dist/
ls -lh dist/            # inspecciona el artefacto resultante

Usa npm ci (o el equivalente de tu gestor) en automatización: respeta el archivo de bloqueo y falla si cambió. npm install puede resolver versiones distintas en cada ejecución.

Variables de entorno y secretos

La misma aplicación necesita valores distintos según dónde se ejecute: la URL de la API, el puerto, las credenciales de la base de datos o el modo de depuración. Esos valores se leen de variables de entorno, no se escriben en el código. 

DATABASE_URL=postgres://user:pass@localhost:5432/app
API_BASE_URL=https://api.ejemplo.com
NODE_ENV=production
LOG_LEVEL=info

En local se suelen cargar desde un archivo .env que nunca se sube al repositorio; en producción las inyecta la plataforma o el orquestador. El código solo conoce el nombre de la variable: 

const apiUrl = process.env.API_BASE_URL;
if (!apiUrl) {
  throw new Error('Falta API_BASE_URL');
}

Un archivo .env.example con los nombres y valores de ejemplo sí se versiona: documenta qué hay que configurar sin exponer credenciales reales. Añade .env al .gitignore desde el primer commit.

Hay una distinción importante en aplicaciones frontend: todo lo que se incluye en un bundle de JavaScript es público, aunque la variable se llame SECRET_KEY. Los secretos reales deben vivir solo en el servidor.

Contenedores con Docker

Un contenedor empaqueta la aplicación junto con su entorno de ejecución: sistema base, dependencias del sistema, librerías y código. Así el servidor solo necesita Docker, en lugar de una lista exacta de versiones instaladas a mano.

Dos conceptos que conviene no confundir: la imagen es una plantilla inmutable construida desde un Dockerfile; el contenedor es una instancia en ejecución de esa imagen. 

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY dist/ ./dist/
ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "dist/server.js"]

El orden de las instrucciones importa porque cada una crea una capa que se guarda en caché. Copiar primero los archivos de dependencias permite reutilizar la capa de npm ci cuando solo cambia el código. 

docker build -t mi-app:1.4.0 .
docker run --rm -p 3000:3000 --env-file .env mi-app:1.4.0

Para aplicaciones con varios servicios (API, base de datos, caché) se usa docker-compose.yml, que describe la red, los volúmenes y las variables de cada servicio en un solo archivo.

Etiqueta las imágenes con una versión o el hash del commit, no solo latest. Sin una etiqueta única no puedes saber qué versión está corriendo ni volver a ella.

Integración y entrega continua (CI/CD)

La integración continua ejecuta automáticamente las comprobaciones cada vez que alguien abre un cambio: formateo, linting, pruebas y build. La entrega continua lleva ese artefacto ya verificado a un entorno, y la implementación continua lo publica en producción sin intervención manual. 

name: deploy
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

La clave es que el mismo artefacto se promueva entre entornos: el paquete que pasó las pruebas es el que se sube a producción. Recompilar en cada entorno abre la puerta a diferencias sutiles.

Proteger la rama principal y exigir que las comprobaciones pasen antes de fusionar convierte la CI en una red de seguridad: el error se detecta cuando el cambio es pequeño, no días después.

Estrategias de publicación

La forma de publicar depende del tipo de aplicación. Lo importante es que el mecanismo sea repetible y que exista una forma de volver atrás.

  • Sitios estáticos: se sube el directorio dist/ a un hosting de archivos (GitHub Pages, Netlify, Cloudflare Pages). No hay servidor que mantener; la plataforma se encarga de la caché y del HTTPS.
  • Aplicaciones con servidor: se publica la imagen en un registro y se actualiza el contenedor en el servidor o en un orquestador, normalmente detrás de un proxy inverso como nginx.
  • Plataformas como servicio (PaaS): la plataforma recibe el código o la imagen y gestiona el entorno de ejecución, el escalado y también las variables de entorno.
  • Funciones sin servidor: se despliega cada función por separado y el proveedor la ejecuta bajo demanda. El artefacto suele ser un archivo comprimido.

Para reducir riesgos se usan despliegues blue-green (dos versiones conviven y se cambia el tráfico de una a otra) o canario (una pequeña parte del tráfico va a la versión nueva). Ambas estrategias permiten detectar problemas antes de afectar a todo el mundo y facilitan la vuelta atrás.

Buenas prácticas

  • Fija las versiones de las dependencias con un archivo de bloqueo y usa instalación estricta en automatización.
  • Construye una sola vez y promueve el mismo artefacto entre entornos.
  • Trata la configuración como datos externos: variables de entorno, nunca constantes en el código.
  • Versiona la definición de la infraestructura y del despliegue en el repositorio.
  • Haz que el despliegue sea idempotente: ejecutarlo dos veces debe dejar el mismo estado.
  • Registra versión, hash del commit y hora de cada publicación.
  • Comprueba la salud de la aplicación después de publicar con una ruta de /health.
  • Prepara siempre la vuelta atrás antes de pulsar el botón de publicar.

Errores comunes

  • Confiar en npm install en lugar del archivo de bloqueo: el build deja de ser reproducible.
  • Subir un archivo .env con credenciales reales al repositorio.
  • Incluir secretos en el bundle frontend, donde cualquiera puede leerlos.
  • Recompilar en producción y publicar código distinto del que pasó las pruebas.
  • Usar imágenes latest: una reforma del mismo nombre cambia lo que se ejecuta.
  • Publicar sin una comprobación de salud ni un plan de vuelta atrás.
  • Mezclar migraciones de base de datos con el arranque de la aplicación sin controlar el orden.

Si algo funciona en local pero no en producción, compara primero tres cosas: versión de las dependencias, variables de entorno y versión del entorno de ejecución. Casi siempre la diferencia está ahí.
