Security

Cryptography basics

Cryptography makes data unintelligible to anyone without the key. As a programmer you will not invent algorithms — and it is best that you do not try — but you do need to know which tool to choose in each case: hash to verify, encryption to hide, signature to authenticate.

Hash and encryption: not the same thing

The most common confusion in security. They serve opposite purposes:

Characteristic Hash Encryption
Is it reversibleNo: one-way only (impossible to reverse)Yes: decrypt with the key
ReturnsA fixed-size «fingerprint»Roughly the same size as the original
PurposeVerify integrity or identityHide the content
Uses a keyNo (in basic use)Always
Example usePasswords, checksums, deduplicationTLS, disks, encrypted databases

«Encrypting passwords» is a classic mistake: if the server holds the key, an attacker who steals it decrypts them all. Passwords are hashed with a salt. (See Storing passwords.)

Hash functions

A hash turns any input into a fixed-length string, deterministically: the same input always gives the same output, but the input cannot be deduced from the output. Changing a single bit of the original completely changes the hash (avalanche effect).

  • SHA-256 / SHA-3: the recommended ones today.
  • MD5 and SHA-1: broken for security (only useful for compatibility checksums).
  • A collision (two different inputs, same hash) is theoretically possible; in SHA-256 it is computationally infeasible.
echo -n "pfd1795" | sha256sum
  # b94d5a...  (64 hexadecimal characters = 256 bits)

Typical use: check that a downloaded file is identical to the original:

sha256sum ubuntu.iso
  # compare the result with the value published by the provider

Storing passwords

A user database must not store passwords, not even hashed with plain SHA-256: they are so fast that an attacker tries billions of passwords per second with graphics cards. You need hashes that are deliberately slow and salted:

Algorithm Comment
bcryptVery widespread; includes a salt and an adjustable cost factor.
argon2idWinner of the «Password Hashing» competition; recommended option today.
scryptSimilar, designed to resist specialised hardware (GPU/ASIC).
PBKDF2Acceptable, although the least protected of the list.
MD5 / SHA-1 / SHA-256 aloneNever for passwords.
 
// bcrypt: the "cost factor" makes the hash 2^cost times slower
  import bcrypt from 'bcryptjs';

  const hash = await bcrypt.hash(password, 12);      // on registration
  const ok = await bcrypt.compare(password, hash);   // on login

The resulting hash already includes the salt embedded:

$2a$12$R9h/cIPz0gi.URNNX3BkhO0qEHdZ8mG6bI7j1tXnSjW09pSmH8ED6
   |   |  |                       |
   |   |  |                       └ hash (with the salt inside)
   |   |  └ cost factor (2^12 iterations)
   |   └ bcrypt algorithm
   └ format prefix

The salt is a random value mixed with the password before hashing. It prevents two users with the same password from sharing a hash, and prevents the attacker from using precomputed tables (rainbow tables).

Symmetric encryption

The same key encrypts and decrypts. It is fast and works for any volume of data, but there is a logistical problem: how to get the key to the recipient without anyone intercepting it.

  • AES: the current standard (AES-128 or AES-256).
  • ChaCha20-Poly1305: preferable on mobiles for its efficiency (TLS 1.3 uses it too).
  • Old ones (DES, 3DES, RC4): replaced, do not use in new projects.
openssl enc -aes-256-cbc -salt -in secret.txt -out secret.enc
  openssl enc -d -aes-256-cbc -in secret.enc -out secret.txt

The mode matters as much as the algorithm: GCM (authenticated) is the default option; CBC modes without a MAC are vulnerable to tampering. In practice, use verified libraries and let them choose mode and padding.

Asymmetric encryption

It solves the symmetric problem with a key pair: what one encrypts, only the other decrypts. You distribute the public one to everyone; the private one never leaves your machine.

  • To receive messages: anyone encrypts with your public key; only you decrypt with the private one.
  • To prove identity: the private key signs; anyone verifies with the public one.
  • Current algorithms: RSA (minimum 2048 bits), ECDSA, Ed25519, X25519.
# Generate an SSH pair (ed25519 type, modern)
  ssh-keygen -t ed25519 -C "you@email.com"
  # id_ed25519     → private key (never share it)
  # id_ed25519.pub → public key (publish it on GitHub / servers)

On the web, HTTPS uses asymmetric only to establish the connection (exchange or agree on a key), and then encrypts everything else with symmetric, which is much faster. More details in Network security and TLS.

Digital signatures

A signature proves who issued the data and that it did not change since. You sign with the private key; anyone can verify with the public one:

  1. The hash of the document is computed.
  2. The hash is encrypted with the private key → the signature.
  3. The recipient recomputes the hash and decrypts the signature with the public key: if it matches, it is authentic and intact.

Real use: software updates (the operating system verifies the package signature), signed packages, JWT (the server signs the token and thus detects modifications), TLS certificates and Git commits:

# Verifiable signed commits on GitHub
  git commit -S -m "Change"
  git log --show-signature

Encrypting or signing are different things: encryption protects confidentiality; signing protects authenticity and integrity. They can be combined: sign and then encrypt.

Secret management

A cryptographic key protects nothing if it lives in the repository. Basic rules:

  • No credentials in source code — use environment variables or a manager
  • Key auto-rotation: plan what to do when (not «if») one leaks
  • .env is ignored in Git (.gitignore) and a .env.example without real values is documented.
  • Production secrets do not share values with development.
# Check whether a key ended up stuck in Git history
  git log --all -S 'AKIA' --oneline     # AWS access
  git log --all -S 'API_KEY' --oneline

Verification commands

Tools you already have installed to work with hashes and keys:

# Verify the integrity of a downloaded file
  sha256sum file.iso

  # Generate a salt or cryptographic randomness (for seeds, session IDs)
  openssl rand -hex 32
  openssl rand -base64 24

  # Generate a strong API key for your projects
  openssl rand -hex 32 | cut -c1-32

  # Check which hash a Linux system password file uses
  sudo cat /etc/shadow | head -1   # $6$ = SHA-512 with salt; $y$ = yescrypt

And for the HTTPS connection, continue in Network security · Verifying TLS certificates.

Test evaluation tools only on your own systems or with explicit authorisation. More checks on the web side in Security · Checking your own site.

Best practices

  • Do not invent cryptographic schemes: use reviewed libs such as crypto, openssl or sodium.
  • Passwords: bcrypt or argon2id with salt and a generous cost factor.
  • Distinguish goals: hash to verify, encrypt to hide, sign to authenticate.
  • AES with GCM mode (authenticated) if you must encrypt with your own libraries.
  • RSA keys of 2048+ bits, preferably Ed25519 for new use.
  • Secrets outside the repo; rotate what leaked, do not just «delete» it in the next commit.
