Linux y servidores

Un servidor Linux es un sistema pensado para estar encendido mucho tiempo, atender peticiones y hacerlo de forma predecible. Administrarlo consiste menos en memorizar comandos y más en saber qué proceso escucha, qué usuario lo ejecuta, dónde escribe sus registros y qué cambió justo antes de que algo fallara.

En 5 puntos

  • El kernel es el núcleo del sistema; una distribución añade gestor de paquetes, servicios y herramientas de administración.
  • Trabajar con el menor privilegio posible es la regla básica: usuario propio, sudo para lo necesario y acceso root por SSH desactivado.
  • systemctl controla servicios y journalctl lee sus registros; enable y start son acciones distintas.
  • Antes de culpar a la aplicación, comprueba red, disco, memoria, permisos y hora del sistema.
  • Toda intervención en producción necesita una idea clara de cómo comprobar el resultado y cómo volver atrás.

Qué significa administrar un servidor

Linux es el kernel y una distribución es ese kernel junto con bibliotecas, gestor de paquetes, servicios y herramientas: Debian, Ubuntu, Fedora, Alpine o Rocky, entre otras. Un servidor suele funcionar sin entorno gráfico: todo se hace por consola, de forma local o a través de una conexión remota.

Administrarlo implica mantener cuatro cosas bajo control: quién puede entrar, qué procesos se ejecutan, qué recursos consumen y qué ocurre cuando algo cambia. La mayoría de las incidencias se reducen a una de esas preguntas. Por eso conviene conocer el estado normal del sistema antes de tocarlo: cuántos servicios hay, cuánto disco se usa y qué registros aparecen en una mañana cualquiera.

La terminal es la herramienta de trabajo, pero este artículo no es un catálogo de comandos. Para navegación, archivos, permisos y tuberías, consulta Terminal y línea de comandos; aquí el foco está en lo que se hace en una máquina que presta un servicio a otras.

Sistema de archivos y configuración

Linux organiza todo en un único árbol que empieza en /. Saber qué hay en cada directorio evita editar el archivo equivocado y ayuda a encontrar la configuración de un servicio.

Ruta Contenido habitual
/etc Configuración del sistema y de los servicios.
/var/log Registros de aplicaciones y del sistema.
/home Directorios personales de los usuarios.
/srv Datos servidos por el propio sistema.
/usr Programas y bibliotecas instalados.
/proc Información del kernel y de los procesos, generada al leerla. 
ls -la /etc/nginx
cat /etc/os-release
df -h
find /var/log -maxdepth 1 -type f

Antes de modificar un archivo de configuración conviene copiarlo y saber cómo recargar el servicio. Muchas configuraciones tienen una orden de comprobación propia, como nginx -t, que valida el archivo antes de aplicarlo. Cambiar, comprobar y recargar es mejor que cambiar y reiniciar a ciegas.

Los archivos bajo /proc no son archivos normales: los genera el kernel al leerlos. No se editan. Si necesitas cambiar un parámetro del kernel, usa la interfaz prevista para ello y documenta el cambio.

Usuarios, grupos y sudo

Cada proceso pertenece a un usuario y a un grupo. Esa identidad decide qué archivos puede leer o escribir y qué acciones puede realizar. El usuario root tiene todos los permisos; el trabajo diario debe hacerse con un usuario normal y elevar privilegios solo para la orden concreta que lo necesita. 

whoami
id
sudo -l
passwd
getent group sudo

sudo permite ejecutar una orden como otro usuario, normalmente root, y deja constancia en los registros. No es lo mismo que iniciar sesión como root: mantiene una identidad auditada y limita el alcance de cada elevación. Conviene que cada persona tenga su propio usuario, así se puede revocar el acceso sin afectar a las demás.

Los datos de cuentas locales viven en /etc/passwd y los hashes de contraseñas en /etc/shadow, con permisos restringidos. En entornos grandes se usan directorios centralizados, pero la idea es la misma: una identidad por persona o servicio y privilegios mínimos.

  • Crear usuarios específicos para servicios que no necesitan login interactivo.
  • No compartir contraseñas: usar claves SSH y cuentas individuales.
  • Revisar periódicamente quién pertenece a los grupos con privilegios.
  • Evitar sudo en scripts que no necesitan elevación; reducir el alcance reduce el riesgo.

Servicios con systemd

En la mayoría de las distribuciones actuales, systemd es el iniciador del sistema y gestiona los servicios mediante unidades. Una unidad describe qué orden arranca, con qué usuario, en qué condiciones y qué hacer si termina de forma inesperada. 

systemctl status nginx
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx
sudo systemctl enable nginx
systemctl is-enabled nginx

start arranca el servicio ahora; enable hace que arranque en el próximo reinicio. Son decisiones independientes: una aplicación puede estar funcionando y no sobrevivir a un reinicio, o estar habilitada y detenida. Después de cambiar una unidad hay que recargar la configuración de systemd con sudo systemctl daemon-reload.

Los registros de las unidades se consultan con journalctl. Filtrar por servicio y por fecha es la forma más rápida de relacionar un fallo con un cambio. 

journalctl -u nginx -f
journalctl -u nginx --since '1 hour ago'
journalctl -p err --since today
systemctl list-units --type=service --state=failed

No todos los servicios son unidades de systemd. Un proceso lanzado a mano, un contenedor o una tarea en segundo plano pueden escapar a systemctl. Si un servicio no aparece ahí, busca primero cómo se arranca realmente.

Red y puertos

Un servidor ofrece servicios a través de puertos. Saber qué interfaz escucha cada proceso y qué reglas de cortafuegos permiten el tráfico evita muchos diagnósticos erróneos: una aplicación puede estar perfectamente arrancada y ser inalcanzable desde fuera. 

ip addr
ip route
ss -tulpn
curl -I http://127.0.0.1:3000
dig ejemplo.com

ss -tulpn lista los puertos en escucha y el proceso asociado. Es la primera comprobación cuando algo «no responde». Si el proceso escucha solo en 127.0.0.1, el tráfico externo no llegará aunque el cortafuegos esté abierto; si escucha en 0.0.0.0, conviene revisar quién puede alcanzarlo.

El cortafuegos se gestiona con herramientas como ufw o firewalld, según la distribución. Regla general: permitir el tráfico que hace falta y nada más. 

sudo ufw status
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw enable

Antes de abrir un puerto público conviene confirmar que el servicio está detrás de TLS o de un proxy que lo termina. Los conceptos de puertos, DNS y capas se explican con detalle en Redes y la configuración segura de certificados en TLS.

Acceso remoto con SSH

SSH es la puerta de entrada habitual a un servidor. Usa criptografía para autenticar y cifrar la sesión, y admite contraseñas o claves. Las claves son la opción preferida: son más difíciles de adivinar, se pueden revocar y permiten automatizar accesos sin guardar contraseñas. 

ssh-keygen -t ed25519
ssh-copy-id deploy@servidor
ssh deploy@servidor

La clave pública se copia al servidor y la privada se queda en la máquina cliente. Un archivo ~/.ssh/config permite dar nombres cortos a los servidores y fijar usuario, puerto y clave, de modo que no haya que repetirlos en cada conexión. 

Host produccion
  HostName 203.0.113.10
  User deploy
  IdentityFile ~/.ssh/id_ed25519

La configuración del demonio SSH vive normalmente en /etc/ssh/sshd_config. Tres ajustes habituales en un servidor expuesto son desactivar la autenticación por contraseña, prohibir el acceso directo como root y limitar qué usuarios o grupos pueden entrar. Después de cambiarlos se valida la configuración y se recarga el servicio, manteniendo abierta una sesión existente hasta comprobar que se puede volver a entrar. 

sudo sshd -t
sudo systemctl reload ssh

El nombre del servicio puede ser ssh o sshd según la distribución. Cierra la sesión antigua solo después de haber comprobado una conexión nueva con la configuración aplicada; de lo contrario puedes quedarte fuera.

Tareas programadas

Muchas operaciones de mantenimiento se repiten: copias, rotación de registros, limpieza de archivos temporales o comprobaciones de salud. cron es el mecanismo clásico y sigue siendo habitual; los temporizadores de systemd son la alternativa moderna cuando la tarea depende de un servicio o necesita registrar mejor su estado. 

0 3 * * * /usr/local/bin/backup.sh
*/15 * * * * /usr/local/bin/comprobar-salud.sh

Los cinco campos de una línea de cron indican minuto, hora, día del mes, mes y día de la semana. El primer ejemplo se ejecuta a las 03:00 cada día; el segundo, cada quince minutos. La hora se interpreta según la zona horaria del servidor, otro detalle que conviene comprobar cuando una tarea «no aparece» cuando se espera. 

timedatectl
crontab -l
sudo systemctl list-timers

Una tarea programada debe ser corta, escribir en un registro y avisar si falla. Si dos ejecuciones pueden solaparse, hace falta un bloqueo o un temporizador con Persistent=true. Y si la tarea modifica datos, su diseño debe incluir cómo verificar que terminó bien.

Paquetes y actualizaciones

El gestor de paquetes instala, actualiza y elimina software de forma consistente. En la familia de Debian se usa apt; en Fedora y Rocky, dnf. Mantener el sistema actualizado corrige vulnerabilidades, pero también puede cambiar comportamientos, así que en producción se planifica. 

sudo apt update
sudo apt upgrade
sudo apt install nginx
apt list --upgradable

update refresca el índice de paquetes disponibles; upgrade instala las versiones nuevas. Son pasos distintos. Para actualizaciones automáticas hay que decidir qué se instala sin revisión y qué requiere intervención; los parches de seguridad suelen automatizarse y los cambios de versión mayor, planificarse.

Antes de actualizar conviene saber si hay una copia y cómo se reinicia el servicio. Después, comprobar versión, registros y pruebas básicas. Si el servidor forma parte de un despliegue, la configuración debería estar en código y no solo en la máquina, para poder reconstruirla. Ese es el mismo principio que se aplica al construir imágenes en Docker y contenedores.

Diagnóstico inicial

Cuando un servidor falla, resiste la tentación de reiniciar de inmediato: el estado actual es evidencia. Empieza por acotar el problema y recoger datos en este orden.

  1. Qué cambió: despliegue, configuración, actualización o cambio de red recientes.
  2. Quién está conectado: who y last muestran sesiones y accesos previos.
  3. Recursos: uptime, free -h, df -h y top descartan CPU, memoria y disco lleno.
  4. Servicios: systemctl --failed y journalctl -p err señalan qué se ha roto.
  5. Red: ss -tulpn y curl comprueban que el puerto está abierto y responde.
  6. Hora: timedatectl explica certificados caducados y tareas que no disparan.
who
last -n 10
uptime
free -h
df -h
systemctl --failed
journalctl -p err --since '1 hour ago'

Anota los valores antes de intervenir. Si el disco está al 99 %, borrar registros sin entender por qué crecieron puede destruir la pista que explicaba el fallo. Después de aplicar una corrección, vuelve a ejecutar las mismas comprobaciones y deja constancia de qué cambió.

El diagnóstico es la misma disciplina que se aplica al código: reproducir, observar, cambiar una sola cosa y verificar. Las pruebas automatizadas de Testing automatizado y las canalizaciones de GitHub Actions y CI/CD sirven para que muchos de estos fallos se detecten antes de llegar al servidor.

Errores comunes

  • Usar start cuando se quería enable, y descubrir que el servicio no arranca tras un reinicio.
  • Editar un archivo de configuración sin copia ni comprobación previa.
  • Dejar sesiones root compartidas en lugar de usuarios individuales con sudo.
  • Cerrar la conexión SSH antes de comprobar que la nueva configuración permite volver a entrar.
  • Mirar solo el proceso de la aplicación cuando el puerto, el cortafuegos o el DNS son los culpables.
  • Ignorar la zona horaria al interpretar registros y tareas programadas.
  • Instalar paquetes sin control de versiones en la configuración y no poder reconstruir la máquina.
  • Reiniciar antes de recoger registros y perder la causa del fallo.

Un cambio en producción sin forma de verificarlo ni de deshacerlo no es una corrección, es una apuesta. Decide antes qué comprobarás y cuál será el plan de vuelta atrás.
