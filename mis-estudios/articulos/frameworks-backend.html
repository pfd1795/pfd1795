Frameworks

Frameworks de back-end

Un framework de back-end organiza el código que recibe peticiones, aplica reglas de negocio y devuelve respuestas. Sus herramientas pueden facilitar el enrutado, el manejo de errores, la validación y el acceso a datos, pero no sustituyen el diseño de la aplicación. Comprender el ciclo petición-respuesta y separar responsabilidades ayuda a construir servicios más claros y mantenibles.

En 5 puntos

  • El back-end procesa solicitudes, aplica lógica de negocio y responde a clientes como navegadores, aplicaciones móviles u otros servicios.
  • Un framework de servidor ofrece convenciones y herramientas para tareas comunes, como rutas y middleware.
  • Separar rutas, controladores, servicios y acceso a datos permite asignar responsabilidades y probar cada parte con más facilidad.
  • REST, GraphQL y WebSockets son enfoques distintos para comunicar sistemas; no son intercambiables en todos los casos.
  • La seguridad debe diseñarse en cada capa: validar entradas, controlar permisos y manejar errores sin revelar información sensible.

¿Qué es un framework de back-end?

El back-end es la parte de una aplicación que se ejecuta en el servidor o en un entorno de servicio. Puede recibir solicitudes por una red, consultar datos, aplicar reglas de negocio y preparar una respuesta. El front-end suele ser el navegador o la aplicación que inicia la interacción, aunque un servicio también puede comunicarse con otro servicio.

Un framework de back-end proporciona una estructura para desarrollar ese software. Según la tecnología, puede incluir un servidor HTTP, un sistema de rutas, middleware, herramientas de validación, plantillas o integración con bases de datos. Algunas soluciones son ligeras y dejan muchas decisiones al equipo; otras ofrecen una estructura más prescriptiva.

Usar un framework no hace que una aplicación sea automáticamente segura, escalable o correcta. El equipo sigue siendo responsable de definir sus reglas, validar los datos, controlar el acceso, gestionar errores y mantener sus dependencias.

El ciclo petición-respuesta

En una comunicación HTTP habitual, el cliente envía una petición que incluye un método, una ruta, encabezados y, en algunos casos, un cuerpo. El servidor recibe esa petición, identifica qué operación corresponde, ejecuta el trabajo necesario y devuelve una respuesta con un código de estado, encabezados y, a menudo, contenido.

  1. El cliente realiza una petición: por ejemplo, solicita una lista de productos.
  2. El servidor interpreta la ruta y el método: el enrutador busca la operación correspondiente.
  3. Se ejecutan verificaciones y reglas: middleware y lógica de aplicación pueden validar la petición y los permisos.
  4. La aplicación obtiene o modifica datos: puede consultar una base de datos u otro servicio.
  5. El servidor construye una respuesta: devuelve un código de estado y contenido apropiado.

El siguiente diagrama muestra una estructura frecuente. La forma concreta depende del framework y de la arquitectura escogida.

Enrutado, controladores y middleware

El enrutado relaciona un método HTTP y una ruta con una operación. Por ejemplo, una aplicación puede usar GET /articulos para consultar una colección y POST /articulos para solicitar la creación de un recurso.

Un controlador recibe la petición asociada a una ruta y organiza la respuesta. Es buena práctica evitar que acumule toda la lógica de negocio y todas las consultas a datos: delegar responsabilidades facilita comprender, probar y mantener el código.

El middleware es una función que puede ejecutarse durante el procesamiento de una petición, antes de que se complete la respuesta. Puede registrar información, analizar el cuerpo, comprobar autenticación o manejar errores. El orden de registro importa: un middleware debe ejecutarse en el momento adecuado y continuar el flujo o terminar la respuesta correctamente.

En Express, una ruta puede conectar una URL con una función manejadora. También es habitual separar el registro de rutas, las funciones de control y la lógica de dominio en módulos distintos. La estructura adecuada depende del tamaño y las necesidades del proyecto.

Capas de una aplicación

Una aplicación de servidor puede dividirse en capas con responsabilidades diferenciadas. No existe una única arquitectura obligatoria, pero separar las funciones reduce la mezcla de detalles HTTP, reglas de negocio y consultas a datos.

Capa Responsabilidad habitual Ejemplo de tarea
Enrutado Relaciona métodos y rutas con manejadores. Conectar GET /articulos/:id con una operación de consulta.
Controlador Interpreta la petición y coordina la respuesta HTTP. Leer parámetros, invocar un servicio y elegir el código de estado.
Servicio Implementa reglas y casos de uso de la aplicación. Comprobar si se permite publicar un artículo.
Acceso a datos Obtiene o modifica información persistente. Buscar un registro mediante una consulta o un repositorio.
Middleware Aplica procesamiento transversal al flujo de petición. Registrar solicitudes o verificar credenciales.

Las capas pueden llamarse de otra manera y combinarse en proyectos pequeños. El criterio importante es que cada pieza tenga una responsabilidad entendible y que las dependencias no creen ciclos difíciles de mantener.

ORM y acceso a datos

La capa de acceso a datos comunica la aplicación con un sistema de almacenamiento. Puede usar consultas SQL directas, una biblioteca de consultas o un ORM (mapeador objeto-relacional), que relaciona estructuras del lenguaje de programación con tablas y registros relacionales.

Un ORM puede reducir la repetición de operaciones comunes y ofrecer abstracciones para consultas, relaciones y cambios de esquema. Sin embargo, no elimina la necesidad de entender la base de datos: consultas ineficientes, relaciones mal modeladas o acceso excesivo a registros pueden afectar al rendimiento y a la corrección.

  • Valida los datos antes de persistirlos y aplica restricciones adecuadas en la base de datos.
  • Usa consultas parametrizadas o mecanismos equivalentes para no concatenar entradas sin tratar en sentencias.
  • Define cómo se manejan transacciones cuando varias operaciones deben completarse juntas.
  • Evita exponer detalles internos del almacenamiento en respuestas públicas si no es necesario.

El ORM es una herramienta de implementación, no una capa de seguridad automática. La autorización, la validación y el diseño de consultas siguen siendo responsabilidades de la aplicación.

Renderizado en servidor y API

En el renderizado en servidor, el servidor genera HTML para una página y lo envía al navegador. Este enfoque puede entregar contenido listo para mostrar y resulta útil para sitios cuyo contenido se organiza alrededor de páginas. La hidratación o el JavaScript del cliente pueden añadir interactividad, si el proyecto los utiliza.

Una API expone operaciones o datos para que otro cliente los consuma. Una API HTTP puede responder con JSON, aunque el formato y el protocolo dependen del diseño. El cliente puede ser una aplicación web, una aplicación móvil, una integración o incluso otro servicio.

Renderizar HTML y exponer una API no son opciones mutuamente excluyentes. Una misma aplicación puede servir páginas y ofrecer endpoints de datos. La elección depende de los clientes, el contenido, las necesidades de interacción y los requisitos operativos.

REST, GraphQL y WebSockets

REST, GraphQL y WebSockets suelen aparecer en conversaciones sobre comunicación entre clientes y servidores, pero representan conceptos de distinto tipo. REST es un estilo arquitectónico para diseñar interfaces de recursos; GraphQL es un lenguaje de consulta y un entorno de ejecución para APIs; WebSocket es un protocolo que permite comunicación bidireccional persistente.

Enfoque Modelo de comunicación Puede encajar cuando… Consideración
REST Operaciones HTTP sobre recursos, normalmente identificados por rutas. Se busca una API basada en recursos y métodos HTTP conocidos. Diseña de manera consistente rutas, estados, errores y compatibilidad.
GraphQL El cliente expresa en una consulta los campos que necesita, dentro del esquema disponible. Varios clientes necesitan consultar combinaciones diferentes de datos. Hay que controlar la complejidad de consultas, los permisos y el costo de ejecución.
WebSockets Conexión persistente para intercambio bidireccional de mensajes. Se necesitan actualizaciones frecuentes en ambas direcciones, como colaboración en vivo. Requiere gestionar conexiones, autenticación, reconexiones y escalado operativo.

La tabla es una guía general, no una clasificación de calidad. REST y GraphQL describen formas de diseñar APIs; WebSocket describe un protocolo de comunicación. Una aplicación puede combinar mecanismos si sus necesidades lo justifican.

Autenticación y autorización

La autenticación comprueba quién realiza una solicitud. La autorización determina qué acciones puede realizar esa identidad. Son controles diferentes: saber quién es una persona no implica que tenga permiso para acceder a todos los recursos.

El framework puede facilitar middleware o puntos de integración para estos controles, pero la aplicación debe definir las políticas. Comprueba los permisos en el servidor para cada operación protegida; ocultar un botón en el front-end no impide que alguien intente llamar directamente a una ruta.

  • Valida entradas y limita los datos aceptados a lo que la operación necesita.
  • Evita incluir contraseñas, secretos o detalles internos en registros y respuestas.
  • Usa mecanismos de sesión o tokens adecuados al contexto y protege su almacenamiento y transporte.
  • Devuelve errores útiles para el cliente sin revelar trazas internas ni información confidencial.
  • Aplica límites y controles adicionales cuando las operaciones o los recursos lo requieran.

La autenticación y la autorización deben formar parte del diseño de cada ruta protegida. Añadir un control genérico sin revisar los permisos de cada recurso puede dejar accesos indebidos.

Servidor HTTP con Express

Este ejemplo muestra un servidor mínimo en Node.js con Express y un endpoint REST de lectura. Incluye una ruta para consultar una colección y otra para obtener un elemento por identificador, además de respuestas básicas para solicitudes inválidas o recursos inexistentes.

Para ejecutarlo se necesita un proyecto que tenga Express instalado. La instalación de dependencias y la configuración de producción dependen del proyecto y no se incluyen aquí. 

const express = require('express');

const app = express();
const puerto = process.env.PORT || 3000;

app.use(express.json());

const articulos = [
  { id: 1, titulo: 'Introducción a HTTP' },
  { id: 2, titulo: 'Diseño de APIs' }
];

app.get('/articulos', (req, res) => {
  res.status(200).json(articulos);
});

app.get('/articulos/:id', (req, res) => {
  const id = Number(req.params.id);

  if (!Number.isInteger(id) || id < 1) {
    return res.status(400).json({ error: 'Identificador inválido' });
  }

  const articulo = articulos.find((elemento) => elemento.id === id);

  if (!articulo) {
    return res.status(404).json({ error: 'Artículo no encontrado' });
  }

  return res.status(200).json(articulo);
});

app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: 'Error interno del servidor' });
});

app.listen(puerto, () => {
  console.log(`Servidor escuchando en el puerto ${puerto}`);
});

El middleware express.json() permite interpretar cuerpos JSON en las solicitudes que lo admiten, aunque este ejemplo solo expone rutas de lectura. La lista de artículos vive en memoria y se pierde al reiniciar el proceso: una aplicación real normalmente delegaría la persistencia a una capa de datos.

El manejador de errores del ejemplo es deliberadamente sencillo. En una aplicación real, registra errores de forma controlada, distingue clases de fallos y evita enviar detalles internos al cliente.

Errores comunes

Error Consecuencia Mejor práctica
Concentrar rutas, reglas y consultas en una sola función. El código se vuelve difícil de probar y cambiar sin efectos colaterales. Separa responsabilidades cuando la complejidad lo justifique.
Confiar en la validación del cliente. Una solicitud puede enviarse directamente con datos inesperados. Valida las entradas en el servidor y define restricciones en el almacenamiento.
Confundir autenticación con autorización. Un usuario autenticado puede terminar accediendo a recursos que no le corresponden. Comprueba identidad y permisos por operación y recurso.
Devolver siempre el código de estado de éxito. Los clientes no pueden distinguir una operación correcta de una fallida. Elige códigos y formatos de error coherentes con el resultado.
Exponer mensajes de error internos. La respuesta puede revelar rutas, consultas, datos o detalles de implementación. Devuelve mensajes seguros y conserva el detalle técnico en registros protegidos.
Elegir una tecnología de comunicación por moda. La solución puede añadir complejidad sin resolver una necesidad real. Parte de los requisitos de los clientes, los datos y el patrón de interacción.
Suponer que el ORM evita cualquier problema de consultas. Puede haber consultas costosas o acceso excesivo a datos. Revisa las consultas y mide el comportamiento con cargas representativas.
