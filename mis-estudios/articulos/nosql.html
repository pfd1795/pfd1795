Bases de datos NoSQL

Una base de datos NoSQL no organiza los datos en tablas, filas y columnas: los guarda como pares clave-valor, documentos, familias de columnas o grafos. Cada modelo elige un compromiso distinto entre flexibilidad, escalado y consistencia. No es un sustituto universal de SQL, sino otra herramienta con ventajas y costes propios.

En 5 puntos

  • NoSQL agrupa modelos muy distintos: clave-valor, documentos, columnas anchas y grafos, cada uno con su forma de consultar.
  • El modelo documental guarda estructuras anidadas y permite leer un objeto completo con una sola consulta, sin unir tablas.
  • CAP obliga a decidir qué ocurre cuando la red se parte: consistencia o disponibilidad, no las dos a la vez en ese instante.
  • En bases documentales se modela según las consultas: algo de duplicación controlada suele ser preferible a muchas uniones.
  • Los índices y la forma de las consultas importan más que la etiqueta «SQL» o «NoSQL» del motor elegido.

¿Qué es NoSQL?

NoSQL significa not only SQL («no solo SQL»). No describe un producto ni un lenguaje de consulta único, sino una familia de bases de datos que no exige el modelo relacional de tablas con esquema fijo. Algunas usan un lenguaje parecido a SQL y otras consultan mediante APIs o recorridos del grafo.

Lo que tienen en común es que la estructura la decide quien escribe el dato y que muchas están pensadas para repartirse entre varios servidores. Las cuatro familias principales resuelven problemas distintos:

Modelo Unidad de datos Consulta típica Caso de uso
Clave-valorPar clave y valor opaco.Leer por clave.Cachés, sesiones, contadores.
DocumentosDocumento con campos anidados.Filtrar por campos y agregar.Catálogos, perfiles, contenido.
Columnas anchasFamilias de columnas por fila.Leer por clave de partición.Series temporales, grandes volúmenes de escritura.
GrafosNodos, aristas y propiedades.Recorrer relaciones.Recomendaciones, redes, fraude.

«NoSQL» no implica «sin esquema». El esquema sigue existiendo, pero suele estar en el código de la aplicación o en validaciones del motor, no impuesto por un CREATE TABLE previo.

Por qué aparecieron

Los motores relacionales destacan por las uniones, las transacciones ACID y un lenguaje de consulta potente. Durante años fueron la opción por defecto. Con el crecimiento de los servicios web aparecieron cargas que encajaban peor: millones de escrituras repartidas, datos que cambiaban de forma cada semana y objetos en memoria que había que convertir en filas antes de guardarlos.

Muchas bases NoSQL respondieron escalando horizontalmente: añadir servidores baratos en lugar de comprar uno más grande. Otras simplificaron la escritura o permitieron guardar un agregado entero —por ejemplo, un pedido con sus líneas— como una sola unidad. El precio fue renunciar a algunas garantías o a la flexibilidad de consultas arbitrarias.

Hoy la frontera es menos rígida. Los motores relacionales soportan JSON y se escalan mejor, y los motores documentales ofrecen transacciones y uniones limitadas. Elegir bien empieza por las necesidades reales, no por la moda.

Clave-valor

Es el modelo más simple: una clave identifica un valor y el motor solo sabe leer, escribir y borrar por esa clave. El valor puede ser texto, un número o un objeto opaco para la base de datos. Redis es el ejemplo más conocido y suele trabajar en memoria, con opciones de persistencia. 

SET sesion:abc123 '{"usuario": 42, "inicio": 1763970000}' EX 3600
GET sesion:abc123

HSET usuario:42 nombre Ana ciudad Sevilla
HGETALL usuario:42

INCR contador:visitas
EXPIRE contador:visitas 86400

Cada operación es muy rápida y tiene un coste predecible. Por eso este modelo brilla en cachés, sesiones, colas sencillas y contadores. La limitación es evidente: no se puede preguntar «dame todas las sesiones de Sevilla» sin mantener un índice propio, porque el motor no interpreta el contenido del valor.

Trabajar en memoria implica perder datos si no se configura persistencia. Un caché puede reconstruirse, pero una sesión o un contador de negocio no deberían depender de una réplica que nadie ha configurado.

Documentos

Una base documental guarda registros parecidos a JSON —BSON en MongoDB— dentro de colecciones. Cada documento puede tener campos distintos y anidar objetos y listas, así que un agregado completo cabe en una sola unidad de almacenamiento. 

db.usuarios.insertOne({
  nombre: 'Ana',
  correo: 'ana@example.com',
  direccion: { ciudad: 'Sevilla', pais: 'ES' },
  etiquetas: ['cliente', 'premium']
});

db.usuarios.find({ 'direccion.ciudad': 'Sevilla' });

La notación con punto permite filtrar por un campo anidado sin declarar columnas. Para resumir datos se usa un pipeline de agregación: cada etapa transforma el flujo de documentos y pasa el resultado a la siguiente. 

db.pedidos.aggregate([
  { $match: { estado: 'pagado' } },
  { $group: { _id: '$clienteId', total: { $sum: '$importe' } } },
  { $sort: { total: -1 } },
  { $limit: 10 }
]);

El inconveniente aparece cuando los mismos datos se necesitan con formas muy distintas. Si el documento guarda los productos de cada pedido, responder «¿cuántas veces se vendió este teclado?» exige recorrer todos los pedidos o mantener otra colección calculada.

Columnas anchas

Los almacenes de columnas anchas —Cassandra o HBase— agrupan las columnas en familias y organizan las filas alrededor de una clave de partición. El diseño se hace pensando en las consultas: la clave determina dónde vive el dato y, por tanto, qué preguntas se pueden responder rápido. 

CREATE TABLE lecturas (
  sensor_id uuid,
  fecha date,
  hora time,
  valor double,
  PRIMARY KEY ((sensor_id, fecha), hora)
) WITH CLUSTERING ORDER BY (hora DESC);

SELECT hora, valor FROM lecturas
WHERE sensor_id = 11111111-1111-1111-1111-111111111111
  AND fecha = '2026-11-24';

Esta tabla responde muy bien a «dame las lecturas de un sensor en un día», porque esa consulta toca una sola partición. Cambiar la pregunta a «dame todas las lecturas de un día» obligaría a recorrer todos los sensores: en este modelo ese coste se paga en el diseño, no en el momento de consultar.

Son motores adecuados para escrituras masivas, series temporales e historiales que crecen sin parar. A cambio, las uniones entre tablas no existen y la coherencia se ajusta por operación.

Grafos

Una base de grafos guarda nodos (entidades), aristas (relaciones) y propiedades en ambos. Las relaciones son datos de primera clase: se recorren sin calcular uniones entre tablas, aunque el camino tenga varios saltos. 

CREATE (ana:Persona {nombre: 'Ana'})-[:AMIGA_DE]->(luis:Persona {nombre: 'Luis'});

MATCH (ana:Persona {nombre: 'Ana'})-[:AMIGA_DE*1..2]-(otra:Persona)
RETURN DISTINCT otra.nombre;

La consulta encuentra a los amigos y a los amigos de amigos de Ana. En SQL esa operación requeriría unir la tabla de personas consigo misma tantas veces como saltos, y cada salto encarecería la consulta. Aquí el coste crece sobre todo con el número de nodos que se visitan.

Encajan bien en recomendaciones, redes sociales, jerarquías organizativas, rutas y detección de fraude. Si las relaciones son escasas y sencillas, un modelo relacional suele ser más fácil de mantener.

Consistencia y CAP

En un sistema distribuido, cada escritura se replica en varios nodos. El teorema CAP describe el compromiso cuando la red se parte y los nodos no pueden comunicarse: en ese momento hay que elegir entre devolver una respuesta consistente —todos ven el mismo valor— o estar disponible —responder aunque sea con datos desactualizados—.

La partición de red no se elige: es una circunstancia que puede ocurrir. Por eso se habla de sistemas CP, que rechazan escrituras antes que devolver datos divergentes, y de sistemas AP, que aceptan escrituras y convergen después. Muchos motores permiten además ajustar la coherencia por consulta: leer de un solo nodo es rápido, leer de una mayoría es más lento pero más fiable.

La coherencia eventual significa que, si deja de llegar escrituras, todas las réplicas acabarán convergiendo. No significa «los datos están mal», sino que durante un tiempo puede leerse un valor antiguo. En una interfaz hay que decidir cómo se muestra ese estado: confirmación pendiente, reintento o lectura desde la réplica principal.

CAP no dice que un sistema deba renunciar para siempre a dos de tres propiedades. Solo describe qué prioriza cuando la red falla; fuera de ese escenario, un motor puede ser consistente y disponible a la vez.

Las transacciones tampoco son exclusivas de SQL. Varias bases documentales ofrecen transacciones ACID sobre varios documentos; el coste es mayor que una escritura aislada. Como siempre, conviene usarlas donde el negocio lo exige —por ejemplo, mover saldo entre cuentas— y no por costumbre.

Modelado y desnormalización

En un modelo relacional se normaliza para evitar duplicados: el nombre del cliente se guarda una sola vez y se referencia por su identificador. En un modelo documental se decide para cada relación si conviene incrustar el dato dentro del documento o guardar una referencia a otro documento.

Como regla inicial, se incrustan las relaciones «uno a pocos» que casi siempre se leen juntas; se referencian las relaciones «uno a muchos» que crecen sin límite y los datos compartidos por muchas entidades. Un pedido lleva incrustadas sus líneas; un cliente referencia sus pedidos. 

db.pedidos.insertOne({
  cliente: { id: 42, nombre: 'Ana' },
  lineas: [
    { productoId: 7, nombre: 'Teclado', cantidad: 2 }
  ],
  total: 58.00
});

Aquí el nombre del cliente y de los productos se copia a propósito: es el estado en el momento de la compra. Si el cliente cambia de nombre mañana, el pedido antiguo debe seguir mostrando el nombre que tenía entonces. Esa copia no es un error de normalización, sino una decisión de negocio.

Desnormalizar no significa duplicar sin control. Cada copia necesita una respuesta clara a la pregunta «¿qué pasa si esto cambia?»: se actualiza, se ignora porque es una instantánea, o se recalcula desde una fuente única.

Consultas e índices

Un índice es una estructura auxiliar que evita recorrer toda la colección. Sin él, una búsqueda por campo lee cada documento; con él, el motor salta directamente a las entradas candidatas. El orden de los campos de un índice compuesto importa: primero los campos de igualdad, después los de ordenación y por último los de rango. 

db.usuarios.createIndex({ 'direccion.ciudad': 1, edad: -1 });

db.usuarios.find(
  { 'direccion.ciudad': 'Sevilla', edad: { $gte: 18 } },
  { nombre: 1, correo: 1, _id: 0 }
).sort({ edad: -1 }).limit(20);

La proyección del ejemplo devuelve solo dos campos, así que el índice puede cubrir parte de la respuesta. Para confirmar que se estáUsing el índice previsto, los motores ofrecen una orden de explicación del plan —explain() en MongoDB— que muestra si se está usando un índice o hubo un escaneo completo de la colección.

La paginación con skip grande es otra trampa habitual: el motor debe descartar uno a uno los documentos anteriores. Para listas largas se pagina por clave, guardando el último valor visto y buscando a continuación de él. 

db.usuarios.find({ _id: { $gt: ultimoIdVisto } })
  .sort({ _id: 1 })
  .limit(20);

Cada índice acelera consultas pero encarece las escrituras y ocupa memoria. Crear índices «por si acaso» sin medir las consultas reales suele empeorar el conjunto.

Cuándo usar NoSQL y cuándo SQL

La decisión depende de la forma de los datos y, sobre todo, de las preguntas que se les van a hacer. Unos criterios prácticos:

  • Datos con relaciones de muchos a muchos y consultas variadas: un modelo relacional con SQL y uniones suele ser más claro y flexible.
  • Transacciones que abarcan varias entidades: prioriza un motor con garantías ACID sólidas, sea relacional o documental.
  • Agregados que se leen y escriben juntos, con campos que cambian: un modelo documental reduce uniones y migraciones.
  • Escrituras masivas y consultas conocidas de antemano: una base de columnas anchas escala bien si el diseño respeta sus claves de partición.
  • Recorridos profundos de relaciones: un grafo evita repetir uniones.
  • Acceso por clave con latencia mínima: una base clave-valor, frecuentemente delante de otra base como caché.

En aplicaciones reales es normal combinarlas: PostgreSQL para los datos de negocio, Redis para la caché y un motor de búsqueda para las consultas de texto. Cada motor resuelve una parte y el código decide dónde vive cada responsabilidad.

La pregunta nunca es «¿SQL o NoSQL?», sino «¿qué garantías necesito y qué consultas voy a repetir?». Cambiar de modelo después suele costar más que elegir con calma.

Migraciones y evolución del esquema

Sin esquema fijo no hay ALTER TABLE, pero los datos siguen cambiando de forma. Una práctica segura es tratar cada cambio como aditivo: añadir un campo nuevo, dejar que el código antiguo lo ignore y rellenarlo con una tarea de fondo. Solo después se empieza a exigir y, mucho más tarde, se retira el campo anterior. 

db.usuarios.updateMany(
  { version: { $exists: false } },
  { $set: { version: 1 } }
);

db.usuarios.updateMany(
  { nombreCompleto: { $exists: false }, nombre: { $exists: true } },
  [
    { $set: { nombreCompleto: '$nombre' } }
  ]
);

Un campo version permite que dos versiones del servicio convivan durante un despliegue gradual: la nueva lee ambos formatos y la antigua sigue funcionando. Cuando todas las instancias están actualizadas, se limpian los campos temporales.

En motores con validación de documentos conviene definir las reglas en el propio motor para detectar escrituras mal formadas. Y antes de borrar cualquier campo, hay que comprobar con consultas de conteo que ya ningún documento lo usa.

Migrar «en caliente» una colección grande puede bloquear escrituras o saturar el motor. Se suele hacer por lotes, con pausas y monitorizando la latencia, no con una sola orden masiva.

Errores comunes

Error Por qué está mal Qué hacer
Elegir NoSQL «porque escala» sin mirar las consultas. Cada modelo escala bien solo para ciertos patrones de acceso. Listar las consultas críticas y comprobar qué claves e índices las sirven.
Duplicar datos sin decidir cómo se actualizan. Las copias se desincronizan y aparecen respuestas contradictorias. Documentar cada copia como instantánea o incluirla en la misma transacción.
Consultar por un campo sin índice. El motor recorre toda la colección y la latencia crece con los datos. Crear índices según consultas reales y revisar el plan con explain().
Confiar en la coherencia eventual sin mostrarlo. El usuario ve datos antiguos o confirmaciones dudosas. Diseñar estados pendientes, reintentos o lecturas desde la réplica principal.
Paginar con skip muy grande. Hay que descartar todos los documentos anteriores en cada página. Paginar por clave usando el último valor visto.
