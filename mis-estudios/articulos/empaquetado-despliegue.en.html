Packaging and deployment

That it works on your machine is only the beginning. Packaging turns code into a reproducible artifact; deploying puts it at other people's disposal without the process depending on who runs it.

In 5 points

  • Packaging means producing an artifact (a directory, a compressed file or a container image) that contains everything needed to run the application.
  • A build must be reproducible: the same inputs always produce the same result, regardless of the machine it runs on.
  • Environment variables separate configuration from code; secrets are never written into the repository.
  • Docker packages the application with its environment; an image is immutable and a container is a running instance of that image.
  • CI/CD automates verification and publication: every change goes through the same tests and reaches production in a predictable way.

What packaging and deploying mean

During development you run the code directly: you open a file, start a local server and see the result instantly. In production nobody needs to have the same tools or the same versions installed. That is why two moments are separated.

Packaging means transforming source code into an artifact: a directory of static files, a compressed archive, an npm package or a container image. That artifact is self-contained and can be moved from one environment to another.

Deploying means taking that artifact and making it run in the target environment: uploading it to a server, creating the containers, applying the migrations and leaving the application answering requests.

The important boundary between the two is reproducibility. If the deployment recompiles the code with a different version of the dependencies, you are no longer publishing what you tested: you tested one thing and published another.

The build process

A build gathers the dependencies, transforms the code and generates the final files. In a modern web application it can include several tasks:

  • Install dependencies from a lock file (package-lock.json, pnpm-lock.yaml, a pinned requirements.txt).
  • Compile or transpile: TypeScript to JavaScript, JSX to function calls, Sass to CSS.
  • Bundle and minify: join modules and reduce size so the browser downloads fewer files.
  • Process resources: optimise images, copy fonts and resolve asset paths.
  • Generate the version manifest, with the commit hash and the build date, to know what is deployed.
npm ci                  # install exactly what the lockfile says
npm run test            # fail the build if tests fail
npm run build           # generate the dist/ directory
ls -lh dist/            # inspect the resulting artifact

Use npm ci (or your manager's equivalent) in automation: it respects the lock file and fails if it changed. npm install may resolve different versions on each run.

Environment variables and secrets

The same application needs different values depending on where it runs: the API URL, the port, the database credentials or the debug mode. Those values are read from environment variables, not written into the code. 

DATABASE_URL=postgres://user:pass@localhost:5432/app
API_BASE_URL=https://api.example.com
NODE_ENV=production
LOG_LEVEL=info

Locally they are usually loaded from a .env file that is never pushed to the repository; in production the platform or the orchestrator injects them. The code only knows the variable name: 

const apiUrl = process.env.API_BASE_URL;
if (!apiUrl) {
  throw new Error('Missing API_BASE_URL');
}

A .env.example file with the names and example values is versioned: it documents what must be configured without exposing real credentials. Add .env to .gitignore from the first commit.

There is an important distinction in frontend applications: everything included in a JavaScript bundle is public, even if the variable is called SECRET_KEY. Real secrets must live only on the server.

Containers with Docker

A container packages the application together with its runtime environment: base system, system dependencies, libraries and code. That way the server only needs Docker instead of an exact list of manually installed versions.

Two concepts worth not confusing: the image is an immutable template built from a Dockerfile; the container is a running instance of that image. 

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY dist/ ./dist/
ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "dist/server.js"]

The order of the instructions matters because each one creates a layer that is cached. Copying the dependency files first allows reusing the npm ci layer when only the code changes. 

docker build -t my-app:1.4.0 .
docker run --rm -p 3000:3000 --env-file .env my-app:1.4.0

For applications with several services (API, database, cache) a docker-compose.yml is used, which describes the network, the volumes and the variables of each service in a single file.

Tag images with a version or the commit hash, not just latest. Without a unique tag you cannot know which version is running or go back to it.

Continuous integration and delivery (CI/CD)

Continuous integration automatically runs the checks every time someone opens a change: formatting, linting, tests and build. Continuous delivery takes that already verified artifact to an environment, and continuous deployment publishes it to production without manual intervention. 

name: deploy
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

The key is that the same artifact is promoted across environments: the package that passed the tests is the one that goes to production. Recompiling in each environment opens the door to subtle differences.

Protecting the main branch and requiring the checks to pass before merging turns CI into a safety net: the error is detected when the change is small, not days later.

Release strategies

The way to publish depends on the type of application. What matters is that the mechanism is repeatable and that there is a way to go back.

  • Static sites: the dist/ directory is uploaded to a file host (GitHub Pages, Netlify, Cloudflare Pages). There is no server to maintain; the platform handles caching and HTTPS.
  • Applications with a server: the image is published to a registry and the container is updated on the server or in an orchestrator, usually behind a reverse proxy like nginx.
  • Platform as a service (PaaS): the platform receives the code or the image and manages the runtime environment, scaling and also the environment variables.
  • Serverless functions: each function is deployed separately and the provider runs it on demand. The artifact is usually a compressed file.

To reduce risk, blue-green deployments (two versions coexist and traffic is switched from one to the other) or canary deployments (a small part of the traffic goes to the new version) are used. Both strategies let you detect problems before they affect everyone and make rollback easier.

Best practices

  • Pin dependency versions with a lock file and use strict installation in automation.
  • Build once and promote the same artifact across environments.
  • Treat configuration as external data: environment variables, never constants in code.
  • Version the definition of the infrastructure and the deployment in the repository.
  • Make deployment idempotent: running it twice should leave the same state.
  • Log the version, commit hash and time of each release.
  • Check the application's health after publishing with a /health route.
  • Always prepare the rollback before pressing the publish button.

Common mistakes

  • Trusting npm install instead of the lock file: the build stops being reproducible.
  • Pushing a .env file with real credentials to the repository.
  • Including secrets in the frontend bundle, where anyone can read them.
  • Recompiling in production and publishing code different from what passed the tests.
  • Using latest images: a rebuild under the same name changes what runs.
  • Publishing without a health check or a rollback plan.
  • Mixing database migrations with application startup without controlling the order.

If something works locally but not in production, first compare three things: dependency versions, environment variables and runtime version. The difference is almost always there.

Quick reference

Concept What it is for
Build Transform source code into a reproducible artifact.
Lockfile Pin the exact versions of dependencies.
Environment variable Separate configuration from code.
Image Immutable template with application and environment.
Container Running instance of an image.
CI Automatically verify every change.
CD Automatically publish a verified artifact.
Blue-green Two versions coexist to allow an immediate rollback.
