Editores, IDEs y depuración

El editor es donde escribes el código; el depurador es donde entiendes por qué no hace lo que esperabas. Dominar ambas herramientas acelera más que cualquier truco de lenguaje.

En 5 puntos

  • Un editor de texto edita archivos y se apoya en extensiones; un IDE integra editor, compilador, depurador y gestor de proyecto en uno.
  • La mayoría de los desarrolladores hoy usan un editor extensible (VS Code) que se comporta casi como un IDE gracias a las extensiones.
  • Depurar no es «leer el código hasta ver el error»: es observar el estado real del programa mientras se ejecuta.
  • Las herramientas básicas del depurador son breakpoints, step over/into/out, watch y la pila de llamadas.
  • El console.log (o print) es útil, pero no sustituye al depurador cuando el flujo es complejo.

¿Qué es un editor y qué es un IDE?

Un editor de texto es un programa que edita archivos de texto plano. Su trabajo es ayudarte a escribir: coloreado de sintaxis, autocompletado, búsqueda y reemplazo, y extensiones que añaden capacidades. No sabe nada de tu proyecto ni de cómo se ejecuta.

Un IDE (entorno de desarrollo integrado) es un editor al que se le ha unido el resto del flujo de trabajo: compilador o intérprete, depurador, gestor de proyecto, control de versiones y, a menudo, diseñador de interfaces o base de datos. Todo convive en una misma ventana y comparte el contexto del proyecto.

La frontera se ha difuminado: un editor moderno con extensiones (VS Code, Neovim) puede comportarse casi como un IDE. La diferencia real no es la cantidad de funciones, sino si el entorno entiende tu proyecto como un todo o solo edita archivos.

Editores de texto

  • VS Code: el más extendido. Gratuito, multiplataforma y con un ecosistema enorme de extensiones (lenguajes, temas, linters, depuradores). Su núcleo es ligero; la potencia viene de las extensiones.
  • Vim / Neovim: editores modales que se manejan desde el teclado. Empiezan vacíos y se convierten en lo que tú configuras; curva de aprendizaje alta, productividad muy alta para quien los domina.
  • Sublime Text, Notepad++, Kate: editores ligeros y rápidos, ideales para abrir archivos sueltos o editar en máquinas con pocos recursos.
  • Editores del sistema (nano, vi): vienen instalados en casi cualquier servidor Linux; saber lo mínimo es una habilidad de supervivencia.

Lo que un buen editor aporta de serie: coloreado de sintaxis, autocompletado (IntelliSense), ir a definición, renombrar símbolo, formateo y Git integrado.

Entornos de desarrollo integrados (IDE)

  • Visual Studio: el IDE clásico para .NET y C++. Pesado pero muy completo: depurador visual, diseñador de formularios, profiler.
  • JetBrains (IntelliJ, PyCharm, WebStorm, Rider): IDEs por lenguaje con refactorizaciones avanzadas y análisis estático profundo. De pago, con versiones gratuitas limitadas.
  • Eclipse / NetBeans: históricos del mundo Java; hoy menos comunes salvo en entornos corporativos legados.
  • Xcode: el IDE de Apple para Swift/Objective-C y desarrollo de apps para sus plataformas.
  • Android Studio: basado en IntelliJ, el IDE oficial para Android.

Un IDE brilla cuando el proyecto es grande y el lenguaje es estático (Java, C#, C++): el compilador y el IDE comparten un modelo del código que permite refactorizaciones seguras. En lenguajes dinámicos (JavaScript, Python) un editor extensible suele bastar.

Depuración: observar el estado real

Depurar es ejecutar el programa paso a paso y observar cómo cambian las variables, en lugar de adivinar leyendo el código. El flujo típico:

  1. Reproduce el bug de forma fiable (si no puedes reproducirlo, no puedes arreglarlo).
  2. Pon un breakpoint cerca de donde sospechas que falla.
  3. Ejecuta el programa; se detendrá en el breakpoint.
  4. Inspecciona variables, pila de llamadas y flujo.
  5. Avanza paso a paso hasta encontrar dónde el estado deja de coincidir con lo esperado.
  6. Corrige y vuelve a ejecutar para confirmar.

El depurador no arregla nada por sí solo: te da información. El error suele estar entre el último estado correcto y el primero incorrecto.

Breakpoints, step y control de flujo

// Ejemplo para depurar en el navegador (DevTools) o en VS Code.
function calcularTotal(items) {
  let total = 0;
  for (const item of items) {
    total += item.precio * item.cantidad;  // ← pon aquí un breakpoint
  }
  return total;
}
  • Breakpoint: pausa la ejecución en esa línea antes de ejecutarla.
  • Conditional breakpoint: solo pausa si una condición se cumple (p. ej. item.precio < 0), útil en bucles largos.
  • Step over (F10): ejecuta la línea actual y pasa a la siguiente sin entrar en las funciones que llama.
  • Step into (F11): entra dentro de la función que se llama en esa línea.
  • Step out (Shift+F11): sale de la función actual y vuelve al llamador.
  • Continue (F5): reanuda hasta el siguiente breakpoint.
  • Logpoint: imprime un mensaje en consola sin modificar el código ni pausar.

Watch, call stack y variables

  • Variables locales: panel que muestra el valor actual de cada variable en el ámbito actual.
  • Watch: expresiones que tú defines y que se reevalúan en cada paso (p. ej. items.length o total > 100).
  • Call stack (pila de llamadas): la cadena de funciones que llevó hasta aquí. Hacer clic en un marco te lleva al código de esa función con su contexto.
  • Scope chain: variables accesibles desde el bloque actual, incluyendo los ámbitos superiores.

La pila de llamadas es la herramienta más infravalorada: cuando un error dice «en línea 42», el marco real del fallo suele estar dos o tres niveles más arriba en la pila.

Logging: el complemento práctico

Imprimir mensajes sigue siendo útil, sobre todo en código asíncrono, servidores o cuando no hay depurador disponible (producción, CI). 

// JavaScript
console.log('valor:', valor);        // mensaje general
console.warn('algo raro');            // advertencia (amarillo)
console.error('fallo grave');         // error (rojo)
console.table(arrayDeObjetos);        // tabla legible
console.time('carga'); /* ... */ console.timeEnd('carga'); // medir tiempo

// Python
import logging
logging.basicConfig(level=logging.DEBUG)
logging.debug('valor: %s', valor)
logging.exception('fallo')  // incluye el traceback
  • Úsalo para trazar el flujo, no para inspeccionar estado detallado (para eso, el depurador).
  • Evita dejar console.log en el código final; usa un logger con niveles y desactívalo en producción.
  • En el navegador, console.log acepta formatters: console.log('%c texto', 'color: red').

Buenas prácticas

  • Aprende los atajos de teclado del depurador: ahorran más tiempo que cualquier extensión.
  • Mantén el código formateado y con nombres claros; depurar código ofuscado es perder el tiempo.
  • Reproduce el bug con un caso mínimo antes de depurar: menos ruido, causa más visible.
  • No depures con print cuando tengas un depurador a mano; pero no desprecies el logging en entornos sin depurador.
  • Configura source maps si tu código se transpila o se minifica, para depurar el código original.
  • Usa linters y formateadores (ESLint, Prettier, Black, rustfmt) para detectar errores antes de ejecutar.

Errores comunes

  • Depurar sin reproducir primero el bug: te pierdes en el flujo normal del programa.
  • Poner breakpoints en el lugar equivocado y concluir «no pasa nada».
  • Confundir step over con step into y saltarse la función que falla.
  • Inspeccionar variables en el ámbito equivocado del call stack.
  • Dejar console.log con datos sensibles en producción.
  • Cambiar el código mientras depuras y perder el rastro de qué funcionaba.

Si el programa «se comporta distinto» al depurar, puede ser un heisenbug: condiciones de carrera o código que depende del tiempo. En esos casos, logging y reproducibilidad controlada ayudan más que el depurador interactivo.

Referencia rápida

Herramienta Para qué sirve
Breakpoint Pausar la ejecución en una línea.
Step over / into / out Avanzar sin entrar, entrar o salir de funciones.
Watch Observar expresiones mientras avanzas.
Call stack Ver la cadena de llamadas que llevó al punto actual.
Logpoint Imprimir sin modificar código ni pausar.
Source map Mapear código transpilado/minificado al original.
