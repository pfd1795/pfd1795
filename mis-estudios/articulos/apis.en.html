Software architecture and design

Client-server and APIs

Every modern web application talks —in one way or another— to a backend over HTTP. Here we explain the client-server model (who does what), how to design a readable REST API, and how clients prove their identity: sessions, JWT tokens and OAuth2.

In 5 points

  • The client sends requests; the server replies. Everything else (session state, cache) lives between the two.
  • A REST API exposes resources in URLs («nouns») and uses HTTP methods as verbs: GET/POST/PUT/PATCH/DELETE.
  • Stateless: each request carries everything needed to be understood, which is why an authentication mechanism is needed.
  • Three ways to authenticate: session + cookie, JWT token, or delegating to a service (OAuth2/OIDC).
  • The contract with external clients is documented and versioned; error codes are part of the contract.

The client-server model

The client asks for something (a page, a datum, an action) and the server supplies the answer with the logic, the data and the guarantees (persistence, integrity). They speak the protocol you choose, almost always HTTP over TLS:

«Stateless» does not mean «memoryless»: it means the conversation is not stored on the server. What needs to persist is saved in the DB; what identifies the user travels in every request (cookie or token).

REST APIs: resources and methods

REST is an architectural style: every business concept is a resource identified by a stable URL, and HTTP methods express the operations:

Resource Operation Method · route
List articlesRead the collectionGET /api/articles
Detail of an articleSingle readGET /api/articles/42
Create articleCreationPOST /api/articles
Replace articleFull updatePUT /api/articles/42
Update part of the articlePartial updatePATCH /api/articles/42
Delete articleDeletionDELETE /api/articles/42
Action with its own semanticsCommand, not resourcePOST /api/articles/42/publish (acceptable as an exception)
  • Names in plural, lowercase and without verbs in the route; with / as a hierarchical separator.
  • The verbs go in the method, not in the URL: GET /api/deleteArticle?id=42 is a sign of improper design.
  • Filters, pagination and ordering go in the query string: ?page=2&limit=20&sort=-date.
  • Complex searches are modelled as their own resources (GET /api/arts/search?q=…) or as POST to a query endpoint.
# Manual test of an API with curl (the client would call it with fetch)
  curl -s https://api.example.dev/api/articles?limit=2 \
    -H 'Accept: application/json'

  curl -s -X POST https://api.example.dev/api/articles \
    -H 'Content-Type: application/json' \
    -H 'Authorization: Bearer eyJhbGci...' \
    -d '{"title":"New article","body":"..."}'

JSON: the exchange format

JSON is structured text: objects between braces, lists between brackets, and values that can be string, number, boolean, null or another nested structure: 

{
    "page": 1, "limit": 20, "total": 143,
    "items": [
      { "id": 42, "title": "HTTP and the web browser", "tags": ["http", "web"] }
    ]
  }
  • Keys are usually in camelCase (or snake_case; pick one style and be consistent across the whole API).
  • Dates are sent as ISO 8601: "2026-11-06T10:30:00Z" (UTC and with an explicit zone).
  • JS offers mapping out of the box in JSON.parse and JSON.stringify; fetch already brings .json().
  • Careful with money values in floats: if precision matters, use integers in the smallest unit (cents).
const response = await fetch('/api/articles?limit=20');
  if (!response.ok) {
    throw new Error('HTTP ' + response.status);
  }
  const { page, total, items } = await response.json();

Status codes and error handling

Significant codes for an API (summarised from Networks · HTTP):

Code When to use it in an API
200 OKSuccess on GET/PUT/PATCH/DELETE
201 CreatedResource created by POST; Location points to the new resource
204 No ContentSuccess with no body to return (DELETE)
400 Bad RequestMalformed request or invalid fields
401 UnauthorizedUnauthenticated (missing or no longer valid credential)
403 ForbiddenAuthenticated, but no permission
404 Not FoundThe resource does not exist (or is not revealed for security)
409 ConflictState clash (email already registered)
422 Unprocessable EntityValid syntax but semantically rejectable (empty fields)
429 Too Many RequestsRate limit
500Unhandled error; should not reach production with details

The error body should be predictable; the common proposal is RFC 9457 (Problem Details): type, title, status, detail. At the very least, include a traceability identifier.

403 vs 404: if revealing the existence of the resource is sensitive data (private organisations), answer 404.

Authentication: session, JWT and OAuth2

Who the user making the request is; three dominant approaches:

Mechanism How it works When it suits
Session + cookie The server keeps state («session no. 15») and delivers a cookie; the client resends it automatically Sites with front and back in the same project; maximum revocation capability
JWT token The server signs a self-verifiable token; the client sends it in Authorization: Bearer … on every request Public APIs, mobile, service-to-service; serverless identity
OAuth2 / OIDC Delegates authentication to a provider (Google, GitHub): the server trusts the token issued by it «Sign in with…», integrations between organisations, SSO

Authentication answers «who are you?». Authorisation answers «what can you do?» (roles, permissions per resource). Both are needed.

JWT inside out

A JSON Web Token is a header.payload.signature string, each part in Base64URL:

eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxNSIsInJvbCI6IkFETUlOIn0 . 1b4ad1c5
    { "alg": "HS256" }     { "sub": "15", "rol": "ADMIN" }   HMAC-SHA256(key, header+payload)
  • Header: signing algorithm.
  • Payload: claims (subject, expiration, roles). It can be read without a key; nothing secret travels inside.
  • Signature: the server verifies it with its private key / the shared secret; any modification of the payload breaks it.

The payload «expires» in the exp claim, but that is not magic: the server checks the datum when validating. To revoke a token you need a token revocation list (for example, per session) or short expirations + refresh token. 

# Decode the payload of a JWT (does not verify signatures: only interprets)
  echo 'eyJzdWIi...payload...' | base64 --decode

Choosing the right piece

Before designing your backend and integrating, answer in order:

  1. Which resources exist and who reads/edits each one?
  2. Who is the client (your own frontend, apps, third parties)? That conditions CORS, auth and versioning.
  3. Do you need real time? (WebSockets and SSE are another family of protocols on top of HTTP.)
  4. Which business domain is understood intuitively and which flow is documented on each endpoint? (contract and examples).

A good predictor of simple systems: each endpoint answers one intent; clients reproduce it without surprises. The base of your API is the business rules, not the technology chosen.

Best practices

  • Return correct status codes: they are a contract, not decoration.
  • Do not expose keys or internal IDs that should not travel; validate and sanitise on the server (Security).
  • Pagination always on the collection, from day one (the list of 10 records will grow).
  • Idempotency of PUT/DELETE: repeating the same request does not duplicate effects.
  • Version the API in the route (/v1/) if there are external clients that will depend on it.
  • Never log credentials: no later filter justifies what has already leaked.
