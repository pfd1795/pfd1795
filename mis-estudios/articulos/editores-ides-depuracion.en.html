Development tools

Editors, IDEs and debugging

The editor is where you write code; the debugger is where you understand why it does not do what you expected. Mastering both tools speeds you up more than any language trick.

In 5 points

  • A text editor edits files and relies on extensions; an IDE integrates editor, compiler, debugger and project manager into one.
  • Most developers today use an extensible editor (VS Code) that behaves almost like an IDE thanks to extensions.
  • Debugging is not "reading the code until you spot the error": it is observing the real state of the program while it runs.
  • The basic debugger tools are breakpoints, step over/into/out, watch and the call stack.
  • console.log (or print) is useful, but it does not replace the debugger when the flow is complex.

What is an editor and what is an IDE?

A text editor is a program that edits plain text files. Its job is to help you write: syntax highlighting, autocompletion, search and replace, and extensions that add capabilities. It knows nothing about your project or how it runs.

An IDE (integrated development environment) is an editor to which the rest of the workflow has been attached: compiler or interpreter, debugger, project manager, version control and, often, interface or database designers. Everything coexists in a single window and shares the project context.

The line has blurred: a modern editor with extensions (VS Code, Neovim) can behave almost like an IDE. The real difference is not the number of features, but whether the environment understands your project as a whole or only edits files.

Text editors

  • VS Code: the most widespread. Free, cross-platform and with a huge ecosystem of extensions (languages, themes, linters, debuggers). Its core is light; the power comes from extensions.
  • Vim / Neovim: modal editors driven from the keyboard. They start empty and become whatever you configure; steep learning curve, very high productivity for those who master them.
  • Sublime Text, Notepad++, Kate: light and fast editors, ideal for opening loose files or editing on machines with few resources.
  • System editors (nano, vi): shipped with almost any Linux server; knowing the minimum is a survival skill.

What a good editor provides out of the box: syntax highlighting, autocompletion (IntelliSense), go to definition, rename symbol, formatting and integrated Git.

Integrated development environments (IDE)

  • Visual Studio: the classic IDE for .NET and C++. Heavy but very complete: visual debugger, form designer, profiler.
  • JetBrains (IntelliJ, PyCharm, WebStorm, Rider): per-language IDEs with advanced refactorings and deep static analysis. Paid, with limited free versions.
  • Eclipse / NetBeans: historical in the Java world; less common today except in legacy corporate environments.
  • Xcode: Apple's IDE for Swift/Objective-C and app development for its platforms.
  • Android Studio: based on IntelliJ, the official IDE for Android.

An IDE shines when the project is large and the language is static (Java, C#, C++): the compiler and the IDE share a model of the code that enables safe refactorings. In dynamic languages (JavaScript, Python) an extensible editor is usually enough.

Debugging: observing the real state

Debugging means running the program step by step and watching how variables change, instead of guessing by reading the code. The typical flow:

  1. Reproduce the bug reliably (if you cannot reproduce it, you cannot fix it).
  2. Place a breakpoint near where you suspect it fails.
  3. Run the program; it will pause at the breakpoint.
  4. Inspect variables, call stack and flow.
  5. Step forward until you find where the state stops matching what you expected.
  6. Fix it and run again to confirm.

The debugger fixes nothing by itself: it gives you information. The error usually lies between the last correct state and the first incorrect one.

Breakpoints, step and flow control

// Example to debug in the browser (DevTools) or in VS Code.
function calculateTotal(items) {
  let total = 0;
  for (const item of items) {
    total += item.price * item.quantity;  // ← put a breakpoint here
  }
  return total;
}
  • Breakpoint: pauses execution on that line before running it.
  • Conditional breakpoint: only pauses if a condition holds (e.g. item.price < 0), useful in long loops.
  • Step over (F10): runs the current line and moves to the next without entering the functions it calls.
  • Step into (F11): steps into the function called on that line.
  • Step out (Shift+F11): leaves the current function and returns to the caller.
  • Continue (F5): resumes until the next breakpoint.
  • Logpoint: prints a message to the console without modifying the code or pausing.

Watch, call stack and variables

  • Local variables: panel showing the current value of each variable in the current scope.
  • Watch: expressions you define and that are re-evaluated on every step (e.g. items.length or total > 100).
  • Call stack: the chain of functions that led here. Clicking a frame takes you to that function's code with its context.
  • Scope chain: variables accessible from the current block, including outer scopes.

The call stack is the most underrated tool: when an error says "line 42", the real frame where it fails is usually two or three levels higher in the stack.

Logging: the practical complement

Printing messages is still useful, especially in asynchronous code, servers or when no debugger is available (production, CI). 

// JavaScript
console.log('value:', value);        // general message
console.warn('something odd');       // warning (yellow)
console.error('serious failure');    // error (red)
console.table(arrayOfObjects);       // readable table
console.time('load'); /* ... */ console.timeEnd('load'); // measure time

// Python
import logging
logging.basicConfig(level=logging.DEBUG)
logging.debug('value: %s', value)
logging.exception('failure')  // includes the traceback
  • Use it to trace the flow, not to inspect detailed state (for that, the debugger).
  • Avoid leaving console.log in the final code; use a logger with levels and disable it in production.
  • In the browser, console.log accepts formatters: console.log('%c text', 'color: red').

Best practices

  • Learn the debugger's keyboard shortcuts: they save more time than any extension.
  • Keep code formatted with clear names; debugging obfuscated code wastes time.
  • Reproduce the bug with a minimal case before debugging: less noise, more visible cause.
  • Do not debug with print when you have a debugger at hand; but do not dismiss logging in environments without a debugger.
  • Configure source maps if your code is transpiled or minified, to debug the original code.
  • Use linters and formatters (ESLint, Prettier, Black, rustfmt) to catch errors before running.

Common mistakes

  • Debugging without first reproducing the bug: you get lost in the program's normal flow.
  • Placing breakpoints in the wrong spot and concluding "nothing happens".
  • Confusing step over with step into and skipping the failing function.
  • Inspecting variables in the wrong scope of the call stack.
  • Leaving console.log with sensitive data in production.
  • Changing code while debugging and losing track of what worked.

If the program "behaves differently" while debugging, it may be a heisenbug: race conditions or time-dependent code. In those cases, logging and controlled reproducibility help more than the interactive debugger.

Quick reference

Tool What it is for
Breakpoint Pause execution on a line.
Step over / into / out Advance without entering, enter, or leave functions.
Watch Observe expressions while stepping.
Call stack See the chain of calls that led to the current point.
Logpoint Print without modifying code or pausing.
Source map Map transpiled/minified code back to the original.
