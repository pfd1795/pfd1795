Software architecture and design

Design principles and SOLID

Designing software means deciding how to distribute responsibilities and how to make its parts change without breaking others. SOLID brings together five object-oriented design principles that help reason about those decisions: single responsibility, open/closed, Liskov substitution, interface segregation and dependency inversion. They are not mechanical rules nor do they guarantee good design on their own; they serve to identify couplings and improve code when there is a concrete need.

In 5 points

  • SOLID is a set of five principles for thinking about object-oriented software design.
  • Single responsibility seeks that a module has a main reason to change.
  • Open/closed and Liskov substitution promote safe extensions and compatible behaviors.
  • Interface segregation and dependency inversion reduce unnecessary dependencies between components.
  • Applying SOLID does not mean creating more classes: the design should respond to real needs and stay understandable.

What is SOLID?

SOLID is an acronym that groups five design principles associated with object-oriented programming. Its purpose is to help build components with clear responsibilities and dependencies that can be managed when the system evolves.

The principles do not describe a single architecture or a list of mandatory steps. They are criteria for evaluating decisions: which parts change together?, which dependencies make a piece hard to test?, can an implementation replace another without altering expectations?

Although they are explained with classes and interfaces, many of their ideas also apply to modules, functions and services. The chosen abstraction should fit the language and the size of the problem.

Letter Principle Guiding question
S Single responsibility Does this module have a main reason to change?
O Open/closed Can I add behavior without repeatedly modifying stable code?
L Liskov substitution Does an alternative implementation meet the expectations of the type it replaces?
I Interface segregation Do consumers depend only on the operations they need?
D Dependency inversion Does important logic depend on contracts instead of concrete details?

S: single responsibility

The single responsibility principle (SRP) proposes that a module have a main responsibility and a coherent reason to change. It does not require a class to do a single operation: it seeks to avoid the same unit mixing concerns that change for different reasons.

For example, a class that computes a purchase total, generates a report and sends it by email brings together calculation rules, presentation and communication. If tax rules, report format or email service change, the same class may need modifications for different reasons.

An alternative is to separate those concerns into components with defined functions: a service to calculate, a formatter to present and an adapter to send. Separation should follow the real organization of the domain; creating a class per line of code is not the goal.

«A reason to change» is interpreted in relation to the actors or areas that request changes, not as a literal rule about the number of methods.

O: open/closed

The open/closed principle (OCP) states that a software unit should allow its behavior to be extended without requiring repeated modifications of its stable code. It does not mean code can never change: it means it is worth designing extension points when foreseeable changes justify it.

If a function selects an operation through a chain of conditionals, each new type may require editing that function. When behaviors vary, an interface or interchangeable strategy can let you add an implementation without rewriting the logic that uses it. 

class DiscountCalculator {
  calculate(purchase, customerType) {
    if (customerType === 'regular') {
      return purchase * 0.05;
    }

    if (customerType === 'preferred') {
      return purchase * 0.10;
    }

    return 0;
  }
}

In this example, adding another category forces modifying the same function. An option for a system where those rules change frequently is to represent each policy as an object with a common method: 

class RegularDiscount {
  calculate(purchase) {
    return purchase * 0.05;
  }
}

class PreferredDiscount {
  calculate(purchase) {
    return purchase * 0.10;
  }
}

function calculateDiscount(purchase, policy) {
  return policy.calculate(purchase);
}

const discount = calculateDiscount(
  200,
  new PreferredDiscount()
);

The second form introduces additional abstractions. If only two stable rules exist and the system is small, a simple condition may be clearer. Extension should solve a real cost, not anticipate imaginary possibilities.

L: Liskov substitution

The Liskov substitution principle (LSP) indicates that an implementation of a type should be usable where that type is expected without breaking the properties the program assumes. In practical terms, a derived class or an implementation should not surprise whoever uses it by failing to meet the established contract.

A design problem signal appears when a subclass needs to reject operations the base type promises, changes the meaning of a method or demands more restrictive conditions than the original contract.

For example, if a Storage type promises to store and retrieve values, every implementation presented under that contract should offer both operations with the agreed behavior. A read-only implementation should not pretend to meet that contract if it cannot store.

The principle does not forbid inheritance. It invites defining clear contracts and checking that variants respect the expectations of client code. In some cases, composition or smaller interfaces better represent real capabilities.

I: interface segregation

The interface segregation principle (ISP) recommends that consumers not depend on operations they do not use. Instead of a large interface forcing implementation of irrelevant methods, smaller contracts can be defined according to the needed capabilities.

Imagine a device interface with operations for printing, scanning and sending a fax. A device that only prints would have to include methods it cannot offer, possibly with errors or empty implementations. Separating capabilities lets each consumer depend on what it really needs. 

class Printer {
  print(document) {
    console.log(`Printing: ${document}`);
  }
}

class Scanner {
  scan(document) {
    return `Copy of: ${document}`;
  }
}

function sendToPrinter(printer, document) {
  printer.print(document);
}

JavaScript does not natively require declaring interfaces like some typed languages, but separation of capabilities can also be reflected in functions, modules and documented contracts.

D: dependency inversion

The dependency inversion principle (DIP) proposes that high-level modules, where the important rules live, should not depend directly on low-level details. Both should depend on abstractions. In turn, concrete details implement those abstractions.

A notification service that directly creates an SMTP client is coupled to a concrete technology. If it receives a dependency that meets a common contract, it can use different sending methods without changing the central logic. 

class NotificationService {
  constructor(channel) {
    this.channel = channel;
  }

  send(recipient, message) {
    return this.channel.send(recipient, message);
  }
}

class ConsoleChannel {
  send(recipient, message) {
    console.log(`To ${recipient}: ${message}`);
  }
}

const service = new NotificationService(new ConsoleChannel());
service.send('team@example.test', 'The task finished');

The abstraction does not have to be a formal interface. It can be a contract, a function or an object with the operations the module needs. Dependency injection is a common technique for providing those dependencies from outside; it is a way of implementing the idea, not an exact synonym of the principle.

How the principles relate

The principles support each other. A clear responsibility makes it easier to locate changes; small contracts avoid unnecessary dependencies; abstractions allow substituting implementations and extending behaviors. The diagram summarizes a possible relationship, not a mandatory application sequence.

Together, these criteria help components have understandable boundaries and collaborate through contracts. Even so, a system can be maintainable without applying every principle explicitly, and a rigid application of SOLID can produce unnecessary abstractions.

When to apply SOLID

SOLID is especially useful when reviewing code that changes frequently, is hard to test or forces modifying many parts to add a capability. It also offers a common vocabulary to discuss why a dependency or a responsibility hinders maintenance.

  • Start from an observable problem: repeated changes, difficult tests or dependencies that prevent replacing a piece.
  • Identify which responsibility or contract is involved before adding a new abstraction.
  • Make a bounded change and check that existing behavior still works.
  • Use tests to document important contracts and detect regressions.
  • Re-evaluate the design when new requirements appear; there is no need to anticipate them all.

Simplicity is also a design property. If an abstraction does not reduce present complexity or ease a likely change, it may be better to keep the direct solution.

Common mistakes

Mistake Why it harms Better approach
Interpreting single responsibility as «one class, one method». Produces artificial divisions without clarifying the real reasons for change. Look for coherent responsibilities and related reasons for change.
Designing extensions for any imaginable future. Adds complexity before a need exists. Introduce extension points when a change pattern justifies them.
Using inheritance only to reuse code. The subclass may not meet the base class contract. Check substitutability and consider composition when it fits better.
Creating huge interfaces with optional or empty methods. Consumers depend on operations they do not need and contracts lose clarity. Split capabilities according to the needs of their consumers.
Confusing dependency inversion with using an injection container. An injection tool does not guarantee dependencies are well designed. First define the needed contract, then the mechanism to provide the implementation.
Applying the five principles as a rigid checklist. Can lead to layers and abstractions that add no value. Use them as design questions against concrete problems.
