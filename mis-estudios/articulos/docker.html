Docker y contenedores

Un contenedor agrupa una aplicación con todo lo que necesita para ejecutarse y la separa del sistema donde corre. Docker popularizó ese modelo y lo convirtió en una herramienta concreta: describir el entorno en un archivo de texto, construir una imagen repelable y arrancar tantas instancias como hagan falta, igual en el portátil que en el servidor.

En 5 puntos

  • Un contenedor aísla procesos que comparten el núcleo del sistema; no es una máquina virtual con un sistema operativo completo.
  • Una imagen es una plantilla inmutable formada por capas; un contenedor es una instancia en ejecución de esa imagen.
  • Un buen Dockerfile aprovecha la caché de capas, usa construcción multietapa y no ejecuta la aplicación como root.
  • Los datos que deben sobrevivir al contenedor van en volúmenes o montajes enlazados, nunca dentro de la capa writable.
  • Docker Compose describe varios servicios en un solo archivo; en CI conviene etiquetar la imagen por commit y publicarla en un registro.

Qué es un contenedor

Un contenedor es un proceso, o un grupo de procesos, con su propio sistema de archivos, variables de entorno y límites de recursos. El motor de contenedores usa aislamiento del núcleo del sistema para que cada grupo crea que tiene su propia máquina, sin arrancar un sistema operativo invitado completo.

Esa diferencia explica por qué arrancan en segundos y por qué son ligeros. Una máquina virtual virtualiza el hardware y necesita un sistema operativo por invitada; un contenedor virtualiza el entorno de ejecución y comparte el núcleo con el anfitrión. En Linux, el aislamiento se apoya en espacios de nombres y grupos de control; Docker los presenta con una interfaz sencilla.

Característica Máquina virtual Contenedor
Sistema operativo Uno completo por invitada. Comparte el núcleo del anfitrión.
Arranque Segundos o minutos. Milisegundos o segundos.
Tamaño Gigabytes. Megabytes, según la imagen base.
Aislamiento Más fuerte, a nivel de hardware. Más ligero, a nivel de proceso.

Los contenedores no son una forma de seguridad perfecta por sí solos. Para cargas con requisitos de aislamiento estrictos se combinan con otras capas: usuarios sin privilegios, seccomp, limitaciones de capacidades o máquinas virtuales ligeras.

Imágenes y capas

Una imagen es una plantilla de solo lectura. Contiene el sistema base, las dependencias, el código y la configuración necesarios para arrancar un proceso. Un contenedor es esa imagen en ejecución, con una capa writable encima donde se escriben los cambios temporales.

Las imágenes se construyen por capas. Cada instrucción del Dockerfile genera una capa que se guarda en caché. Si solo cambia la última instrucción, Docker reutiliza todas las anteriores. Por eso conviene copiar primero los archivos que cambian con menos frecuencia, como los manifiestos de dependencias. 

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

En este ejemplo, si el código cambia pero package.json no, la capa de npm ci se reutiliza. Si se copiara todo antes de instalar, cualquier cambio en un archivo obligaría a reinstalar las dependencias.

Las imágenes se identifican por nombre y etiqueta, por ejemplo mi-app:1.4.0. La etiqueta latest es solo un nombre por defecto: no garantiza que sea la versión más reciente ni la misma en dos máquinas. En automatización se prefieren etiquetas concretas, como el número de versión o el hash del commit.

Escribir un Dockerfile

Un Dockerfile es la receta de la imagen. La construcción multietapa permite usar una etapa con herramientas de compilación y otra mucho más pequeña solo con el resultado. Así el compilador no viaja a producción. 

FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

La primera etapa, build, instala dependencias de desarrollo y genera dist/. La segunda copia solo ese resultado y las dependencias de producción. La instrucción USER node evita que el proceso principal se ejecute como root dentro del contenedor, una de las precauciones más rentables.

Conviene fijar versiones concretas de la imagen base, por ejemplo node:20.11-alpine en lugar de node:latest. Una imagen base mutable puede cambiar el comportamiento de la aplicación sin que cambie el Dockerfile. También ayuda un archivo .dockerignore para no copiar node_modules, .git ni secretos locales al contexto de construcción. 

node_modules
.git
.env
dist
README.md

El contexto de construcción es todo lo que Docker envía al motor antes de ejecutar el Dockerfile. Un directorio lleno de archivos grandes o datos privados se convierte en una imagen innecesariamente grande y en una oportunidad de filtrar información.

Comandos esenciales

El flujo básico es construir una imagen, arrancar un contenedor desde ella y observar qué hace. Estos comandos cubren la mayor parte del trabajo diario: 

docker build -t mi-app:1.4.0 .
docker run --rm -p 3000:3000 --name mi-app mi-app:1.4.0
docker ps
docker logs -f mi-app
docker exec -it mi-app sh
docker stop mi-app
docker rm mi-app
  • build crea la imagen a partir del Dockerfile del directorio actual.
  • run crea y arranca un contenedor; --rm lo borra al terminar.
  • ps lista los contenedores en ejecución; ps -a incluye los detenidos.
  • logs -f sigue la salida del proceso principal en tiempo real.
  • exec -it abre una sesión interactiva dentro de un contenedor en marcha.
  • stop envía la señal de parada; rm elimina el contenedor ya detenido.

Un contenedor vive mientras viva su proceso principal. Si CMD es un proceso que termina enseguida, el contenedor se detiene aunque otros procesos sigan en marcha. Por eso los servicios de larga duración deben iniciar su proceso servidor como comando principal.

Volúmenes y datos persistentes

Borrar un contenedor borra también su capa writable. Cualquier dato que deba sobrevivir, como una base de datos o los archivos subidos por usuarios, tiene que vivir fuera de esa capa. Docker ofrece tres formas principales:

  • Volúmenes con nombre: los gestiona Docker, son la opción recomendada para datos de aplicación.
  • Montajes enlazados: enlazan un directorio del anfitrión; son prácticos en desarrollo, pero acoplan el contenedor a una ruta concreta.
  • Sistemas de archivos temporales: viven en memoria y sirven para datos que no deben escribirse en disco.
docker volume create datos-app
docker run --rm -v datos-app:/var/lib/app mi-app:1.4.0
docker volume ls

Con Docker Compose se declaran en la sección volumes del archivo. Hay que tener cuidado con docker compose down -v: el modificador -v elimina también los volúmenes declarados, incluidos los datos que contenían.

Las imágenes deben poder arrancar desde cero. Si una aplicación solo funciona después de editar archivos a mano dentro del contenedor, la imagen no está reproduciendo su entorno y la próxima reedición volverá a fallar.

Redes y puertos

Cada contenedor tiene su propia pila de red. Publicar un puerto con -p 3000:3000 expone el puerto 3000 del contenedor en el puerto 3000 del anfitrión. Sin esa opción, el servicio sigue siendo alcanzable desde otros contenedores de la misma red, pero no desde fuera. 

docker network create mi-red
docker run --rm --network mi-red --name api mi-app:1.4.0
docker run --rm --network mi-red --name db postgres:16-alpine

Dentro de una red definida por el usuario, los contenedores se resuelven por nombre: api puede conectarse a db sin conocer su dirección IP. La red por defecto de Docker no ofrece esa resolución y conviene evitarla en proyectos con varios servicios.

Otro error frecuente es usar localhost desde dentro de un contenedor para hablar con un servicio del anfitrión. Para el contenedor, localhost es él mismo. En su lugar se usa el nombre del servicio dentro de la red, o la dirección host.docker.internal cuando el motor la ofrece.

Varios servicios con Docker Compose

Una aplicación real suele tener varios procesos: API, base de datos, caché o cola. Docker Compose describe todos ellos en un archivo compose.yaml y los arranca como un conjunto con una sola orden. 

services:
  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: production
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    volumes:
      - datos:/var/lib/postgresql/data
    secrets:
      - db_password

volumes:
  datos:

secrets:
  db_password:
    file: ./secrets/db_password.txt
docker compose up --build
docker compose logs -f api
docker compose down

depends_on controla el orden de arranque, pero no espera a que el servicio esté listo para aceptar conexiones. Para eso se usa una condición de salud (condition: service_healthy) o, mejor aún, que la aplicación reintente la conexión al arrancar. Una base de datos puede estar «arrancada» y seguir sin aceptar consultas unos segundos.

El mismo archivo sirve en desarrollo y en producción si se separa la configuración con archivos de sustitución o variables de entorno. Lo que no debe cambiar entre entornos es la imagen: se construye una vez y se promociona.

Variables de entorno y secretos

Las variables de entorno son la forma habitual de pasar configuración a un contenedor: dirección de la base de datos, puerto, zona horaria o nivel de registro. Un archivo .env permite agruparlas en desarrollo, pero debe estar en .gitignore y nunca dentro de la imagen. 

docker run --rm --env-file .env mi-app:1.4.0

Los secretos, como contraseñas o tokens, merecen más cuidado. Docker Compose permite declararlos como archivos que se montan en /run/secrets/, de modo que no aparecen en variables de entorno ni en el historial de la imagen. En un orquestador se usa su mecanismo de secretos equivalente.

  • No copiar secretos con COPY: forman parte de la imagen y cualquiera con acceso a ella puede leerlos.
  • No imprimir variables de entorno en los registros de arranque.
  • Dar al proceso usuario no root y permisos de lectura solo sobre el archivo que necesita.
  • Rotar credenciales y revisar qué imágenes antiguas siguen publicadas en el registro.

Las variables de entorno se ven con docker inspect. Son adecuadas para configuración no sensible; para credenciales, usa secretos o un gestor externo.

Optimizar el tamaño de las imágenes

Una imagen más pequeña se descarga antes, ocupa menos en el registro y reduce la superficie de ataque. Tres decisiones suelen bastar para mejorar mucho el resultado:

  • Elegir una base ligera: una variante alpine o slim puede reducir drásticamente el tamaño, aunque conviene comprobar compatibilidad.
  • Usar construcción multietapa: dejar compiladores y herramientas de prueba fuera de la imagen final.
  • Agrupar y limpiar en la misma capa: instalar y borrar la caché del gestor de paquetes en un solo RUN, porque borrar en una capa posterior no reduce el tamaño total.
RUN apk add --no-cache curl \
 && npm ci --omit=dev \
 && npm cache clean --force

También ayuda revisar qué se está copiando. Un COPY . . sin .dockerignore puede incluir pruebas, documentación y archivos temporales que nunca se usan en ejecución. Para diagnosticar el tamaño, se puede inspeccionar el historial de capas con docker history mi-app:1.4.0.

Docker en integración continua

La imagen construida en un proceso automatizado debe poder identificarse de forma inequívoca. La práctica habitual es etiquetarla con el hash del commit y subirla a un registro; así cada despliegue apunta a una imagen concreta, no a una etiqueta que cambia. 

- name: Construir imagen
  run: docker build -t registro/mi-app:${{ github.sha }} .
- name: Publicar imagen
  run: docker push registro/mi-app:${{ github.sha }}

Con docker buildx se pueden construir imágenes para varias arquitecturas y usar la caché del registro para acelerar ejecuciones posteriores. Si la canalización ya genera un artefacto con el código compilado, la imagen puede copiar ese artefacto en vez de repetir el build dentro del Dockerfile.

Antes de publicar conviene ejecutar las pruebas sobre la imagen final, no solo sobre el código fuente. Así se comprueba también que las dependencias de producción, los permisos y el comando de arranque son correctos. El análisis de vulnerabilidades de la imagen base se añade como otra comprobación, no como sustituto de esas pruebas.

La automatización que ejecuta estos pasos se describe en un workflow, como los de GitHub Actions y CI/CD. La decisión de qué se publica y cuándo es la misma: construir una vez, verificar y promocionar el mismo artefacto.

Errores comunes

  • Confiar en latest en lugar de fijar una versión o un hash: la misma etiqueta puede apuntar a imágenes distintas con el tiempo.
  • Instalar dependencias de desarrollo en la imagen final por no usar construcción multietapa.
  • Escribir datos dentro del contenedor y perderlos al recrearlo.
  • Usar localhost para comunicar contenedores en lugar del nombre del servicio.
  • Copiar un archivo .env al contexto de construcción y dejar secretos dentro de la imagen.
  • Ejecutar el proceso principal como root cuando no hay una razón concreta.
  • Crear una capa nueva para limpiar cachés, sin ahorrar por ello espacio en la imagen.
  • Creer que depends_on espera a que un servicio esté listo para aceptar conexiones.
  • Reconstruir la imagen en cada entorno y acabar desplegando artefactos distintos.

Si un contenedor se detiene al arrancar, mira primero docker logs. Casi siempre el proceso principal terminó por un error de configuración, un puerto ocupado o una ruta que no existe dentro de la imagen.

Concepto Para qué sirve
Imagen Plantilla inmutable construida por capas.
Contenedor Instancia en ejecución de una imagen.

Volumen Almacenamiento que sobrevive al contenedor.
