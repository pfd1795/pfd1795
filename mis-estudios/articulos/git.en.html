Version control

Git

Git is a distributed version control system: it records the project's history, allows parallel work with branches and collaboration through remote repositories.

What it is and how it thinks

Git stores snapshots of the project, not just differences. Each snapshot is a commit identified by a hash and chained to the previous one, which forms the history.

There are three zones worth distinguishing:

Zone What it contains How to move to the next
Working directoryThe files as you edit themgit add
Staging areaThe changes ready to commitgit commit
RepositoryThe commit historygit push to the remote

A commit is a meaningful save point. Staging changes in parts lets you create small, clear commits instead of one giant, mixed one.

Basic flow

# Initial configuration (once)
  git config --global user.name "Your Name"
  git config --global user.email "you@email.com"

  # Start: create a repository or clone an existing one
  git init my-project
  git clone https://example.com/user/repo.git

  # Daily work cycle
  git status                     # what has changed?
  git add index.html             # stage a specific file
  git add .                      # stage all changes
  git commit -m "Add the search box"   # save the snapshot
  git log --oneline              # view the summary history

Branches

A branch is an independent line of development. They are used to work on a feature without touching the stable version, usually main. 

git switch -c new-feature     # create a branch and switch to it
  # ... work and commit ...

  git switch main                 # go back to the main branch
  git merge new-feature           # bring the branch's changes in

  # Modern alternative: rebase rewrites history to leave it linear
  git switch new-feature
  git rebase main

Never rewrite the history of a shared branch. A rebase or a push --force on main breaks everyone else's work. Rewrite only your local branches.

If two branches touch the same lines a conflict appears: Git marks the files, you choose the final content, save and run git add and git commit to complete the merge.

Remote repositories

git remote -v                   # see the configured remotes
  git remote add origin URL       # add a remote called "origin"
  git push -u origin main         # push the branch and set it as default
  git pull                        # fetch and merge the remote's changes
  git fetch                       # fetch the changes WITHOUT merging yet

The key difference: fetch is safe because it only updates your copy of the remote; pull is fetch plus merge and can cause conflicts immediately.

Undoing changes

# Discard changes to a file you have NOT staged
  git restore file.txt

  # Remove a file from the staging area (without losing changes)
  git restore --staged file.txt

  # Fix the last commit (message or forgotten files)
  git commit --amend

  # Revert a commit already published by creating a new one that undoes it
  git revert a1b2c3d

  # Go back in local history (only if it is not shared!)
  git reset --hard a1b2c3d

For local work use restore and reset; for history already shared, revert, which deletes nothing.

Rebase and conflict resolution

When two histories diverge there are two ways to join them. Merge creates a merge commit and keeps both lines; rebase «replays» your branch's commits onto the other, producing a linear history: 

  # History with merge                    # History with rebase
  A---B---C---M---D (main)                 A---B---C---X'---Y' (main)
       \           /                                      /
        X---Y-----(feature)                ...cleaner to read

Rebasing your local branch before a pull request is a common practice (clean history); after publishing, only merge (or rebase carefully and with a heads-up to the team, because the hashes change).

A conflict is not an error: it is Git asking for a human decision:

  1. git status lists the conflicting files (marked both modified).
  2. Open them and decide the final content: the markers delimit the disputed zone:
<<<<<<< HEAD
  version on your branch (the current one)
  =======
  version on the branch being merged
  >>>>>>> incoming-branch
  1. Edit the result (you can keep both sides: remove the markers) and save.
  2. git add file marks it resolved; git commit (on merge) or git rebase --continue closes the step.
  3. If you get it wrong: git merge --abort or git rebase --abort returns everything to the previous point.

The default editor matches what git detects (git config --global) for the merge; there is also git mergetool, which opens a three-pane graphical viewer to resolve conflicts more comfortably.

Stash and cherry-pick

stash saves your unfinished work and leaves the directory clean, so you can switch tasks and come back later: 

git stash push -m "wip: search box"   # save and clean
  git stash list                      # see your stashes
  git stash pop                       # apply the most recent and drop it
  git stash apply stash@{2}           # apply a specific one (without dropping)

cherry-pick copies one specific commit from another branch into yours, without bringing the rest: 

git cherry-pick a1b2c3d              # bring that specific fix
  git cherry-pick -n a1b2c3d          # without committing (useful for regrouping)

Tags, bisect and Pull Requests

Tags mark relevant points in history, typically versions (v1.0.0); annotated ones carry a message, date and signature: 

git tag -a v1.0.0 -m "First stable version"
  git tag                              # list
  git push origin v1.0.0               # tags are not pushed with a normal push

git bisect bisects to find the exact commit that introduced a bug: you mark one «bad» and one «good», and Git serves the middle commit for you to say only whether it works or not, halving the range each step: 

git bisect start
  git bisect bad            # today: fails
  git bisect good v1.2.0    # that version worked
  # ... test, mark bad/good, repeat ...
  git bisect reset          # finish and return to your branch

The flow with a Pull Request (GitHub) / Merge Request (GitLab) is the collaborative one: one branch per task, push, and a «merge request» with review by other people, line-by-line comments, automatic CI and approval before merging: 

git switch -c my-feature        # 1) branch per task
  # ... commits ...
  git push -u origin my-feature   # 2) publish the branch
  # 3) from the web: Open Pull Request, it is reviewed and merged
  # 4) after the merge, locally: git switch main && git pull && git branch -d my-feature

On the host, main is usually protected (nobody pushes directly) so every change arrives reviewed by PR. Even in single-person projects it makes sense: each PR stays as a unit of changes with date, description and documented discussion.

Best practices

  • Make commits small and atomic: one logical change per commit.
  • Write messages in the imperative and descriptive: «Add email validation».
  • Ignore generated files and secrets with a .gitignore; never upload keys.
  • Create a branch per task and merge it through a pull request or merge request.
  • Before working, git pull to start from the most recent state.
  • Review git status and git diff before committing.

Quick reference

Command What it does
git initCreate a repository in the current folder.
git clone URLCopy a remote repository.

git addMove changes to the staging area.
git commit -m "..."Record a snapshot.
git log --onelineSummarised commit history.
git diffDifferences between work zones.
