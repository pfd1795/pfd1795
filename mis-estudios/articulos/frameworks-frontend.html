Frameworks

Frameworks de front-end

Un framework de front-end ofrece convenciones y herramientas para construir interfaces web a partir de piezas reutilizables. React, Vue y Svelte permiten organizar la interfaz mediante componentes y responder a cambios en los datos, pero difieren en su modelo y en el trabajo que realizan durante la ejecución o la compilación. Elegir uno depende del proyecto, del equipo y de cuánto comportamiento necesita la interfaz.

En 5 puntos

  • Un framework o biblioteca de front-end ayuda a estructurar interfaces dinámicas; no reemplaza HTML, CSS ni JavaScript.
  • Un componente encapsula una parte de la interfaz y puede recibir datos para representar distintos casos.
  • El estado contiene datos que pueden cambiar y cuya actualización debe reflejarse en la interfaz.
  • React, Vue y Svelte comparten el enfoque por componentes, pero sus APIs, herramientas y modelos de actualización son diferentes.
  • No toda página necesita un framework: para contenido principalmente estático, HTML, CSS y JavaScript pueden ser suficientes.

¿Qué es?

El front-end es la parte de una aplicación web con la que interactúa la persona usuaria: contenido, controles, navegación y respuestas a acciones. Se construye sobre tecnologías web como HTML, CSS y JavaScript.

Un framework de front-end organiza cómo se construyen y actualizan esas interfaces. Suele ofrecer una forma de dividir la pantalla en componentes, relacionar datos con lo que se muestra y gestionar cambios. Algunos proyectos usan «framework» como término general; otros distinguen entre framework y biblioteca por el alcance de las herramientas o por cuánto prescribe la arquitectura.

React se describe habitualmente como una biblioteca para interfaces de usuario, aunque forma parte de un ecosistema amplio de herramientas. Vue y Svelte se presentan como frameworks para construir interfaces, con sus propias convenciones y herramientas. En la práctica, los tres pueden servir para crear interfaces basadas en componentes; su modo de desarrollo no es idéntico.

Estos sistemas no generan automáticamente una aplicación completa ni resuelven por sí solos el diseño, la accesibilidad, el almacenamiento de datos o la seguridad. Esas responsabilidades siguen requiriendo decisiones explícitas.

¿Por qué usar un framework?

Cuando una interfaz contiene muchas vistas, interacciones y datos cambiantes, mantener el DOM manualmente puede volverse difícil. Un framework establece una forma consistente de asociar datos con la interfaz y de dividir el trabajo en piezas reutilizables.

  • Organización: divide una interfaz grande en componentes con responsabilidades más acotadas.
  • Reutilización: permite mostrar la misma pieza con diferentes datos, por ejemplo, varias filas de una lista.
  • Actualización: ayuda a reflejar cambios de estado en la interfaz sin tener que modificar cada elemento manualmente.
  • Convenciones compartidas: facilita que un equipo siga patrones comunes para construir y revisar funciones de interfaz.
  • Herramientas del ecosistema: puede integrarse con herramientas de desarrollo, pruebas, enrutamiento o construcción, según las necesidades del proyecto.

Estas ventajas tienen un costo: hay que aprender el modelo, mantener dependencias, configurar herramientas y seguir actualizaciones. El framework aporta valor cuando la complejidad del proyecto justifica ese costo.

El concepto de componente

Un componente es una unidad de interfaz que puede combinar estructura, comportamiento y, según el framework, estilos o lógica relacionada. Un botón, una tarjeta de producto o una barra de navegación pueden ser componentes. La granularidad debe ayudar a comprender y mantener el proyecto; dividir todo en piezas diminutas no siempre mejora el diseño.

Muchos componentes reciben propiedades (a menudo llamadas props): valores que quien los usa proporciona para determinar qué mostrar. Por ejemplo, un componente Saludo podría recibir un nombre y presentar un mensaje personalizado. Las propiedades suelen tratarse como entradas, no como datos que el componente modifica directamente.

Una composición de componentes permite construir una vista más compleja a partir de piezas pequeñas. El diagrama resume un flujo común: la aplicación entrega propiedades a un componente; este combina esas entradas con su estado y produce una representación de la interfaz.

La figura expresa una idea general, no una API idéntica a la de todos los frameworks. Cada herramienta define sus propios mecanismos para declarar componentes, recibir propiedades, gestionar el estado y responder a eventos.

Estado y flujo de datos

El estado es información que puede cambiar mientras la aplicación se ejecuta y que afecta a lo que se muestra. Un contador, el texto de un campo o el estado de apertura de un menú son ejemplos. Cuando el estado cambia por el mecanismo previsto por el framework, este puede actualizar la interfaz correspondiente.

En un patrón de flujo de datos unidireccional, los datos bajan desde componentes superiores hacia componentes descendientes mediante propiedades. Un componente hijo comunica una acción al padre mediante una función o un evento; el componente que posee el estado decide cómo actualizarlo.

Este patrón hace más fácil seguir de dónde vienen los datos y quién puede modificarlos. No significa que toda aplicación deba concentrar el estado en un solo lugar. Mantener cada dato cerca de los componentes que lo necesitan suele reducir complejidad, mientras que el estado compartido puede elevarse o administrarse con una herramienta apropiada.

  • Propiedades: entradas que el componente recibe de quien lo invoca.
  • Estado: datos que cambian y cuya actualización puede afectar la interfaz.
  • Evento o acción: interacción que expresa una intención, como pulsar un botón.
  • Actualización: cambio del estado que puede producir una nueva representación visual.

Evita duplicar el mismo dato en varios estados independientes si puede derivarse de una única fuente. Las copias pueden quedar desincronizadas cuando una de ellas cambia y las otras no.

React, Vue y Svelte

React, Vue y Svelte permiten construir interfaces con componentes, pero utilizan modelos y convenciones diferentes. La comparación siguiente es conceptual: las APIs concretas pueden cambiar entre versiones y los proyectos pueden añadir herramientas externas.

Aspecto React Vue Svelte
Enfoque Biblioteca de interfaz basada en componentes; suele combinarse con herramientas del ecosistema. Framework progresivo con componentes y opciones para adoptar más estructura según el proyecto. Framework de componentes que compila componentes para producir código que actualiza la interfaz.
Cómo se escribe la interfaz Frecuentemente con JSX, una sintaxis que combina JavaScript y una descripción similar a marcado. Frecuentemente con archivos de componente que separan plantilla, lógica y estilos. Con archivos de componente que combinan marcado, lógica y estilos, procesados por sus herramientas.
Estado Se gestiona mediante mecanismos como estado local, propiedades y, si hace falta, soluciones compartidas. Se puede declarar con opciones de la API de Options o de Composition, según el estilo elegido. Se declara con la sintaxis y las convenciones de reactividad de la versión y configuración utilizada.
Actualización de interfaz React calcula cambios en la interfaz a partir de una nueva descripción; usa reconciliación y un modelo de árbol de elementos. Vue rastrea dependencias reactivas y actualiza las partes afectadas mediante su sistema de renderizado. El compilador analiza los componentes y genera mecanismos de actualización para los cambios detectados.
Elección frecuente Puede encajar cuando el equipo necesita su ecosistema, sus patrones o experiencia previa. Puede resultar atractivo cuando se busca una adopción gradual y una estructura integrada. Puede interesar a equipos que valoran su modelo de compilación y su sintaxis de componentes.

No existe una opción universalmente mejor. La experiencia del equipo, las necesidades de accesibilidad, el soporte requerido, el ecosistema, las restricciones técnicas y la capacidad de mantenimiento son criterios más útiles que una afirmación aislada sobre velocidad o popularidad.

Virtual DOM y renderizado

El DOM es la representación que el navegador expone para el documento HTML. Cambiarlo permite actualizar una página, pero administrar manualmente muchas modificaciones puede ser complicado.

El término Virtual DOM suele referirse a una representación en memoria de la interfaz que ciertos sistemas comparan entre actualizaciones para decidir qué cambios aplicar al DOM real. React utiliza un proceso de reconciliación basado en su representación de elementos. Vue también usa un DOM virtual en su sistema de renderizado.

Svelte sigue un enfoque de compilación: procesa componentes durante la construcción y genera código que actualiza la interfaz cuando cambian los datos. Por eso suele explicarse como una alternativa basada en compilación, no simplemente como otro framework que funciona del mismo modo que React o Vue.

Estas descripciones no permiten concluir por sí solas cuál será más rápido en una aplicación concreta. El rendimiento depende del patrón de uso, el tamaño del código, las actualizaciones, el navegador, la configuración y otras decisiones. Para elegir por rendimiento, mide una carga representativa del proyecto en vez de basarte únicamente en el nombre de una técnica.

Renderizar también puede referirse a producir HTML en el servidor, renderizar en el navegador o generar una salida estática durante la construcción. Son estrategias de entrega diferentes, y algunos ecosistemas admiten varias.

Un contador en React, Vue y Svelte

Los siguientes ejemplos representan la misma interacción: mostrar un número y aumentarlo al pulsar un botón. Son ejemplos breves para comparar los modelos; requieren un proyecto configurado para cada herramienta y no son archivos HTML autónomos.

React

import { useState } from 'react';

function Contador() {
  const [cantidad, setCantidad] = useState(0);

  return (
    <section>
      <p>Cantidad: {cantidad}</p>
      <button onClick={() => setCantidad(cantidad + 1)}>
        Sumar
      </button>
    </section>
  );
}

El estado local se declara con useState. Al llamar a la función de actualización, React recibe el nuevo estado y vuelve a procesar el componente según sus reglas.

Vue

<script setup>
import { ref } from 'vue';

const cantidad = ref(0);
</script>

<template>
  <section>
    <p>Cantidad: {{ cantidad }}</p>
    <button @click="cantidad++">
      Sumar
    </button>
  </section>
</template>

En este ejemplo con Composition API, ref crea un valor reactivo. En la plantilla, Vue actualiza la vista cuando cambia ese valor; dentro del bloque de JavaScript se accede mediante .value en contextos donde no se aplica la desreferencia automática de la plantilla.

Svelte

<script>
  let cantidad = 0;
</script>

<section>
  <p>Cantidad: {cantidad}</p>
  <button on:click={() => cantidad += 1}>
    Sumar
  </button>
</section>

Este ejemplo ilustra la sintaxis clásica de eventos de Svelte. La sintaxis concreta puede variar según la versión del compilador y las convenciones actuales del proyecto; al iniciar un proyecto, conviene seguir la documentación correspondiente a la versión instalada.

Cuándo no usar un framework

Un framework no es un requisito para crear una web. Añadirlo puede aumentar el tamaño del código entregado, la complejidad de configuración y el esfuerzo de mantenimiento. Si el sitio tiene pocas interacciones y contenido principalmente estático, HTML semántico, CSS y JavaScript sencillo pueden ser suficientes.

También puede no convenir si el equipo no tiene tiempo para aprender y mantener la herramienta, si el proyecto debe integrarse con una base existente incompatible o si los beneficios no compensan el costo. La decisión debe considerar la vida del proyecto, no solo la rapidez de escribir la primera pantalla.

Una estrategia intermedia es incorporar comportamiento dinámico solo en las partes que lo necesitan, sin convertir toda página en una aplicación compleja. La arquitectura depende del sitio, de sus requisitos y de las capacidades del equipo.

Errores comunes

Error Por qué causa problemas Mejor enfoque
Elegir por una afirmación general de rendimiento. El resultado depende del proyecto, su configuración y cómo se actualiza la interfaz. Compara una carga representativa y mide con herramientas adecuadas.
Guardar el mismo dato en varios estados sin necesidad. Las copias pueden divergir y mostrar información contradictoria. Define una fuente principal y calcula los valores derivados cuando sea posible.
Crear componentes demasiado grandes o demasiado pequeños. En un extremo se mezclan responsabilidades; en el otro, la composición se vuelve difícil de seguir. Divide según responsabilidades claras y reutilización real.
Modificar directamente el DOM sin considerar el modelo del framework. Puede desincronizar la interfaz con el estado que mantiene la aplicación. Usa los mecanismos previstos por la herramienta y reserva la manipulación directa para casos que la justifiquen.
Tratar las propiedades como estado modificable por el componente hijo. Se vuelve confuso quién es responsable de actualizar los datos. El hijo comunica una acción y el propietario del dato decide el cambio.
Usar un framework aunque la página no lo necesite. Añade dependencias y conceptos que el proyecto quizá no aproveche. Evalúa la cantidad de interacción, el mantenimiento y las capacidades del equipo.
Copiar ejemplos sin verificar la versión. La sintaxis, las herramientas y las convenciones pueden cambiar. Comprueba la documentación de la versión que utiliza el proyecto.
