Automated testing

An automated test is a program that checks another program and decides whether the result is correct without human intervention. Chosen well, tests turn the fear of touching code into the confidence to change it: they fail quickly, point to the exact spot and run the same on everyone's laptop and on the continuous integration server.

In 5 points

  • A test is code that verifies code: it sets up a situation, performs an action and compares the result with what was expected.
  • Unit tests check isolated pieces, integration tests verify that several pieces cooperate, and end-to-end tests walk through a complete flow from the interface.
  • A healthy pyramid has many unit tests, fewer integration tests and a few end-to-end tests: the first are fast and precise, the last are slow and fragile.
  • A good test names the behaviour, has a single reason to fail and does not depend on execution order, the clock or external data.
  • Coverage looks at which code ran, not what was checked: it is useful for finding gaps, not as a goal in itself.

What is an automated test?

A test case describes a starting situation, an action and the expected result. Automating it means writing that description as code so the machine can repeat it. The piece being checked is usually called the subject under test, and the final check is an assertion: a statement that must hold or the test fails. 

import test from 'node:test';
import assert from 'node:assert/strict';
import { cartTotal } from '../cart.js';

test('adds the prices and applies the discount', () => {
  const cart = [
    { price: 10, quantity: 2 },
    { price: 5, quantity: 1 }
  ];

  const total = cartTotal(cart, 0.1);

  assert.equal(total, 22.5);
});

Here the situation is the cart, the action is calling cartTotal and the assertion compares the result with 22.5. If someone changes the calculation and the total is no longer that, the test fails at the exact point of the change.

A test does not prove that the code is correct: it shows that, for the cases it describes, the behaviour still matches what was agreed. Its value lies in being cheap and fast to repeat every time the code changes.

Why automate?

Checking by hand that a page still works after every change is possible at first and impossible after a few months. Automated tests provide three things manual review cannot guarantee:

  • Regression detection: an apparently harmless change that breaks an old feature is found before release.
  • Confidence to refactor: you can restructure code knowing that observable behaviour is still being checked.
  • Executable documentation: test names describe concrete use cases and stay in sync with the code.

Tests have a cost too: they must be written, read and maintained, and sometimes they fail because of a legitimate change. That is why you start with the important behaviours, not every line of the program.

The testing pyramid

Not all tests cost the same. The usual way to picture it is a pyramid: a wide base of fast tests and a narrow tip of slow ones.

Type What it checks Speed and stability
Unit An isolated function or class. Very fast and deterministic.
Integration That several modules cooperate: code, database, queue or API. Fast or medium; somewhat more fragile.
End-to-end A complete user flow through the interface. Slow and more prone to intermittent failures.

If the pyramid is inverted and almost everything is tested from the browser, each run takes minutes, failures are hard to locate and the team stops trusting the result. The practical rule is to check each behaviour at the lowest level that can truly verify it.

Unit tests

A unit test exercises a small piece without starting the whole application. To be stable, the piece must not depend on the current time, the network, a file or the order in which other tests ran. If it does, replace that dependency with a double. 

test('rejects a negative quantity', () => {
  const cart = [{ price: 10, quantity: -1 }];

  assert.throws(() => cartTotal(cart), /quantity/);
});

The arrange, act, assert (AAA) pattern helps keep the structure: first the data is prepared, then the function is called and finally the assertions are made. It is worth leaving a blank line between the three parts so the case can be read at a glance.

You do not need a test for every function. A private function used only from another one is covered by testing the public behaviour; testing it separately couples the test to implementation details that will change.

Integration tests

Integration tests answer a different question: «do these pieces work together?». They check, for example, that a route calls the right service, that a SQL query returns what was expected or that a published message reaches its consumer.

The boundaries of the system are the important ones here. You can use a real database in a test environment, a local HTTP server or an in-memory repository with the same contract. What you avoid is configuration shared between tests: each one should create its own data and clean it up afterwards. 

test('saves the user and returns their id', async () => {
  const saved = [];
  const repository = {
    save: async (user) => {
      saved.push(user);
      return 'u-1';
    }
  };

  const id = await registerUser('ana@example.com', repository);

  assert.equal(id, 'u-1');
  assert.equal(saved[0].email, 'ana@example.com');
});

This test needs no database because it injects a fake repository with the same contract. That makes it fast; a test with the real database would also check the query and the constraints.

End-to-end tests

An end-to-end test, or E2E, drives the real application through the interface: it opens a page, fills in a form and checks the visible result. It is the one that most resembles what a person does and the best at detecting integration problems between frontend, backend and deployment. 

test('the user can sign in', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('user@example.com');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});

Browser tools such as Playwright or Cypress enable this style of test. A few decisions make the difference:

  • Find elements by role, label or visible text, not by CSS classes that change with the design.
  • Wait for an observable condition instead of using fixed pauses.
  • Prepare data through the API or database before opening the page, rather than doing setup clicks in every test.
  • Save screenshots and traces on failure, to understand the browser state without reproducing it by hand.

An E2E flow does not replace unit tests: when it fails, it usually says «something broke», not which specific function. That is why they are reserved for critical product journeys: sign-up, checkout, publishing.

How to write a good test

A useful test reads like an example. If its name does not tell you which behaviour it describes, someone will have to read the code to understand it. A few simple rules improve the suite a lot:

  • Name the behaviour: «applies the discount to the total» says more than «test 2».
  • One reason to fail: if a test checks three different things, a failure does not tell you which one broke.
  • Assert on results, not on how they are computed: changing the algorithm should not break the test if the result is still correct.
  • Independence: any test should be able to run on its own and in any order.
  • Minimal, explicit data: only the fields that affect the result; the rest is built with factories or generators.
  • No uncontrolled dates or random numbers: fix the clock or inject a deterministic generator.

When a test fails in continuous integration but not locally, it most likely depends on something in the environment: time zone, language, file order or persistent state. Look for that dependency before rerunning it hoping it passes.

Test doubles

A double replaces a real dependency during a test. Names vary by framework, but the ideas are these:

  • Fake: a simple implementation of the same contract, such as an in-memory repository.
  • Stub: returns prepared values and does not check how it is used.
  • Spy: records calls so they can be reviewed afterwards.
  • Mock: additionally requires certain calls to happen and usually fails if they do not.

Use the simplest double that does the job. If you only need a function to return a value, a stub is enough. If you need to check that an email was sent, a spy or a mock makes sense. Replacing too many pieces with mocks produces tests that pass even when the application is broken: they check calls, not behaviour.

It is not worth mocking what is not yours, such as the standard library or the framework. Those libraries already have their own tests; mocking them only adds fragility.

Coverage and quality

Coverage measures which part of the code ran during the tests: lines, branches, functions or statements. It is a useful signal for finding untested areas, not a measure of quality. 

node --test --experimental-test-coverage
npm test -- --coverage

100% line coverage can coexist with tests that check nothing: just call every function without assertions. Conversely, an uncovered area is not always a problem, for example defensive code that cannot be reached.

To judge a test suite properly you can use mutation testing: the tool changes a condition or operator in the code and checks whether any test fails. If none fails, that behaviour was not protected. It is slower than coverage but answers the right question.

Interface tests

In a web interface you can test a piece without a browser by mounting the DOM with a testing library and checking what the user can see and do: a visible error message, a disabled button, the focus after closing a dialog.

These tests resemble unit tests in speed and E2E tests in judgement: they interact with labels and roles, not internal component details. For example, they check that typing into a search field shows the filtered result and updates the counter, regardless of which internal function computes it.

Accessibility and testing get along well: if a test finds a button by its accessible name, that is the same name a screen reader uses. A selector that only works through a CSS class does not provide that signal.

Tests in continuous integration

Tests nobody runs become outdated. Continuous integration runs them on every change and turns the result into a condition for merging: if they fail, the change does not go in. 

name: tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test

Order matters: fast checks come first to give feedback early, and the build or browser tests run afterwards. It is worth pinning the runtime version and using a strict dependency install so a failure does not depend on an accidental update.

Flaky tests deserve immediate attention. A test that fails once every twenty runs trains the team to ignore the result and destroys the value of the whole suite. Isolate it, fix it or remove it; do not leave it for later.

Common mistakes

  • Testing implementation details, such as the name of an internal variable or a specific call, instead of the observable result.
  • Writing tests that share state: one modifies a global variable and the next one fails only when run after it.
  • Using fixed pauses in browser tests instead of waiting for a condition.
  • Chasing a coverage percentage with empty assertions.
  • Mocking so many dependencies that the test stops resembling the real application.
  • Repeating the same long journey in dozens of E2E tests when a few unit tests cover it better.
  • Ignoring flaky tests until nobody trusts the result of continuous integration.
  • Not updating a test when the expected behaviour really changes: then the test is the one that is wrong.

If a test fails after an intentional change, do not tweak it until it passes. First check whether the new behaviour is what you want and write the assertion to match that decision.

Quick reference

Concept What it is for
Assertion Check that the result meets expectations.
Unit test Verify an isolated, deterministic piece.
Integration test Verify that several pieces cooperate.
E2E test Walk through a complete flow from the interface.
Double Replace a dependency to control the test.
AAA Arrange, act and assert, in that order.
Coverage Point out code not executed by the tests.
Regression A failure in a feature that used to work.
